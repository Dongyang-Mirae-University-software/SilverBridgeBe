  Skill이란?
  Claude Code(AI 코딩 도우미)가 특정 작업을 할 때 따르는 "체크리스트 + 템플릿"
  꾸러미입니다. 각 Skill은 .claude/skills/<이름>/SKILL.md 파일로 존재하며,
  자연어로 호출하면(예: "architecture-review 진행해줘") AI가 해당 가이드를
  로드한 뒤 그 절차대로 작업을 수행합니다.

  ▶ 설치 위치
    .claude/skills/<skill-name>/SKILL.md
    .claude/skills/README.md  (전체 목록 인덱스)

  ▶ 레벨별 분류
    Macro       : architecture-review        (패키지·모듈·레이어 구조)
    Meso        : design-patterns, java-code-review, solid-principles
                                              (클래스·인터페이스 설계)
    Micro       : clean-code                 (함수·네이밍·표현식)
    Framework   : spring-boot-patterns, jpa-patterns
                                              (Spring/JPA 특화)
    Cross-cut   : security-audit, test-quality, logging-patterns,
                  concurrency-review, performance-smell-detection,
                  api-contract-review        (보안·테스트·로깅·동시성·성능·API)
    Workflow    : work-prompt, git-commit, changelog-generator,
                  issue-triage, maven-dependency-audit, java-migration
                                              (작업 절차·커밋·릴리스·의존성·버전업)

  ※ 정확한 최신 목록은 .claude/skills/README.md 가 기준입니다(이 문서는 요약).

  ▶ 타입별 분류
    Audit (기존 코드 점검) : architecture-review, java-code-review,
                            security-audit, api-contract-review,
                            performance-smell-detection, concurrency-review
    Template (새 코드 작성): spring-boot-patterns, jpa-patterns,
                            design-patterns, solid-principles, clean-code,
                            logging-patterns, test-quality

  ▶ 자주 쓰는 호출 예시
    "test-quality 로 AuthService 단위 테스트 추가"
    "security-audit 으로 auth 도메인 OWASP 점검"
    "jpa-patterns 로 User 엔티티 N+1 검토"
    "spring-boot-patterns 로 Controller-Service-Repository 검토"
    "architecture-review 로 domain/global 패키지 경계 점검"
    "java-code-review 로 PR 변경 파일 리뷰"

  ▶ 협업 원칙 (CLAUDE.md §2)
    1) 개발자가 결정, AI는 제안만 — 변경은 항상 검토 후 적용
    2) 자동 git 커밋·푸시 금지 — 명시적 승인 후 진행
    3) 변경 범위 투명화 — 어떤 파일이 왜 바뀌는지 항상 설명
    4) 점진적 채택 — 읽기 전용 분석 → 제안 → 리뷰 → 적용 순서

  SilverBridge 백엔드 프로젝트 설명서
================================================================================

--------------------------------------------------------------------------------
  1. 이 프로젝트는 무엇인가요?
--------------------------------------------------------------------------------

SilverBridge는 노인(피보호자)과 그 가족(보호자)을 연결하는 서비스입니다.

  - 피보호자 (WARD)   : 돌봄을 받는 노인
  - 보호자 (GUARDIAN) : 피보호자를 관리하는 가족/보호자
  - 관리자 (ADMIN)    : 서비스 전체를 관리하는 운영자

이 저장소는 "백엔드" 코드입니다.
백엔드란, 앱/웹 화면 뒤에서 실제 데이터를 처리하고 저장하는 서버 프로그램입니다.
프론트엔드(화면)가 백엔드에 "요청"을 보내면, 백엔드가 처리한 결과를 "응답"으로 돌려줍니다.
이 요청/응답 방식을 API라고 부릅니다.

  [개발 서버]
  서버 주소  : api.devdmu.gosky.kr (포트 6511)
  메인 페이지: devdmu.gosky.kr
  데이터베이스: PostgreSQL 17 (포트 6513)
  캐시 서버  : Redis 7.2 (포트 6514)


--------------------------------------------------------------------------------
  2. 사용하는 기술 (비유로 이해하기)
--------------------------------------------------------------------------------

  Java 21 / Spring Boot 4 : 서버를 만드는 프로그래밍 언어와 프레임워크.
                            "프레임워크"는 건물의 철골 구조처럼 기본 틀을 제공합니다.

  PostgreSQL 17  : 관계형 데이터베이스. 회원 정보, 연결 정보 등 모든 데이터를
                   저장하는 창고. 엑셀 표처럼 행/열로 데이터를 관리합니다.

  Redis 7.2      : 매우 빠른 임시 저장소. SMS 인증번호처럼 "잠깐 저장했다가
                   쓰고 버리는" 데이터를 담습니다.
                   냉장고(PostgreSQL) vs 조리대(Redis) 의 차이로 이해하세요.

  JWT (토큰)      : 로그인 후 받는 "디지털 출입증". 이후 모든 API 요청에 토큰을
                   함께 보내 본인임을 증명합니다.
                   accessToken (30분 유효) / refreshToken (7일 유효)

  WebSocket (STOMP, 네이티브 wss) : 서버가 클라이언트에게 먼저 메시지를 보낼 수 있는
                   양방향 통신 방식. 연결 요청/수락/해제 등 실시간 알림에 사용.

  FCM            : Firebase Cloud Messaging. 앱이 꺼져 있어도 도달하는 푸시 알림.

  Flyway         : 데이터베이스 스키마 버전 관리 도구. V1, V2, ... 순서대로
                   마이그레이션을 자동 적용합니다.

  Docker         : 서버 프로그램을 "컨테이너"라는 독립된 환경에 담아 실행.
                   어느 서버에서든 동일하게 동작하도록 포장해줍니다.

  Swagger / OpenAPI : API 명세서 자동 생성 도구.
                   주소: api.devdmu.gosky.kr/swagger-ui/index.html


--------------------------------------------------------------------------------
  3. 주요 기능과 API 흐름
--------------------------------------------------------------------------------

  ★ API란?
  앱이 서버에 특정 주소(URL)로 요청을 보내는 것입니다.
    - GET    : 데이터 조회 (읽기)
    - POST   : 데이터 생성 또는 특정 동작 실행
    - PUT    : 데이터 전체 수정
    - PATCH  : 데이터 일부 수정
    - DELETE : 데이터 삭제


  [ 3-1. 일반 회원가입 (4단계) ]
  ─────────────────────────────
  이메일/비밀번호로 가입하며 전화번호 SMS 인증이 필요합니다.

  1단계) 이메일 중복 확인
    → POST /api/auth/signup/email/check
    → 이미 가입된 이메일이면 오류 반환

  2단계) SMS 인증코드 발송
    → POST /api/auth/signup/sms/send
    → 입력한 전화번호로 6자리 숫자 문자 발송 (5분 유효)
    → 재발송 쿨다운 없음 — 즉시 재요청 가능. 단 한 번호당 발송 상한(1시간 10회, A-M3)
    → 재발송: POST /api/auth/signup/sms/resend

  3단계) SMS 인증코드 확인
    → POST /api/auth/signup/sms/verify
    → 받은 숫자 입력해 본인 확인 (인증 완료 후 10분 이내에 4단계 진행)
    → 5회 이상 오류 시 인증코드 자동 초기화 → 재발송 필요
    → 응답으로 verificationNonce(UUID) 반환 — 4단계 요청에 그대로 첨부 필수

  4단계) 회원가입 완료
    → POST /api/auth/signup
    → 이름, 이메일, 비밀번호, 전화번호, 역할(WARD/GUARDIAN), 성별(FEMALE/MALE),
      생년월일(yyyy-MM-dd · 미래 불가 · 만 14세 이상~120세 이하), 우편번호(숫자 5자리),
      주소, 상세주소, verificationNonce 입력
    → 모든 필드 필수 (우편번호·주소는 카카오 주소 API 결과값 권장)
    → verificationNonce 누락/불일치 시 SMS_NOT_VERIFIED 400
      (phone 단일 식별만으로 인증 우회 가입하던 결함 차단 — H-5)


  [ 3-2. 로그인 / 로그아웃 / 토큰 재발급 ]
  ─────────────────────────────
  로그인:
    → POST /api/auth/signin
    → 이메일 + 비밀번호 입력
    → 성공 시 accessToken(30분) + refreshToken(7일) 반환

  이후 모든 API 요청 헤더에 다음 형식으로 토큰 첨부:
    Authorization: Bearer {accessToken}

  accessToken 만료 시 재발급:
    → POST /api/auth/refresh
    → refreshToken 전달 → 새 accessToken + 새 refreshToken 반환
    → 기존 refreshToken은 즉시 무효화 (Refresh Token Rotation)
    → 폐기된 옛 refreshToken이 다시 들어왔는데 같은 사용자에게 다른
      refreshToken이 남아 있으면 도난 신호로 간주 → 해당 사용자의 모든
      refreshToken 강제 폐기 + access_log에 TOKEN_REUSE_DETECTED 기록 (H-3)
    → POST /api/auth/refresh 도 1분 10회 rate limit 적용 (M-8)

  로그아웃:
    → POST /api/auth/logout
    → accessToken을 Redis 블랙리스트에 등록해 재사용 차단
      (키는 토큰 원문이 아니라 SHA-256 해시 — Redis 메모리 절약·원문 비노출, M-6)
    → 미인증 상태 요청은 401 JSON 반환 (permitAll에서 logout만 분리, L-3)

  아이디(이메일) 찾기:
    → POST /api/auth/find-email
    → 이름 + 전화번호로 계정 조회
    → 마스킹된 이메일 반환 (예: us**@example.com)

  ※ 보안 정책:
    - 로그인 실패 응답 통합: 미가입 이메일 / 비밀번호 불일치 모두
      INVALID_CREDENTIALS(401) 동일 응답 — 계정 존재 여부 추측 차단 (H-1)
    - INACTIVE 안내는 비밀번호 검증을 통과한 본인에게만 노출 (H-1)
    - 로그인 실패 잠금은 user.id 기준으로 5회 실패 시 30분 잠금
      (LOGIN_LOCKED 429). 임의 이메일로 정상 사용자를 잠그는 DoS 차단 (H-2)
      ※ 미가입 이메일은 잠금 카운터에 영향 없음
      ※ 5회/30분 값은 application.yaml auth.login.* 로 외부화 (M-12)
    - INACTIVE 계정은 로그인 차단 + Refresh Token 즉시 삭제
      (login·kakaoLogin·refresh 세 경로 모두 일관 적용, H-4)
    - 로그인(/signin)도 IP 기준 1분 10회 rate limit 적용 — 계정 분산
      credential stuffing/password spraying 차단 (A-H2)
    - JWT에 typ(access/refresh) 클레임 부여 → refreshToken을 Authorization
      헤더(Bearer)로 제시해 보호 자원에 접근하는 토큰 혼용을 필터가 차단 (A-H1)
      ※ 배포 시점에 발급돼 있던 옛 accessToken(typ 없음)은 1회 401 후 refresh로 자동 재발급


  [ 3-3. 카카오 로그인/회원가입 ]
  ─────────────────────────────
  카카오 계정으로 소셜 로그인하는 방식입니다.

  기존 회원 로그인:
    → POST /api/auth/signin/kakao  (카카오 인가코드 전달, body: { code })
    → isNewUser=false, accessToken + refreshToken 반환

  신규 회원 가입 (4단계):
    1) POST /api/auth/signin/kakao       → isNewUser=true, kakaoId/이메일 반환
                                            (이름은 항상 null — 카카오 닉네임 미사용, 본인 실명 직접 입력)
    2) POST /api/auth/signup/sms/send    → 전화번호 SMS 발송
    3) POST /api/auth/signup/sms/verify  → SMS 인증 확인 → verificationNonce 반환
    4) POST /api/auth/signup/kakao       → 역할(WARD/GUARDIAN) + 전화번호 + 성별 + 생년월일 +
                                            우편번호 + 주소 + 상세주소 + verificationNonce 입력 후
                                            최종 가입 (모든 필드 필수, 성공 시 201 Created)

  ※ 엔드포인트 정정: 로그인은 /api/auth/signin/kakao, 가입 완료는
    /api/auth/signup/kakao (과거 메모의 /api/auth/kakao·/kakao/register는 오기).
  ※ kakaoId는 1번 응답의 값을 4번까지 계속 사용합니다.
  ※ 3번 응답의 verificationNonce를 4번 요청에 첨부해야 가입됩니다 (H-5).
  ※ isNewUser 값에 따라 응답 구조가 달라집니다.
  ※ 2026-05-25 보안 강화: 백엔드의 인가코드→토큰 교환 요청에 client_secret를 함께 전송합니다.
    값은 KAKAO_CLIENT_SECRET 환경변수로만 주입(코드/Git 비노출)하며, 카카오 콘솔
    [보안 > Client Secret]에서 코드 발급 후 "사용 함" 활성화가 필요합니다. 미설정·약한 값이면
    시작 단계에서 차단됩니다 (Required/SecurityConfigValidator).

  ※ CSRF(state) 방어는 프론트 검증 모델(모델 A)로 결정 (2026-05-18, M-1):
    프론트가 카카오 인가 요청 시 난수 state 생성·sessionStorage 보관,
    콜백에서 자체 대조 후 백엔드에는 code만 전달. 백엔드는 state를 받지도
    검증하지도 않음 (KakaoLoginRequest 변경 없음). 프론트 카카오 로그인은
    아직 미구현 — 신규 구현 시 state 검증 포함 예정.


  [ 3-4. 비밀번호 재설정 (3단계) ]
  ─────────────────────────────
  ※ 2026-05-23 갱신: 시니어/4050 타겟 UX 우선 — 미가입/카카오 계정에 always-200 대신
    명시적 응답(404/400)을 준다. 노출되는 enumeration은 IP 이중 윈도우 RateLimit +
    per-email 발송 상한 + 미가입 WARN 로깅으로 방어.
  이메일 또는 SMS 중 선택. 흐름은 6자리 인증코드 하나로 통일됩니다 (UUID 토큰 없음).

  ▶ 이메일 방식
    1단계) POST /api/auth/find-password/email/send
           → 가입 이메일로 6자리 인증코드 발송 (5분 유효, 쿨다운 없음)
           → 재발송: /email/resend
    2단계) POST /api/auth/find-password/email/verify
           → 6자리 코드 사전 확인 (코드 소비 안 함 — 토큰 미발급)
    3단계) POST /api/auth/password/reset
           → email + 같은 6자리 code + 새 비밀번호 입력 → 변경 완료

  ▶ SMS 방식
    1단계) POST /api/auth/find-password/sms/send
           → 이름+전화번호로 계정 조회 후 6자리 인증코드 SMS 발송 (5분 유효, 쿨다운 없음)
           → 재발송: /sms/resend
    2단계) POST /api/auth/find-password/sms/verify
           → 6자리 코드 사전 확인 (코드 소비 안 함)
    3단계) POST /api/auth/password/reset
           → phone + 같은 6자리 code + 새 비밀번호 입력 → 변경 완료

  ※ email / phone 은 정확히 하나만 채워 보냅니다. 코드 5회 오류 시 무효화 → 재발송 필요.
  ※ confirm(reset) 은 코드 검증을 사용자 조회보다 먼저 수행해 가입 여부·provider 가
    응답으로 새지 않게 합니다 (A-M1).
  ※ 비밀번호 변경 성공 시 모든 기기에서 자동 로그아웃됩니다.
    - refreshToken 전부 삭제 + 발급돼 있던 accessToken도 즉시 무효화
      (Redis password:invalidate:{userId} 에 변경 시각 기록 → JWT 필터가
       그 시각 이전 발급 토큰을 401 차단. Critical-1)
    - 이로써 "비밀번호를 바꿔도 옛 accessToken이 최대 30분 살아 있던" 결함 해소
  ※ 정책(2026-05-23 갱신): send/resend는 미가입 시 404("해당 이메일로 가입된 계정이 없습니다"
    /SMS는 "사용자를 찾을 수 없습니다"), 카카오 가입 계정은 400으로 명확히 안내한다.
    (기존 "가입 여부 노출 방지를 위해 계정이 없어도 200 반환"은 폐지 — 시니어 이탈 UX 개선)
    어뷰징 방어: 미가입 시 SMS/메일 발송 전 차단(비용 보호), 미가입 404는 [PW-RESET] WARN 로깅.
  ※ Rate Limit(2026-05-23 갱신): send/resend 4개는 IP 이중 윈도우 1분 10회 / 1시간 30회.
    per-email 발송 상한 password:email:sendcount 1시간 10회(SMS sms:sendcount A-M3와 대칭).
  ※ POST /api/auth/password/reset 도 1분 10회 rate limit 적용 (M-8).
  ※ 비밀번호 재설정 완료 시 access_log에 IP/UA 포함 기록 (M-3).

  [ 3-6. 보호자 ↔ 피보호자 연결 ]
  ─────────────────────────────
  보호자가 피보호자 6자리 ID를 입력해 연결 요청 → 피보호자가 수락/거절.

  연결 요청 (보호자):
    → POST /api/guardian/connection/request
    → body: { "targetId": "피보호자 6자리 ID" }
    → DB에 PENDING 상태로 저장
    → 피보호자에게 WebSocket + FCM 푸시 알림

  수락/거절 (피보호자):
    → POST   /api/ward/connection/{연결ID}/accept            → ACTIVE 전환    → 보호자에게 WebSocket + FCM 알림
    → DELETE /api/ward/connection/request/{연결ID}/refusal   → CANCELLED 전환 → 보호자에게 WebSocket + FCM 알림 (2026-05-28 추가)

  연결 목록 조회:
    → GET /api/guardian/connection/select    → 보호자: 내 피보호자 (ACTIVE + PENDING)
    → GET /api/guardian/connection/requests  → 보호자: 내가 보낸 요청 전체(취소/거절 포함)
    → GET /api/ward/connection/active        → 피보호자: 내 보호자 (ACTIVE)
    → GET /api/ward/connection/pending       → 피보호자: 받은 PENDING 요청 카드(전화 마스킹, 최소정보)

  연결 조회 응답의 상대방(partner) 프로필 필드 (ConnectionResponse) — 2026-06-02 보강:
    상시 노출 : partnerUserId, partnerName, partnerProfileImage, relation, status,
                isRequester, connectedAt, createdAt
    ACTIVE에서만 노출(PENDING/취소/거절은 null — "연결 성립 전 비노출" 정책):
                partnerPhone, partnerAddress, partnerAddressDetail,
                partnerPostcode, partnerGender(FEMALE/MALE), partnerBirthDate(ISO),
                partnerEmail
    → 케어 서비스 특성상 연결된 양쪽(보호자/피보호자)이 상대 프로필 전체를 상호 열람.
      성별/생년월일/우편번호는 미입력(기존·일부 카카오) 계정이면 ACTIVE라도 null.
    → 민감/시스템 필드(비밀번호·소셜 내부 ID·권한·계정상태·로그인시각)는 절대 미노출.
    ※ 수락 전 카드(/ward/connection/pending)는 의도적으로 최소정보+전화 마스킹 유지(프로필 미노출).

  연결 해제:
    → DELETE /api/guardian/connection/cancel/{연결ID}   → 보호자: PENDING 요청 취소
    → DELETE /api/guardian/disconnection/{연결ID}       → 보호자: ACTIVE 연결 해제
    → DELETE /api/ward/disconnection/{연결ID}           → 피보호자: ACTIVE 연결 해제

  연결 상태 흐름:
    PENDING(대기)  →  ACTIVE(활성)     [피보호자 수락 → 보호자에게 실시간 알림]
    PENDING(대기)  →  CANCELLED(해제)  [보호자 취소(무알림) / 피보호자 거절(보호자에게 실시간 알림, 2026-05-28 추가)]
    ACTIVE(활성)   →  CANCELLED(해제)  [어느 쪽이든 해제 → 상대에게 알림]

  긴급 SOS (피보호자 전용):
    → POST /api/ward/sos   → SOS 발생 이력 저장(sos_event) + 연결된 ACTIVE 보호자 전원에게
                             긴급 알림 발송(WebSocket /topic/{보호자ID}/sos-triggered + FCM). (2026-06-09 추가)
                             · 필수 알림(WARD_SOS) — 보호자 알림 설정(ON/OFF)과 무관하게 FCM 강제 발송.
                               FCM이 실제로 전달되지 않으면(토큰 없음·전 토큰 만료·발송 예외) SMS로 폴백
                               (결과 기반 폴백, M-S2-1). 이상감지와 달리 SOS만 폴백이 있습니다.
                             · 보호자 여러 명이면 전원 발송(한 명 실패가 다른 보호자 막지 않음)
                             · 알림 쿨다운: 같은 피보호자의 반복 SOS는 Redis 쿨다운으로 억제(fail-open)
                             · 동작 설정(GET·PUT /api/ward/sos-setting)은 119 연결·안내 흐름만 정하며,
                               어떤 값에서도 보호자 알림은 항상 발송됩니다 (3-12 참고)
                             · 요청 바디는 선택 — { location } 발생 위치 자유 문구(100자). (2026-07-31 추가)
                               바디 없이 호출하면 종전과 동일(위치 미상 = NULL). 서버는 위치를 추정하지
                               않고(지오코딩·주소 조회 없음) 프론트가 보낸 문구를 보관·노출만 합니다.
                             · 응답: { sosEventId, triggeredAt }
                             · 119 통화 화면 / 보호자 직접 전화는 프론트 처리(백엔드 무관).
                               직접 전화번호는 GET /api/ward/connection/active 의 partnerPhone 사용

  SOS 이력 조회 · 처리 결과(ACK) (보호자 전용, 2026-07-31 추가):
    → GET   /api/guardian/sos/history            → 연결된 피보호자의 SOS 이력(발생 최신순, 페이징)
                             · 쿼리: wardId(선택 — 생략 시 ACTIVE 연결 피보호자 전원의 이력 병합) /
                                     page(기본 0) / size(기본 20, 최대 50)
                             · 응답: PageResponse<SosHistoryItem>
                               { sosEventId, wardId, wardName, triggeredAt, location,
                                 ackStatus, ackNote, acknowledgedByName, acknowledgedAt }
    → PATCH /api/guardian/sos/{sosEventId}/ack   → 처리 결과 기록. 바디 { ackStatus, ackNote(선택 200자) }
                             · ackStatus: SAFE_CONFIRMED(안전 확인) / EMERGENCY_DISPATCHED(응급 출동).
                               미처리는 NULL. 이미 처리된 건도 덮어씁니다(재ACK 허용).
                             · 커밋 후 WebSocket sos-acknowledged 발송 — ACTIVE 보호자 전원 + 피보호자
                               본인. 푸시·문자는 보내지 않습니다(상황 종료 후 상태 갱신이라 소음).
                             · 인가: 요청 시점 ACTIVE 연결인 피보호자의 이력만 조회·처리 가능.
                               연결이 해제되면 과거 이력도 비공개. 연결 없는 대상은 403(+[IDOR-ATTEMPT]
                               WARN), 없는 이력은 404. 인가 목록은 ConnectionService.getActiveWardIds()

                             ⚠️ ACK는 사후 기록일 뿐 알림 발송에 개입하지 않습니다 — 처리된 SOS라도
                               WARD_SOS 필수 알림은 그대로 발송됩니다.

    → body: { "token": "...", "platform": "android|ios|web" }
    → 200: { "message": "FCM 토큰이 등록되었습니다.", "success": true }
    → 동일 토큰 재등록 시 무시(중복 저장 안 함), 200 그대로 반환

  토큰 삭제 (로그아웃 시):
    → DELETE /api/notifications/fcm-token?token=...
    → headers: Authorization: Bearer {accessToken}
    → 200: { "message": "FCM 토큰이 삭제되었습니다.", "success": true }
    → 존재하지 않는 토큰이어도 200 (idempotent)

  [개발 단계 백엔드 테스트 도구]
  프론트 없이 백엔드 단으로 푸시 파이프라인을 검증하고 싶을 때:
    tools/fcm-test/index.html (정적 페이지)
    firebaseConfig / VAPID 키 채운 뒤 npx http-server 로 localhost 서빙 →
    브라우저에서 토큰 발급 → Swagger 로 등록 → 트리거 API 호출 → 푸시 도착 확인.


  [ 3-7-A. 알림 채널 추상화 및 채널별 수신 설정 ]  (2026-05-31 추가 / 알림톡 2026-07-27 가동)
  ─────────────────────────────
  알림을 "이벤트 → 채널 라우터 → 알림 종류의 정책에 따라 채널 결정" 구조로 일반화했습니다.
  전체 계획은 3단계: (1단계) 인프라 + FCM/SMS 추상화 ✅, (2단계) 카카오 알림톡 채널 ✅(2026-07-27
  템플릿 승인·가동), (3단계) 이메일 채널 — 미구현(enum 값만).

  [채널 추상화]
  - NotificationChannelType(enum): FCM / SMS / KAKAO_ALIMTALK / EMAIL
    (EMAIL만 enum 값 정의 상태이고 발송 구현은 없음 → 켜도 조용히 건너뜀)
  - NotificationChannel(전략 인터페이스): 구현체를 빈으로 등록하면 디스패처가 자동 수집.
    구현체 = FcmNotificationChannel / SmsNotificationChannel / KakaoAlimtalkNotificationChannel.
    시그니처는 send(알림종류, 수신자, 내용) — 알림톡이 종류별 승인 템플릿을 고르는 근거로 쓴다.
  - NotificationDispatcher: 알림 종류의 정책에 따라 채널을 정하고, 채널별 발송 실패를 격리
    (한 채널 실패가 다른 채널을 막지 않음), 미구현·미설정 채널은 조용히 건너뜀.
  - WebSocket 실시간 발송은 추상화에 포함하지 않고 항상 발송(온라인 사용자 실시간 동기화 보장).

  [알림 종류별 채널 정책 (NotificationType.Policy)]
  - SETTINGS_ONLY               사용자 설정의 활성 채널로만 발송
                                → 연결 요청/수락/거절/해제, 문의 답변
  - FORCED_PUSH_WITH_SMS_FALLBACK  설정 무시 FCM 강제 + 실제 미전달 시 SMS 폴백
                                → WARD_SOS (생명 관련이라 설정으로 끌 수 없음)
  - FORCED_PUSH_PLUS_SETTINGS   FCM은 항상 + 나머지 채널은 설정대로, SMS 폴백 없음
                                → ANOMALY_DETECTED(이상감지). 문자는 사용자가 선택하는 채널이라
                                  폴백이 그 선택을 뒤집기 때문에 의도적으로 폴백하지 않는다.

  [필수/선택 분류]
  - 필수(설정 무시): SMS 인증번호(가입·비밀번호 재설정) — 디스패처를 경유하지 않는 동기 발송이라
    설정으로 끌 수 없음이 구조적으로 보장됨. 그 외 WARD_SOS·ANOMALY_DETECTED의 FCM(위 정책 참고).
  - 선택(설정 따름): 연결 요청/수락/거절/해제·문의 답변 알림, 그리고 SOS·이상감지의 SMS·알림톡.

  [기본값 정책]
  설정 행이 없는 채널은 기본값 적용 — FCM은 기본 ON(기존 동작 보존), SMS/KAKAO/EMAIL은 기본 OFF.
  → 기존/신규 사용자 백필 마이그레이션 불필요. (저장: user_notification_setting 테이블, V25)

  [API 명세]  (Swagger 태그: "알림 설정")
  설정 조회:
    → GET /api/user/me/notification-settings
    → headers: Authorization: Bearer {accessToken}
    → 200 data: { "settings": [ { "channelType": "FCM", "enabled": true }, ... 전체 채널 ] }
    → 설정한 적 없는 채널은 기본값으로 표시(FCM=true, 그 외 false)

  설정 변경:
    → PUT /api/user/me/notification-settings
    → headers: Authorization: Bearer {accessToken}
    → body: { "settings": [ { "channelType": "SMS", "enabled": true }, ... ] }  (전달한 채널만 갱신)
    → 200 data: 변경 후 전체 채널 설정
    → KAKAO_ALIMTALK를 ON으로 두면 이상감지 알림이 카카오톡으로도 도착(승인 템플릿 문구 고정).
      EMAIL은 설정값만 저장되며 실제 발송은 미지원(3단계).

  [카카오 알림톡 (KAKAO_ALIMTALK)]
  Solapi 발신 프로필을 경유해 카카오톡 채팅으로 도착합니다. 수신자를 전화번호로 찾으므로
  카카오 로그인·친구추가가 필요 없습니다.
  - ⚠️ 사전 심사에서 승인된 템플릿 문구만 발송 가능 — 자유 문구 불가, #{변수}만 치환합니다.
    종류별 승인 템플릿이 없으면 그 종류의 알림톡은 조용히 스킵됩니다.
  - 이상감지 템플릿: 2026-07-27 승인(보호자용). 변수 = wardName·location·detectedTypeLabel·detectedAt
  - 🚫 피보호자 본인에게는 알림톡을 보내지 않습니다 — 승인 문구가 보호자용("회원님께서 보호자로
    등록하시고 직접 신청하신…")이라 본인에게 보내면 사실과 어긋나 카카오 채널 제재 사유가 됩니다.
    본인 수신분은 ANOMALY_DETECTED_SELF 종류로 발송되고 이 종류엔 템플릿 매핑이 없어 알림톡만
    빠집니다(FCM·WebSocket·SMS는 그대로).
  - 🚫 Solapi "알림톡 실패 시 SMS 대체발송"은 콘솔·코드 모두 OFF(disableSms=true) — 문자를
    선택하지 않은 사용자에게 과금·발송이 나가는 것을 막습니다.
  - 환경변수: ALIMTALK_ENABLED / ALIMTALK_PF_ID / ALIMTALK_TEMPLATE_ANOMALY (.env.dev 주입)

  [프론트엔드 영향]
  추가(additive) 변경이라 기존 동작·계약 불변 — FE 수정 없이 현재와 동일하게 동작합니다.
  알림 설정 화면을 만들 경우에만 위 2개 API를 연동하면 됩니다.

  소유자 = 피보호자(ward_id). 보호자는 ACTIVE 연결을 통해 전이 접근합니다(피보호자당 여러 대 = 방별).

    → GET    /api/ward/camera        → 내 카메라 목록
    → PATCH  /api/ward/camera/{id}   → 라벨(설치 위치) 수정
    → DELETE /api/ward/camera/{id}   → 카메라 삭제

  보호자(GUARDIAN 전용):
    → GET /api/guardian/camera       → 연결된 피보호자들의 카메라 목록(ACTIVE 연결 기준 allowlist)

  ※ 타인 카메라 접근 시 403 CAMERA_NOT_AUTHORIZED("본인이 등록한 카메라만 사용할 수 있습니다.")

    없는 카메라는 404. (2026-07-14 정책: 404 위장 → 403 명시 안내)
  ※ 카메라 등록 시 CameraRegisteredEvent가 발행돼 AI 세션 목록을 즉시 재요청합니다
    ("스트리밍 먼저, 등록 나중" 순서에서도 구독이 살아나도록).


  [ 3-11. AI 이상감지 (수신 → 판정 → 이력 → 알림) ]  (anomaly, 2026-07-13/07-14)
  ─────────────────────────────
  AI 서버에는 웹훅이 없어서, 백엔드가 AI의 WebSocket에 **클라이언트로 접속**해 분석 결과를
  구독합니다(AI 서버 코드 변경 없음). 프론트가 호출하는 API가 아니라 서버 내부 파이프라인입니다.

  흐름:
    AI WS(latest_analysis) 수신 → 판정 → 이력 쿨다운 → anomaly_event 적재
    → AnomalyDetectedEvent → (커밋 후) 리스너가 ACTIVE 보호자 전원 + 피보호자 본인에게 발송

  - 구독 대상: 등록된 camera.session_id만 subscribe(미등록 세션은 애초에 구독하지 않음)
  - 판정: ANOMALY_TRIGGER_MODE=DANGER(기본) — AI가 채운 danger 플래그만 신뢰(위험 판정 책임=AI).
    CONFIDENCE는 폴백 모드(confidence >= 0.6). ※ 배포된 AI가 danger를 항상 false로 내리는 동안은
    이력 0건이 정상이며 [ANOMALY-DANGER-MISMATCH] WARN으로 드러납니다.
  - 발송 채널: WebSocket(anomaly-detected, 항상) + FCM(고정) + SMS·알림톡(사용자 설정대로).
    알림톡은 보호자만 받습니다(3-7-A의 알림톡 항목 참고).
  - 문구: 보호자 "OOO님 댁 거실에서 화재가 감지되었습니다." / 본인 "거실에서 화재가 감지되었습니다.
    안전한 곳으로 대피해 주세요."(현장 당사자에게는 대피 행동을 함께 지시)
  - 알림 data: type·wardId·wardName·location·sessionId·detectedType·detectedTypeLabel·
    detectedAt(KST yyyy-MM-dd HH:mm)·anomalyEventId
  - 빈도(2026-07-28 조정): 이력 1분 / 보호자 알림 5분 / 본인 알림 3분.
    이력은 촘촘히 남겨 화재 지속 구간의 타임라인을 확보하고, 사람에게 가는 알림은 성기게 보냅니다
    (보호자는 알림톡·SMS가 같은 간격으로 나가 과금·카카오 신고 리스크가 함께 걸립니다).
  - 발송 실패·WS 연결 실패·AI_API_KEY 미설정은 앱 기동을 막지 않습니다(구독만 비활성).


  [ 3-12. 피보호자 SOS 동작 설정 ]  (sos_setting, 2026-07-23 추가)
  ─────────────────────────────
  환경설정 > "SOS 동작 설정"을 계정 단위로 보관합니다(종전에는 프론트 localStorage 전용이라

  4. WebSocket(실시간 알림) 사용 가이드
--------------------------------------------------------------------------------

  연결 엔드포인트:
    wss://api.devdmu.gosky.kr:6511/ws  (STOMP, 네이티브 WebSocket)
    인증: 쿼리 파라미터로 ?token={accessToken} 전달 (JWT 검증 필수)

  프론트는 @stomp/stompjs의 네이티브 WebSocket으로 연결합니다 (SockJS 불필요).
  예)
    import { Client } from '@stomp/stompjs';
    const stompClient = new Client({
      brokerURL: 'wss://api.devdmu.gosky.kr:6511/ws?token=' + accessToken,
      onConnect: () => {
        stompClient.subscribe('/topic/' + myUserId + '/connection-request', msg => {...});
      },
    });
    stompClient.activate();

  ▶ 구독 가능 토픽 (본인의 userId만 허용 — 타인 토픽 구독 시 거부됨)
    /topic/{userId}/connection-request     피보호자가 받는 보호자의 연결 요청
    /topic/{userId}/connection-accepted    보호자가 받는 피보호자의 수락 알림
    /topic/{userId}/connection-refused     보호자가 받는 피보호자의 거절 알림 (2026-05-28 추가)
    /topic/{userId}/connection-cancelled   연결 해제 알림
    /topic/{userId}/sos-triggered          보호자가 받는 피보호자의 긴급 SOS 알림 (2026-06-09 추가)
    /topic/{userId}/sos-acknowledged       SOS 처리 결과(ACK) 기록 알림 (2026-07-31 추가)
                                           — 해당 피보호자의 ACTIVE 보호자 전원 + 피보호자 본인 수신
                                           payload = sosEventId·wardId·ackStatus·acknowledgedBy·
                                           acknowledgedByName (값은 모두 문자열)
                                           ※ 푸시·문자는 없습니다(상황 종료 후 상태 갱신이라 소음).
    /topic/{userId}/anomaly-detected       이상감지 알림 — 보호자·피보호자 본인 모두 (2026-07-14 추가)
                                           payload = wardId·wardName·location·detectedType·
                                           detectedTypeLabel·detectedAt·anomalyEventId 등
                                           ※ 피보호자 화면을 24시간 켜두는 사용 형태에서는 이 토픽이
                                             가장 확실한 경보 경로입니다(브라우저 알림 권한·무음 설정과 무관).

  ※ 보안: StompSubscriptionAuthorizationInterceptor가 구독 시점에
    {userId}가 인증 세션의 userId와 일치하는지 검증해, 타인의 실시간 알림
    도청을 차단합니다.

  ※ 모든 사용자 ID(users.id, user_id 참조)는 6자리 문자열입니다.
  ※ 테이블 이름은 단수형입니다 (2026-07-14, V31에서 통일 — connection·camera·anomaly_event…).
     users만 예외로 복수형을 유지합니다 — user는 PostgreSQL 예약어라 모든 참조를 "user"로
     인용해야 하고, 인용을 빠뜨린 쿼리는 테이블이 아니라 세션 사용자를 뜻해 조용히 오동작합니다.


  [ users — 회원 ]
  ─────────────────────────────
  id             : 회원 고유 ID (6자리 문자열)
  email          : 이메일 주소 (중복 불가, 로그인 사용)
  password       : 암호화된 비밀번호 (카카오 가입자는 NULL)
  name           : 이름
  phone          : 전화번호 (중복 불가, 선택)
  role           : 역할 — WARD(피보호자) / GUARDIAN(보호자) / ADMIN(관리자)
  status         : 계정 상태 — ACTIVE(정상) / INACTIVE(비활성)
                   ※ 탈퇴는 hard delete로 행 자체가 삭제됨 — INACTIVE는 탈퇴 처리 중
                     과도 상태이거나 관리자 정지 등 비활성 계정을 의미 (3-5절 참고)
  provider       : 가입 방식 — LOCAL(이메일) / KAKAO(카카오)
  provider_id    : 카카오 고유 ID (일반 가입자는 NULL)
  profile_image  : 프로필 이미지 파일명 (NULL 시 기본 이미지)
  gender         : 성별 — FEMALE / MALE (V18 추가, 기존 사용자는 NULL)
  birth_date     : 생년월일 (DATE, V18 추가, 기존 사용자는 NULL)
  postcode       : 우편번호 5자리 (V18 추가, 기존 사용자는 NULL)
  last_login_at  : 마지막 로그인 일시
  address        : 주소 (DB 기본값 빈 문자열, 단 신규 가입·프로필 수정 시 필수)
  address_detail : 상세 주소 (DB 기본값 빈 문자열, 단 신규 가입·프로필 수정 시 필수)
  created_at     : 가입 일시
  updated_at     : 마지막 수정 일시 (트리거로 자동 갱신)
  ※ name 은 V18에서 VARCHAR(50)→VARCHAR(20) 축소. 신규 가입·프로필 수정 시 성별/생년월일/우편번호 필수입력.


  [ refresh_token — 로그인 재발급 토큰 ]
  ─────────────────────────────
  id         : 고유 번호
  user_id    : 어떤 회원의 토큰인지 (users.id FK, CASCADE 삭제)

  ※ 만료된 토큰은 매일 새벽 3시(TokenCleanupScheduler)에 자동 삭제됩니다.
  ※ 비밀번호 변경 시 해당 회원의 모든 refresh token 삭제 + 발급된
    accessToken도 Redis password:invalidate 로 즉시 무효화 (Critical-1).
  ※ refresh token 재사용(도난) 감지 시 해당 회원 토큰 전부 강제 폐기 (H-3).


  [ access_log — 접근 로그 ]

--------------------------------------------------------------------------------
  6. Redis 키 (임시 데이터)
--------------------------------------------------------------------------------

  모든 Redis 키는 global/util/RedisKeys.java 상수로 관리됩니다.

  ▶ SMS 인증
    sms:verify:{phone}           회원가입 SMS 인증코드 (5분)
    sms:verified:{phone}         회원가입 인증 완료 상태 (10분)
                                 값 = verificationNonce(UUID), 가입 요청과 대조 (H-5)
    sms:attempt:{phone}          오류 횟수 (5분)
    sms:sendcount:{phone}        per-phone 발송 건수 — 1시간 10회 상한 (A-M3)
                                 ※ 재발송 쿨다운(sms:cooldown) 키는 폐지됨

  ▶ 비밀번호 재설정 (6자리 코드 — UUID 토큰/쿨다운 폐지)
    password:email:verify:{email}  이메일 재설정 인증코드 (5분)
    password:email:attempt:{email} 이메일 오류 횟수 (5분)
    password:email:sendcount:{email} per-email 발송 건수 — 1시간 10회 상한 (2026-05-23,
                                   SMS sms:sendcount A-M3와 대칭. 가입 확인된 이메일만 카운트)
    password:sms:verify:{phone}    SMS 재설정 인증코드 (5분)
    password:sms:attempt:{phone}   SMS 오류 횟수 (5분)
    password:invalidate:{userId}   비밀번호 변경 시각 — 이전 발급 accessToken
                                   무효화 기준 (TTL = accessToken 만료시간, Critical-1)

  ▶ 카카오 OAuth
    kakao:pending:{kakaoId}      신규 가입 임시 이메일 (10분)
    ※ OAuth state 는 프론트 검증 모델 → Redis 미사용 (M-1)

  ▶ 로그인 보안
    login:fail:{userId}          실패 횟수 (30분, user.id 기준 — H-2)
    login:lock:{userId}          잠금 상태 (30분, user.id 기준 — H-2)
    logout:{SHA-256(accessToken)} 로그아웃 토큰 블랙리스트 (남은 만료시간)
                                 키는 토큰 원문이 아닌 해시 (M-6)

  ▶ 요청 속도 제한
    rate:{endpoint}:{identifier} IP 또는 userId 기반 1분 고정 윈도우 (최대 10회)
                                 INCR+EXPIRE를 Lua로 원자 처리 (RedisCounter, M-4)
                                 적용 endpoint 확대: token-refresh, kakao-login,
                                 pw-reset-confirm (M-8), signin (A-H2)
    rate:{endpoint}:1m:{ip}      비밀번호 재설정 send/resend 이중 윈도우 — 분 카운터 (2026-05-23)
    rate:{endpoint}:1h:{ip}      동 시간 카운터. pw-reset-email/pw-reset-sms = 1분 10회/1시간 30회
                                 (미가입 응답 노출에 따른 자동화 enumeration 방어, 한쪽 초과 시 429)

  ▶ 이상감지 (2026-07-13 / 알림 쿨다운 2026-07-14)
    anomaly:cooldown:{sessionId}:{detectedType}
                                 이상감지 이력 적재 쿨다운 (기본 1분, SET NX EX)
                                 AI는 매 프레임(초당 여러 번) 분석 결과를 broadcast 하므로
                                 이 키가 없으면 위험 1건이 이력 수백 행이 된다.
                                 Redis 장애 시 fail-open (중복 이력 < 이력 유실)
    anomaly:notify:{userId}:{sessionId}:{detectedType}
                                 수신자별 알림 재발송 쿨다운 — 보호자 5분 / 피보호자 본인 3분.
                                 이력 쿨다운과 별개다: 이력은 촘촘히 남기고 사람에게는 성기게 알린다.
                                 보호자 쪽은 알림톡·SMS가 같은 간격으로 나가 과금·카카오 신고
                                 리스크가 함께 걸리므로 더 길게 잡는다.
                                 Redis 장애 시 fail-open (화재 알림을 인프라 장애로 삼키지 않는다)

  ▶ 기타
    character:expression:{wardId} 최근 표정 캐시 (조회 API용)
    ws:connected:{userId}        WebSocket 접속 상태 (12시간)


--------------------------------------------------------------------------------
  7. 보안 정책 요약
--------------------------------------------------------------------------------

  [ 인증/인가 ]
  - JWT: accessToken 30분, refreshToken 7일 (Rotation 적용)
  - JWT typ(access/refresh) 클레임으로 토큰 용도 구분 — refreshToken을 Bearer로
    제시해 보호 자원에 접근하는 혼용을 필터가 차단 (A-H1)
  - 로그아웃 시 accessToken을 Redis 블랙리스트 등록 (키는 SHA-256 해시, M-6)
  - 비밀번호 변경/재설정 시 refreshToken 전부 삭제 + 발급된 accessToken도
    즉시 무효화 (password:invalidate + JWT 필터 iat 검증, Critical-1)
  - refresh token 재사용(도난) 감지 시 해당 회원 토큰 전부 강제 폐기 (H-3)
  - BCrypt strength 12 (M-11)

  - @PreAuthorize로 Role 기반 엔드포인트 제한
    예: /api/guardian/** → GUARDIAN, /api/ward/** → WARD, /api/admin/** → ADMIN
  - /api/auth/logout 은 permitAll에서 분리해 인증 필수, 미인증 401 JSON (L-3)

  [ 응답 보안 헤더 (A-L2) ]
  - HSTS / X-Frame-Options: DENY / X-Content-Type-Options: nosniff / Referrer-Policy: same-origin
  - Content-Security-Policy: default-src 'self' (+ Swagger UI 호환 위해 script/style
    'unsafe-inline') + frame-ancestors 'none' / object-src 'none' / base-uri 'self'

  [ 로그인 보호 ]
  - 로그인 실패 응답 통합: 미가입 이메일 / 비밀번호 불일치 모두
    INVALID_CREDENTIALS(401) — 계정 enumeration 차단 (H-1)
  - INACTIVE 안내는 비밀번호 검증 통과한 본인에게만 노출 (H-1)
  - user.id 기준 5회 실패 → 30분 잠금 (LOGIN_LOCKED 429).
    미가입 이메일은 잠금 카운터 영향 없음 — 정상 사용자 DoS 차단 (H-2)
    잠금 횟수/시간은 application.yaml auth.login.* 로 외부화 (M-12)
  - INACTIVE 계정은 로그인 차단 + Refresh Token 즉시 삭제
    (login·kakaoLogin·refresh 세 경로 일관, H-4)

  [ 관리자 보호 ]
  - 공지사항 쓰기 작업은 admin_audit_log 자동 기록 (AdminAuditLogService)

  [ 전화번호 변경 시 SMS 인증 필수 ]

  - 미인증/nonce 불일치 시 SMS_NOT_VERIFIED 400 반환

--------------------------------------------------------------------------------
  8. 빌드 도구 — Gradle
--------------------------------------------------------------------------------

  ★ Gradle이란?
  프로젝트를 "빌드"하는 도구. 소스 코드를 실행 가능한 JAR 파일로 만들어줍니다.
  마치 요리 레시피(소스)를 실제 음식(실행 파일)으로 만드는 과정입니다.


  [ build.gradle 주요 내용 ]
  ─────────────────────────────

  ▶ plugins
    id 'java'                             → Java 프로젝트
    id 'org.springframework.boot'         → Spring Boot 패키징
    id 'io.spring.dependency-management'  → 버전 관리 자동화

  ▶ java toolchain
    Java 21 사용

  ▶ repositories
    mavenCentral() → 공개 라이브러리 저장소

  ▶ dependencies (주요 라이브러리)

    spring-boot-starter-webmvc            : HTTP API 서버
    spring-boot-starter-data-jpa          : DB 연동 (SQL 자동 생성)
    spring-boot-starter-data-redis        : Redis 연동
    spring-boot-starter-security          : 인증/인가
    spring-boot-starter-oauth2-client     : 카카오 OAuth
    spring-boot-starter-validation        : 입력값 유효성 검사
    spring-boot-starter-mail              : 이메일 발송
    spring-boot-starter-websocket         : WebSocket
    spring-boot-starter-actuator          : /actuator/health 헬스체크 + 관측성
    springdoc-openapi-starter-webmvc-ui   : Swagger UI
    jjwt-api / jjwt-impl / jjwt-jackson   : JWT 토큰
    lombok                                : @Getter, @Setter 등 자동 생성
    postgresql                            : PostgreSQL 드라이버
    flyway-core / flyway-database-postgresql : DB 스키마 버전 관리
    firebase-admin                        : FCM 푸시
    solapi SDK                            : SMS 문자 발송
    aspectjweaver                         : AOP (공통 로그)

  ▶ plugins 추가
    org.owasp.dependencycheck             : 의존성 취약점(CVE) 스캔
                                            CVSS 7.0(High) 이상 발견 시 빌드 실패

  ▶ 주요 Gradle 명령어
    ./gradlew build -x test --no-daemon       → 테스트 제외 빌드 (푸시 전 검증)
    ./gradlew bootJar --no-daemon             → JAR 파일 생성
    ./gradlew test                            → 테스트 실행
    ./gradlew dependencyCheckAnalyze --info   → 의존성 취약점 스캔
                                                결과: build/reports/dependency-check-report.html
    ./gradlew dependencies                    → 의존성 트리

  ※ CI(테스트 자동 실행)는 없습니다 — 로컬에서 ./gradlew build 검증 후 푸시.
  ※ CD는 GitHub Actions(.github/workflows/cd.yml)에 구성되어 있어,
    dev 브랜치 push 또는 수동 workflow_dispatch 시 self-hosted 러너(label: dev)가
    git pull → docker compose up -d --build api → 이미지 정리를 자동 수행합니다.
    배포 직전에 .env.dev 존재 여부를 확인하고, 없으면 친화적 에러로 즉시 중단합니다.

--------------------------------------------------------------------------------
  9-1. 관측성 (Observability) — Spring Boot Actuator
--------------------------------------------------------------------------------

  Actuator는 서버 상태를 외부에 노출하는 표준 엔드포인트 세트입니다.
  보안상 노출은 최소화했습니다.

  ▶ 공개 엔드포인트 (인증 불필요)
    GET /actuator/health   → 200 { "status": "UP" } (DB/Redis 내부 상태는 숨김)
    GET /actuator/info     → 빌드 메타 정보

  ▶ 상태 확인 방법
    로컬    : curl http://localhost:6511/actuator/health
    개발    : curl https://api.devdmu.gosky.kr/actuator/health
    Docker  : docker ps  (STATUS 열에 healthy/unhealthy 표시)

  ▶ 정책
    - show-details: never (DB·Redis 상태 세부 노출 차단)
    - exposure.include = health, info (그 외 actuator 엔드포인트 전부 비공개)
    - health.probes.enabled = true (liveness/readiness 분리)

  10. 폴더 구조
--------------------------------------------------------------------------------

  백엔드 코드는 기능(도메인)별로 폴더가 나뉩니다.

  kr.silverbridge.main
  ├── domain
  │   ├── auth           로그인, 회원가입, 토큰, SMS 인증, 카카오 OAuth, 비밀번호 재설정

  │   │   ├── service    AdminAnnouncement / AdminAnnouncementDraft / AdminAuditLog(쓰기)
  │   │   └── dto        AdminAnnouncementResponse / AnnouncementCreateRequest 등
  │   ├── connection     보호자-피보호자 연결
  │   │   ├── event      연결 상태 변경 이벤트 (Requested/Accepted/Refused/Disconnected)
  │   │   └── listener   이벤트 수신 후 WebSocket + FCM 알림 (AFTER_COMMIT)
  │   ├── announcement   공지사항 엔티티
  │   ├── camera         이상감지 카메라 소유권 (피보호자 등록 / 보호자 조회)
  │   ├── anomaly        AI 이상감지 — WS 구독·판정·이력·알림
  │   │   ├── client     AiLiveStreamSubscriber (AI WS를 클라이언트로 구독)
  │   │   ├── service    AnomalyJudge(판정) / AnomalyEventCooldown / AnomalyNotificationCooldown
  │   │   └── listener   AnomalyNotificationListener (AFTER_COMMIT + @Async 발송)
  │   ├── sos            피보호자 긴급 SOS + SOS 동작 설정(sos_setting)
  │   ├── inquiry        문의하기 / 고객센터 (보호자 작성 + 관리자 답변)
  │   └── notification   알림 채널 추상화 — 채널(FCM·SMS·카카오 알림톡)·디스패처·수신 설정
  │       ├── channel    NotificationChannel 전략 + 구현체 3종
  │       ├── dispatch   NotificationDispatcher / NotificationType(정책)
  │       └── config     AlimtalkProperties (알림 종류 → 승인 템플릿 매핑)
  └── global
      ├── config         Redis/메일/Web/보안 설정, SecurityConfigValidator
      ├── security       Spring Security, RateLimitService
      ├── jwt            JWT 발급/검증, 인증 필터
      ├── client         파일 서버 HTTP 통신
      ├── enums          Role, Status, Provider, ConnectionStatus 등
      ├── entity         공통 BaseTimeEntity
      ├── response       ApiResponse 공통 응답 포맷
      ├── exception      CustomException, GlobalExceptionHandler, ErrorCode

                         WebSocketEventPublisher, presence 리스너

  각 도메인 하위 폴더 공통:
    controller  → API 요청을 받아서 처리 흐름을 지시 (교통 정리)
    service     → 실제 비즈니스 로직 (핵심 두뇌)
    repository  → DB에서 데이터를 꺼내오거나 저장
    entity      → DB 테이블 구조를 코드로 표현
    dto         → API 요청/응답 데이터 형식

  11. 개발 환경 실행 방법
--------------------------------------------------------------------------------

  1) .env.dev 파일 준비 (프로젝트 루트에)
     ※ 누락된 키는 시작 시 RequiredPropertiesValidator/SecurityConfigValidator가
        한 번에 모아 에러로 알려주므로 안심하고 채우면 됩니다.

     ▶ PostgreSQL (DB 컨테이너 + Spring 양쪽에서 사용)
       POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD
       DB_HOST, DB_NAME, DB_USERNAME, DB_PASSWORD
       ※ DB_USERNAME / DB_PASSWORD 는 약한 기본값(dev) 제거로 필수 — 미설정 시 시작 실패 (A-L3)

     ▶ Redis
       REDIS_HOST

     ▶ JWT
       JWT_SECRET           (32자 이상 랜덤, 약한 기본값은 거부됨)
       ※ AI_SERVER_API_KEY 는 AI 도메인 제거로 더 이상 필요/검증되지 않음 (A-L5)

     ▶ 메일 (Spring Mail)
       MAIL_USERNAME, MAIL_PASSWORD
       (선택) MAIL_HOST, MAIL_PORT — 미설정 시 smtp.gmail.com:587

     ▶ 카카오 OAuth
       KAKAO_REST_API_KEY, KAKAO_CLIENT_SECRET, KAKAO_REDIRECT_URI
       ※ KAKAO_CLIENT_SECRET: 카카오 콘솔 [보안 > Client Secret] 발급 값, "사용 함" 활성화 필요 (2026-05-25 추가)

     ▶ Solapi SMS
       SOLAPI_API_KEY, SOLAPI_API_SECRET, SOLAPI_SENDER_PHONE

     ▶ Firebase (FCM)
       FIREBASE_SERVICE_ACCOUNT_BASE64
         서비스 계정 JSON을 base64로 인코딩한 문자열을 단일 라인으로 넣습니다.
         (원본 JSON을 그대로 .env에 넣으면 docker compose env_file 파서가 \n을
          실제 newline으로 변환해 깨지므로 base64로 우회 — application.yaml에서 디코딩)
         예) base64 -w0 service-account.json   → 출력된 문자열을 그대로 대입
         ※ 더 이상 src/main/resources/firebase-service-account.json 또는 docker volume mount 방식을 사용하지 않습니다.

     ▶ (선택) APP_CORS_ORIGINS — 미설정 시 기본값 사용

  2) Docker로 전체 실행
     docker compose -f docker-compose.dev.yml up -d

  3) 빌드 검증 (푸시 전 필수)
     ./gradlew build -x test --no-daemon

  4) API 문서 확인
     로컬   : http://localhost:6511/swagger-ui/index.html
     개발   : https://api.devdmu.gosky.kr/swagger-ui/index.html

  12. Git 브랜치 전략
--------------------------------------------------------------------------------

  prod    : 배포 기준 브랜치
  dev     : 개발 기준 브랜치 (feature 브랜치의 merge 대상)
  feature : 기능 개발 브랜치 (dev에서 분기, merge 후 자동 삭제)

  브랜치 네이밍: type/short-description
    feature, fix, hotfix, refactor, design, docs, test, chore, infra, release

  커밋 메시지 포맷:
    type: 무슨 작업을 했는지 한국어로
    - 상세 내용 (선택)

  작업 순서:
    1) git pull origin dev
    2) git checkout -b type/short-description
    3) 작업 및 커밋
    4) push 전 ./gradlew build -x test --no-daemon 검증
    5) git push origin type/short-description
    6) PR 생성 → dev로 머지 → 브랜치 자동 삭제 → 서버 자동 배포

  ⚠️ dev/prod에 코드를 직접 커밋·푸시하지 않습니다 — feature 브랜치 → PR → dev 흐름만 허용.
  📄 예외: 문서(.md·docs/**)만 바뀌는 변경은 PR을 생략하고 dev에 직접 커밋·푸시합니다
     (2026-06-20 결정). CD가 paths-ignore로 배포를 어차피 건너뛰므로 PR 게이트가 불필요합니다.
     코드가 1줄이라도 섞이면 이 예외는 적용되지 않습니다.

  배포 환경이 둘입니다:
    - vkcs-linux : dev push 시 CD(GitHub Actions self-hosted)로 자동 배포
    - skyserver  : 공개 도메인(api.devdmu.gosky.kr)이 붙은 환경. 수동 배포
                   (git reset --hard origin/dev → docker compose build/up → image prune)
    ※ dev에 머지해도 skyserver는 바뀌지 않습니다. 각 서버의 .env.dev도 서로 별개입니다.

  13. 연관 서비스 — 이미 구축된 SilverBridge 도메인 (다른 저장소)
--------------------------------------------------------------------------------

  SilverBridge는 이 백엔드(SilverBridgeBe) 하나로 끝나지 않고, 같은 GitHub 조직
  (Dongyang-Mirae-University-software)의 여러 저장소가 역할을 나눠 맡는 구조입니다.
  아래 서비스들은 이미 구현되어 배포 서버(skyserver, 내부 IP 58.75.21.151)에
  Docker 컨테이너로 떠 있습니다. 이 백엔드나 프론트에서 "새로 만드는" 것이 아니라
  "API로 연결"하는 대상입니다.

  ※ 아래 포트는 서버 내부(localhost) 기준입니다. 공개 도메인이 붙은 것도 있고,
    없는 것은 SSH 터널로만 접근합니다.

  ▶ (A) SilverBridgeReservation — 병원 예약 / 병원 예약 현황  [이미 구현·가동 중]
    - 역할   : 병원 예약, 예약 현황(운영상태·혼잡도·대기), 예약 가능 시간대 제공
    - 스택   : NestJS + Prisma + JWT  (자체 관리자 웹 admin-ui, MCP 브릿지 포함)
    - 포트   : 6015  (컨테이너 silverbridgereservation-reservation-api-1)
    - 문서   : Swagger  http://localhost:6015/docs
    - 주요 API (prefix /api/v1)
        예약     : POST /reservations,  GET /reservations/my,
                   GET /reservations/{id},  PATCH /reservations/{id}/cancel,
                   DELETE /reservations/{id}
        예약현황 : GET /hospitals,  GET /hospitals/{id},
                   GET /hospitals/{id}/status          (운영상태·혼잡도·대기인원),
                   GET /hospitals/{id}/available-slots  (예약 가능 시간대),
                   GET /hospitals/{id}/departments
    - ⚠️ 데이터는 실제 병원 EMR이 아니라 "더미(모의)"입니다. 데모/과제용 연동 목적.
    - ✅ 결론: 병원 예약·예약 현황은 우리가 새로 구현할 필요 없이 위 API만 연결.

  ▶ (B) SilverBridgeAiServer — AI 이상감지 / 의료 챗 서버  [이미 구현·가동 중]
    - 역할   : 카메라·모델 관리, 이미지/스트림 이상감지 분석, iPad 송출(MJPEG),
               의료 챗(MedGemma) 상담, 예약 API 키 저장, 미니 게임
    - 스택   : FastAPI (Python) + PostgreSQL,  API Key 인증
    - 포트   : 6017 (AI 서버, 컨테이너 silverbridge-ai-server) / 6019 (전용 PG)
    - 주요 API (prefix /api/v1)
        카메라       : /camera (등록·목록·상세·수정·삭제·연결테스트)
        모델         : /models  (등록·목록·상세·활성화 등)
        스트림/이상감지: /stream-sessions, /live-streams/{id}/mjpeg,
                        /live-streams/{id}/latest-analysis
        의료 챗      : POST /chat,  GET /chat/logs
        예약 연동    : POST /reservation-credentials (예약 API 키 저장)
    - 참고: 배포본은 로컬 SilverBridgeAi(개발용)보다 앞선 버전.

  ▶ (C) ChatSilverBridge — 의료 AI(MedGemma) 챗 백엔드
    - 역할   : 증상/건강 질문에 대한 의료 보조 안내형 답변 (모델 medgemma-1.5-4b-it)
    - 스택   : FastAPI (Python),  API: GET /health, POST /chat

  Claude Code Skills (이 저장소에 설치된 20개)

  Skill이란?
  Claude Code(AI 코딩 도우미)가 특정 작업을 할 때 따르는 "체크리스트 + 템플릿"
  꾸러미입니다. 각 Skill은 .claude/skills/<이름>/SKILL.md 파일로 존재하며,
  자연어로 호출하면(예: "architecture-review 진행해줘") AI가 해당 가이드를
  로드한 뒤 그 절차대로 작업을 수행합니다.

  ▶ 설치 위치
    .claude/skills/<skill-name>/SKILL.md
    .claude/skills/README.md  (전체 목록 인덱스)

  ▶ 레벨별 분류
    Macro       : architecture-review        (패키지·모듈·레이어 구조)
    Meso        : design-patterns, java-code-review, solid-principles
                                              (클래스·인터페이스 설계)
    Micro       : clean-code                 (함수·네이밍·표현식)
    Framework   : spring-boot-patterns, jpa-patterns
                                              (Spring/JPA 특화)
    Cross-cut   : security-audit, test-quality, logging-patterns,
                  concurrency-review, performance-smell-detection,
                  api-contract-review        (보안·테스트·로깅·동시성·성능·API)
    Workflow    : work-prompt, git-commit, changelog-generator,
                  issue-triage, maven-dependency-audit, java-migration
                                              (작업 절차·커밋·릴리스·의존성·버전업)

  ※ 정확한 최신 목록은 .claude/skills/README.md 가 기준입니다(이 문서는 요약).

  ▶ 타입별 분류
    Audit (기존 코드 점검) : architecture-review, java-code-review,
                            security-audit, api-contract-review,
                            performance-smell-detection, concurrency-review
    Template (새 코드 작성): spring-boot-patterns, jpa-patterns,
                            design-patterns, solid-principles, clean-code,
                            logging-patterns, test-quality

  ▶ 자주 쓰는 호출 예시
    "test-quality 로 AuthService 단위 테스트 추가"
    "security-audit 으로 auth 도메인 OWASP 점검"
    "jpa-patterns 로 User 엔티티 N+1 검토"
    "spring-boot-patterns 로 Controller-Service-Repository 검토"
    "architecture-review 로 domain/global 패키지 경계 점검"
    "java-code-review 로 PR 변경 파일 리뷰"

  ▶ 협업 원칙 (CLAUDE.md §2)
    1) 개발자가 결정, AI는 제안만 — 변경은 항상 검토 후 적용
    2) 자동 git 커밋·푸시 금지 — 명시적 승인 후 진행
    3) 변경 범위 투명화 — 어떤 파일이 왜 바뀌는지 항상 설명
    4) 점진적 채택 — 읽기 전용 분석 → 제안 → 리뷰 → 적용 순서

  ▶ 자세한 사용법
    .claude/skills/README.md

  SilverBridge 백엔드 프로젝트 설명서
================================================================================

--------------------------------------------------------------------------------
  1. 이 프로젝트는 무엇인가요?
--------------------------------------------------------------------------------

SilverBridge는 노인(피보호자)과 그 가족(보호자)을 연결하는 서비스입니다.

  - 피보호자 (WARD)   : 돌봄을 받는 노인
  - 보호자 (GUARDIAN) : 피보호자를 관리하는 가족/보호자
  - 관리자 (ADMIN)    : 서비스 전체를 관리하는 운영자

이 저장소는 "백엔드" 코드입니다.
백엔드란, 앱/웹 화면 뒤에서 실제 데이터를 처리하고 저장하는 서버 프로그램입니다.
프론트엔드(화면)가 백엔드에 "요청"을 보내면, 백엔드가 처리한 결과를 "응답"으로 돌려줍니다.
이 요청/응답 방식을 API라고 부릅니다.

  [개발 서버]
  서버 주소  : api.devdmu.gosky.kr (포트 6511)
  메인 페이지: devdmu.gosky.kr
  데이터베이스: PostgreSQL 17 (포트 6513)
  캐시 서버  : Redis 7.2 (포트 6514)


--------------------------------------------------------------------------------
  2. 사용하는 기술 (비유로 이해하기)
--------------------------------------------------------------------------------

  Java 21 / Spring Boot 4 : 서버를 만드는 프로그래밍 언어와 프레임워크.
                            "프레임워크"는 건물의 철골 구조처럼 기본 틀을 제공합니다.

  PostgreSQL 17  : 관계형 데이터베이스. 회원 정보, 연결 정보 등 모든 데이터를
                   저장하는 창고. 엑셀 표처럼 행/열로 데이터를 관리합니다.

  Redis 7.2      : 매우 빠른 임시 저장소. SMS 인증번호처럼 "잠깐 저장했다가
                   쓰고 버리는" 데이터를 담습니다.
                   냉장고(PostgreSQL) vs 조리대(Redis) 의 차이로 이해하세요.

  JWT (토큰)      : 로그인 후 받는 "디지털 출입증". 이후 모든 API 요청에 토큰을
                   함께 보내 본인임을 증명합니다.
                   accessToken (30분 유효) / refreshToken (7일 유효)

  WebSocket (STOMP, 네이티브 wss) : 서버가 클라이언트에게 먼저 메시지를 보낼 수 있는
                   양방향 통신 방식. 연결 요청/수락/해제 등 실시간 알림에 사용.

  FCM            : Firebase Cloud Messaging. 앱이 꺼져 있어도 도달하는 푸시 알림.

  Flyway         : 데이터베이스 스키마 버전 관리 도구. V1, V2, ... 순서대로
                   마이그레이션을 자동 적용합니다.

  Docker         : 서버 프로그램을 "컨테이너"라는 독립된 환경에 담아 실행.
                   어느 서버에서든 동일하게 동작하도록 포장해줍니다.

  Swagger / OpenAPI : API 명세서 자동 생성 도구.
                   주소: api.devdmu.gosky.kr/swagger-ui/index.html
                   ▶ 태그(그룹) 규칙 (2026-08-07 통일): "<역할> - <도메인>"
                     역할은 공통 / 피보호자 / 보호자 / 관리자 4가지뿐이며,
                     "누가 쓰는지 → 무슨 기능인지" 두 단계로 읽히게 했습니다.
                     현재 16개 태그 / 23개 컨트롤러 / 81개 엔드포인트가 전부 분류돼 있고,
                     표시 순서도 공통 → 피보호자 → 보호자 → 관리자로 고정입니다.
                     예) 공통 - 인증 / 공통 - 내 계정 / 공통 - 알림 설정 / 공통 - 공지사항 /
                         피보호자 - 연결·SOS·복약·카메라 /
                         보호자 - 연결·SOS 이력·복약·이상감지·카메라·문의 /
                         관리자 - 공지사항·문의
                     ⚠️ 태그 설명은 SwaggerConfig.tags()에 모아 둡니다 — 새 컨트롤러를 만들면
                       여기에 등록해야 설명 없는 태그가 뒤에 붙지 않습니다.


--------------------------------------------------------------------------------
  3. 주요 기능과 API 흐름
--------------------------------------------------------------------------------

  ★ API란?
  앱이 서버에 특정 주소(URL)로 요청을 보내는 것입니다.
    - GET    : 데이터 조회 (읽기)
    - POST   : 데이터 생성 또는 특정 동작 실행
    - PUT    : 데이터 전체 수정
    - PATCH  : 데이터 일부 수정
    - DELETE : 데이터 삭제


  [ 3-0. 기능 전체 흐름 한눈에 보기 ]  (2026-09-02 추가)
  ─────────────────────────────
  기능이 많아져서 "이건 누가 시작해서 어디로 가는 거지?"를 매번 코드에서 찾게 됩니다.
  그래서 흐름만 여기에 모아 뒀습니다. 자세한 주소·응답 형식은 아래 3-1부터의 절과
  5장(테이블 설명)에 있습니다.


  ▶ 서비스 전체 지도

    [피보호자]                      [백엔드]                        [보호자]
        |                              |                               |
        |  가입 → 연결 수락            |            연결 요청           |
        |<-----------------------------+-------------------------------|
        |                              |                               |
        |  SOS 버튼 --------------->   |  --- 앱 알림(+문자) -------->  |
        |  복약 체크 --------------->  |  --- 화면 즉시 갱신 --------> |
        |                              |                               |
    [카메라]---> [AI 서버] ------->    |  --- 화재 알림 ------------->  |
                                       |  <-- "진짜였나요?" 답변 ----- |
                                       |                               |
                                       |  --- 숫자 세기 --> [관리자 화면]

    ★ 서버가 알아서 먼저 움직이는 건 딱 3가지입니다.
      ① AI가 보내온 화재·연기 신호를 받을 때
      ② 약 먹을 시간이 됐을 때
      ③ 이상감지에 아무도 답을 안 했을 때 다시 물어볼 때
      이 3가지 말고는 전부 사용자가 버튼을 눌러야 시작됩니다.


  ▶ ① 서비스 시작 - 가입하고 서로 연결하기        (자세히: 3-1 ~ 3-6)

    가입 (피보호자·보호자 각각 따로 가입합니다)
      → 이메일 중복 확인 → 문자로 본인 확인 → 비밀번호 설정 → 가입 완료
      → 6자리 아이디를 받습니다. 이 아이디로 서로를 찾고 연결합니다.

    연결 (신청은 보호자가 합니다. 피보호자는 받기만 합니다.)
      보호자가 피보호자 아이디를 입력해서 신청
        → 피보호자에게 "연결 요청이 왔어요" 알림
      피보호자가 수락  → 연결됨      → 보호자에게 "수락했어요" 알림
      피보호자가 거절  → 거절됨      → 보호자에게 "거절되었어요" 알림
      보호자가 신청 취소             → 알림 없음
      둘 중 누구든 연결 끊기         → 상대방에게 "연결이 해제되었어요" 알림

    ※ 취소할 때 알림이 없는 건 실수가 아니라 일부러 그런 것입니다.
      거절은 "싫다"는 분명한 의사표시라 상대가 알아야 하지만, 신청을 없던 일로 하는 건
      굳이 알릴 일이 아니라고 판단했습니다. 나중에 "통일성" 때문에 알림을 붙이지 마세요.

    ※ 이 "연결"이 이후 모든 기능의 열쇠입니다.
      SOS 기록, 복약 정보, 이상감지 기록을 볼 수 있는 이유는 오직 "지금 연결되어 있어서"입니다.
      연결을 끊으면 예전 기록까지 그 즉시 안 보이게 됩니다. (개인정보를 남기지 않기 위해)


  ▶ ② 긴급 SOS - 위급할 때 누르는 버튼            (자세히: 3-6 안의 "긴급 SOS")

    피보호자가 SOS 버튼을 누름
      → 먼저 기록을 남깁니다 (알림이 실패하더라도 "눌렀다"는 사실은 반드시 남깁니다)
      → 연결된 보호자 전원에게 알립니다
           앱 푸시 알림 — 보호자가 알림을 꺼놨어도 무조건 보냅니다
             └ 푸시가 안 갔으면 → 문자로 대신 보냅니다 (SOS에만 있는 안전장치입니다)
           보호자가 웹을 보고 있으면 화면에도 즉시 뜹니다
      → 보호자는 나중에 SOS 기록 목록에서 다시 확인할 수 있습니다

    ※ 어떤 설정으로도 보호자 알림을 끌 수 없습니다. 생명이 걸린 알림이라 그렇습니다.
      환경설정의 "SOS 동작 설정"(3-12)은 119 화면을 어떻게 보여줄지만 정합니다.
      ⚠️ 그리고 119로 실제 전화를 걸지 않습니다. 학생 프로젝트라 진짜 신고가 나가면 안 됩니다.
    ※ "보호자에게 직접 전화했다"는 기록이 남더라도, 나머지 보호자에게는 알림이 그대로 갑니다.
      전화받은 사람 말고 다른 가족도 상황을 알아야 하기 때문입니다.


  ▶ ③ AI 이상감지 - 화재를 감지해서 관리자 통계까지  (자세히: 3-10, 3-11, 3-11-A, 3-11-B)

    이 프로젝트에서 가장 긴 흐름입니다. 6칸으로 이어집니다.

    [1] 카메라 등록      집에 카메라를 등록하면 카메라마다 고유 번호가 생깁니다
                            |
    [2] AI와 연결        AI 서버는 우리에게 먼저 연락해 주는 기능이 없습니다.
                         그래서 우리 서버가 AI 서버에 먼저 접속해서 계속 듣고 있습니다.
                         → 우리에게 등록된 카메라 것만 골라서 듣습니다
                            |
    [3] 위험 판단·기록   "위험하다"는 판단은 AI가 합니다. 우리는 AI가 위험이라고 한 것만 믿습니다.
                         → 같은 카메라는 1분에 한 번만 기록합니다 (똑같은 기록이 쌓이지 않게)
                            |
    [4] 알림 보내기      연결된 보호자 전원 + 피보호자 본인에게
                         → 앱 푸시 알림과 화면 알림은 무조건
                         → 문자·카카오 알림톡은 본인이 켜 놓은 것만
                            (카카오 알림톡은 보호자에게만 갑니다. 승인받은 문구가 보호자용이라서요.)
                         → 사람에게는 성기게 보냅니다: 보호자 5분, 본인 3분에 한 번
                            (기록은 촘촘히, 알림은 성기게 - 놀라게 하지 않으려고)
                            |
    [5] 하나로 묶고 물어보기
                         화재가 이어지면 기록은 계속 쌓이지만, 그걸 하나의 "상황"으로 묶습니다.
                         (같은 집·같은 카메라·같은 종류이고, 마지막 감지에서 10분 안이면 같은 상황)
                         → 보호자에게 "진짜 위험이었나요, 잘못 본 건가요?"를 묻습니다
                         → 답은 보호자만 합니다. 한 사람당 한 표이고 나중에 바꿀 수 있습니다.
                         → 보호자끼리 답이 다르면? 다수결로 정하지 않고 "엇갈림"으로 남깁니다.
                            (한 명은 진짜 불로, 한 명은 요리 연기로 봤다는 사실 자체가
                             관리자가 확인해야 할 정보이기 때문입니다)
                            |
                         아무도 답을 안 하면:
                           상황이 끝나고 1시간 뒤에 한 번 더 물어봅니다
                           그 뒤로는 하루에 한 번만 (저녁 8시), 3일까지만 물어봅니다
                           밤 10시~아침 8시에는 묻지 않고 아침으로 미룹니다
                           보호자가 이 "확인해 주세요" 알림만 따로 끌 수 있습니다
                            |
    [6] 관리자 화면      오늘 몇 건이었는지, 그중 진짜는 몇 건이고 잘못 본 건 몇 건인지 보여줍니다

    ⚠️ [5]에서 보호자가 답할 화면이 안 만들어지면, [6]의 통계는 영원히 "아무도 답 안 함"만
      나옵니다. 예전에 SOS에도 "처리했어요" 기능을 만들었는데 화면이 끝내 안 붙어서
      기록이 전부 비어 있었고, 결국 2026-08-26에 그 기능을 없앴습니다. 같은 일을 반복하지 마세요.
    ⚠️ "잘못 봤다"고 답해도 이미 보낸 알림을 취소하지 않습니다.
      "아까 그건 아니었어요"를 또 보내면 알림만 두 배가 되고, 정작 다음에 진짜 불이 났을 때
      사람들이 안 믿게 됩니다.
    ⚠️ 관리자가 "엇갈림"을 정리하는 화면은 아직 없습니다(다음 작업 예정).


  ▶ ④ 복약 알림 - 등록은 보호자, 체크는 피보호자     (자세히: 3-6 안의 "복약")

    역할을 나눈 것이 이 기능의 핵심입니다.
    어르신이 약 이름·용량을 직접 입력하기 어려우니 등록은 보호자가 하고,
    "정말 드셨는지"는 본인만 체크할 수 있게 했습니다.

    보호자: 약을 등록합니다 (약 이름, 먹는 시간)
                            |
    서버(1분마다 확인): 먹을 시간이 됐는데 아직 체크가 안 됐으면
                        → 피보호자에게 "약 드실 시간이에요" 알림 (앱 푸시·문자)
                        → 시간을 놓쳐도 30분까지는 보냅니다
                        → 원하면 15분 뒤에 한 번 더 (사용자가 켜고 끌 수 있습니다)
                            |
    피보호자: 약을 먹고 체크
                        → 보호자 화면이 즉시 갱신됩니다 (푸시 알림은 안 보냅니다)
                          하루에도 여러 번 있는 일이라 푸시로 보내면 시끄럽기 때문입니다
                            |
    서버(저녁에 한 번): 보호자가 정해둔 시각(기본 밤 9시)에
                        → 그 시각까지 먹을 시간이 지난 약 중에 체크 안 된 게 있으면
                          보호자에게 하루 한 번 알려줍니다

    ※ 보호자가 대신 체크하는 기능은 만들면 안 됩니다.
      대신 체크할 수 있으면 "본인이 체크해야 보호자가 안다"가 무너져서
      복용 기록이 사실이 아니라 추측이 되어 버립니다.
    ※ 알림 문구는 "체크되지 않았습니다"입니다. "약을 안 드셨습니다"가 아닙니다.
      서버는 진짜 안 드신 건지 체크만 깜빡한 건지 구분할 방법이 없습니다.
      확실하지 않은 걸 사실처럼 알리면 보호자가 괜한 걱정을 하게 됩니다.
    ※ 보호자가 정한 시각까지만 셉니다. 밤 9시로 정했다면 밤 10시 약은 안 세는 게 맞습니다.
      아직 먹을 때가 안 된 약을 "안 드셨다"고 하면 매일 거짓 알림이 갑니다.


  ▶ ⑤ 문의하기                                    (자세히: 3-6 안의 "문의하기")

    보호자가 문의 작성 → 답변 대기 상태로 관리자 목록에 뜸
    관리자가 답변 → 답변 완료로 바뀌고, 작성자에게 앱 푸시 알림
    관리자 화면에는 "아직 답 못 한 문의 몇 건, 가장 오래 기다린 건 몇 시간"으로 표시됩니다


  ▶ ⑥ 알림이 나가는 길 (모든 알림이 여기를 지납니다)   (자세히: 3-7-A)

    알림 종류가 많지만 전부 같은 길을 지납니다. 새 알림을 만들 때도 이 길을 벗어나지 마세요.

    무슨 일이 생김 (연결 요청, SOS, 화재 감지 등)
      → 저장이 다 끝난 뒤에 알림을 보냅니다 (저장이 실패했는데 알림만 가는 일이 없도록)
      → 알림 보내는 곳은 한 군데뿐입니다. 거기서 종류에 따라 어떻게 보낼지 정합니다.

           "사용자 설정대로"        연결·문의·복약·확인요청
                                    → 사용자가 켜 놓은 방법으로만 보냅니다

           "무조건 푸시 + 문자"     SOS
                                    → 알림을 꺼놨어도 푸시를 보내고, 안 가면 문자로 대신

           "푸시는 무조건 + 나머지는 설정대로"   화재 감지
                                    → 푸시는 반드시, 문자·알림톡은 켜 놓은 사람만

      → 보내는 방법: 앱 푸시 / 문자 / 카카오 알림톡

    ※ 화면 실시간 갱신(웹소켓)은 이 길을 지나지 않고 항상 보냅니다.
      문자 인증번호도 이 길을 지나지 않습니다(설정과 무관하게 보내야 하니까요).
    ※ "무조건 보내는 푸시"는 어떤 설정으로도 줄어들지 않습니다.
      여기에 손대면 SOS·화재 알림이 안 가는 구멍이 생깁니다.
    ※ 카카오 알림톡은 카카오에서 미리 승인받은 문구만 보낼 수 있습니다.
      승인받은 문구가 없는 알림은 알림톡만 조용히 건너뜁니다(다른 방법으로는 갑니다).


  ▶ ⑦ 회원 탈퇴 - 두 걸음에 나눠서 지웁니다         (자세히: 7장 보안 정책)

    탈퇴 신청 (본인 확인: 일반 가입은 비밀번호, 카카오는 "탈퇴"라고 입력)
      → [1걸음] 계정을 "탈퇴 중"으로 바꿉니다
      → 그 사이에 정리할 일들을 합니다
           연결 끊고 상대에게 알리기 / 로그인 정보 지우기 / 등록했던 약 정리하기
      → [2걸음] 계정을 완전히 삭제합니다
           (남겨두면 같은 이메일·전화번호로 다시 가입할 수 없어서 완전히 지웁니다)

    ※ 두 걸음 사이에 서버가 재시작되면 "탈퇴 중"으로 멈춘 계정이 남습니다.
      그래서 10분마다 도는 청소 작업이 오래 멈춰 있는 계정을 찾아 마저 지웁니다.
    ⚠️ "탈퇴 중" 상태는 오직 탈퇴할 때만 써야 합니다.
      휴면 계정이나 관리자 정지 같은 다른 용도로 쓰면, 청소 작업이 그 계정을 삭제해 버립니다.


  ▶ ⑧ 관리자가 하는 일                            (자세히: 3-8, 3-11-B)

    공지사항 쓰기·수정         → 누가 언제 고쳤는지 기록이 남습니다
    문의 답변                  → 위 ⑤
    대시보드 보기 (2개 탭)     → 그냥 숫자만 보는 거라 기록을 남기지 않습니다
                                 (30초마다 새로 보는 화면이라 기록하면 진짜 중요한
                                  수정 기록이 파묻힙니다)
    이상감지 엇갈린 건 정리    → 아직 없습니다 (다음 작업 예정)


  ▶ 모든 기능에 공통으로 적용되는 약속 (자꾸 잊게 되는 것들)

    1) 볼 수 있는 이유는 오직 "지금 연결되어 있어서"입니다.
       수락을 기다리는 중인 요청은 연결이 아닙니다. 그걸 연결로 치면
       아직 수락도 안 한 피보호자의 정보가 보이게 됩니다.

    2) 남의 것을 보려고 하면 "없다"고 숨기지 않고 "당신 것이 아닙니다"라고 알려줍니다.
       어르신·40~50대 사용자가 "왜 안 보이지?"로 헤매다 이탈하는 걸 막기 위해서입니다.
       대신 내용은 절대 안 보여주고, 그런 시도는 로그에 남깁니다.

    3) 날짜와 "오늘"은 항상 한국 시간 기준입니다.
       서버 시간을 그대로 쓰면 아침마다 숫자가 되돌아가는 일이 생깁니다.

    4) 알림을 보내기 전에 "보냈다"고 먼저 적어 둡니다.
       순서를 바꾸면, 보내고 나서 적기 전에 서버가 죽었을 때 다음 차례에 또 보냅니다.
       1분마다 도는 작업이라 같은 알림이 30번 갈 수도 있습니다.

    5) 모르는 값을 0으로 채우지 않습니다.
       "0대"와 "확인할 수 없음"은 다른 이야기입니다. 관리자 화면에서 이걸 섞으면
       우리 서버 고장을 카메라가 전부 꺼진 걸로 오해하게 됩니다.

    6) 확실하지 않은 것을 사실처럼 쓰지 않습니다.
       "약을 안 드셨습니다"(X) → "체크되지 않았습니다"(O)
       "화재가 발생했습니다"(X) → "화재 감지가 있었습니다, 확인해 주세요"(O)

    7) 알림을 너무 많이 보내지 않습니다.
       하루 한 번 요약하고, 같은 알림은 일정 시간 쉬고, 종류별로 끌 수 있게 한 이유가
       전부 이것입니다. 귀찮아서 앱 알림을 통째로 꺼 버리면
       그 집의 SOS·화재 알림까지 같이 죽습니다.

    8) 알림이 실패해도 기록은 남깁니다.
       반대로, 보내기에 실패한 알림은 다시 보내지 않습니다.
       한 번 빠지는 것보다 두 번 가는 게 더 나쁘다고 판단했기 때문입니다.


  [ 3-1. 일반 회원가입 (4단계) ]
  ─────────────────────────────
  이메일/비밀번호로 가입하며 전화번호 SMS 인증이 필요합니다.

  1단계) 이메일 중복 확인
    → POST /api/auth/signup/email/check
    → 이미 가입된 이메일이면 오류 반환

  2단계) SMS 인증코드 발송
    → POST /api/auth/signup/sms/send
    → 입력한 전화번호로 6자리 숫자 문자 발송 (5분 유효)
    → 재발송 쿨다운 없음 — 즉시 재요청 가능. 단 한 번호당 발송 상한(1시간 10회, A-M3)
    → 재발송: POST /api/auth/signup/sms/resend

  3단계) SMS 인증코드 확인
    → POST /api/auth/signup/sms/verify
    → 받은 숫자 입력해 본인 확인 (인증 완료 후 10분 이내에 4단계 진행)
    → 5회 이상 오류 시 인증코드 자동 초기화 → 재발송 필요
    → 응답으로 verificationNonce(UUID) 반환 — 4단계 요청에 그대로 첨부 필수

  4단계) 회원가입 완료
    → POST /api/auth/signup
    → 이름, 이메일, 비밀번호, 전화번호, 역할(WARD/GUARDIAN), 성별(FEMALE/MALE),
      생년월일(yyyy-MM-dd · 미래 불가 · 만 14세 이상~120세 이하), 우편번호(숫자 5자리),
      주소, 상세주소, verificationNonce 입력
    → 모든 필드 필수 (우편번호·주소는 카카오 주소 API 결과값 권장)
    → verificationNonce 누락/불일치 시 SMS_NOT_VERIFIED 400
      (phone 단일 식별만으로 인증 우회 가입하던 결함 차단 — H-5)


  [ 3-2. 로그인 / 로그아웃 / 토큰 재발급 ]
  ─────────────────────────────
  로그인:
    → POST /api/auth/signin
    → 이메일 + 비밀번호 입력
    → 성공 시 accessToken(30분) + refreshToken(7일) 반환

  이후 모든 API 요청 헤더에 다음 형식으로 토큰 첨부:
    Authorization: Bearer {accessToken}

  accessToken 만료 시 재발급:
    → POST /api/auth/refresh
    → refreshToken 전달 → 새 accessToken + 새 refreshToken 반환
    → 기존 refreshToken은 즉시 무효화 (Refresh Token Rotation)
    → 폐기된 옛 refreshToken이 다시 들어왔는데 같은 사용자에게 다른
      refreshToken이 남아 있으면 도난 신호로 간주 → 해당 사용자의 모든
      refreshToken 강제 폐기 + access_log에 TOKEN_REUSE_DETECTED 기록 (H-3)
    → POST /api/auth/refresh 도 1분 10회 rate limit 적용 (M-8)

  로그아웃:
    → POST /api/auth/logout
    → accessToken을 Redis 블랙리스트에 등록해 재사용 차단
      (키는 토큰 원문이 아니라 SHA-256 해시 — Redis 메모리 절약·원문 비노출, M-6)
    → 미인증 상태 요청은 401 JSON 반환 (permitAll에서 logout만 분리, L-3)

  아이디(이메일) 찾기:
    → POST /api/auth/find-email
    → 이름 + 전화번호로 계정 조회
    → 마스킹된 이메일 반환 (예: us**@example.com)

  ※ 보안 정책:
    - 로그인 실패 응답 통합: 미가입 이메일 / 비밀번호 불일치 모두
      INVALID_CREDENTIALS(401) 동일 응답 — 계정 존재 여부 추측 차단 (H-1)
    - INACTIVE 안내는 비밀번호 검증을 통과한 본인에게만 노출 (H-1)
    - 로그인 실패 잠금은 user.id 기준으로 5회 실패 시 30분 잠금
      (LOGIN_LOCKED 429). 임의 이메일로 정상 사용자를 잠그는 DoS 차단 (H-2)
      ※ 미가입 이메일은 잠금 카운터에 영향 없음
      ※ 5회/30분 값은 application.yaml auth.login.* 로 외부화 (M-12)
    - INACTIVE 계정은 로그인 차단 + Refresh Token 즉시 삭제
      (login·kakaoLogin·refresh 세 경로 모두 일관 적용, H-4)
    - 로그인(/signin)도 IP 기준 1분 10회 rate limit 적용 — 계정 분산
      credential stuffing/password spraying 차단 (A-H2)
    - JWT에 typ(access/refresh) 클레임 부여 → refreshToken을 Authorization
      헤더(Bearer)로 제시해 보호 자원에 접근하는 토큰 혼용을 필터가 차단 (A-H1)
      ※ 배포 시점에 발급돼 있던 옛 accessToken(typ 없음)은 1회 401 후 refresh로 자동 재발급


  [ 3-3. 카카오 로그인/회원가입 ]
  ─────────────────────────────
  카카오 계정으로 소셜 로그인하는 방식입니다.

  기존 회원 로그인:
    → POST /api/auth/signin/kakao  (카카오 인가코드 전달, body: { code })
    → isNewUser=false, accessToken + refreshToken 반환

  신규 회원 가입 (4단계):
    1) POST /api/auth/signin/kakao       → isNewUser=true, kakaoId/이메일 반환
                                            (이름은 항상 null — 카카오 닉네임 미사용, 본인 실명 직접 입력)
    2) POST /api/auth/signup/sms/send    → 전화번호 SMS 발송
    3) POST /api/auth/signup/sms/verify  → SMS 인증 확인 → verificationNonce 반환
    4) POST /api/auth/signup/kakao       → 역할(WARD/GUARDIAN) + 전화번호 + 성별 + 생년월일 +
                                            우편번호 + 주소 + 상세주소 + verificationNonce 입력 후
                                            최종 가입 (모든 필드 필수, 성공 시 201 Created)

  ※ 엔드포인트 정정: 로그인은 /api/auth/signin/kakao, 가입 완료는
    /api/auth/signup/kakao (과거 메모의 /api/auth/kakao·/kakao/register는 오기).
  ※ kakaoId는 1번 응답의 값을 4번까지 계속 사용합니다.
  ※ 3번 응답의 verificationNonce를 4번 요청에 첨부해야 가입됩니다 (H-5).
  ※ isNewUser 값에 따라 응답 구조가 달라집니다.
  ※ 2026-05-25 보안 강화: 백엔드의 인가코드→토큰 교환 요청에 client_secret를 함께 전송합니다.
    값은 KAKAO_CLIENT_SECRET 환경변수로만 주입(코드/Git 비노출)하며, 카카오 콘솔
    [보안 > Client Secret]에서 코드 발급 후 "사용 함" 활성화가 필요합니다. 미설정·약한 값이면
    시작 단계에서 차단됩니다 (Required/SecurityConfigValidator).

  ※ CSRF(state) 방어는 프론트 검증 모델(모델 A)로 결정 (2026-05-18, M-1):
    프론트가 카카오 인가 요청 시 난수 state 생성·sessionStorage 보관,
    콜백에서 자체 대조 후 백엔드에는 code만 전달. 백엔드는 state를 받지도
    검증하지도 않음 (KakaoLoginRequest 변경 없음). 프론트 카카오 로그인은
    아직 미구현 — 신규 구현 시 state 검증 포함 예정.


  [ 3-4. 비밀번호 재설정 (3단계) ]
  ─────────────────────────────
  ※ 2026-05-23 갱신: 시니어/4050 타겟 UX 우선 — 미가입/카카오 계정에 always-200 대신
    명시적 응답(404/400)을 준다. 노출되는 enumeration은 IP 이중 윈도우 RateLimit +
    per-email 발송 상한 + 미가입 WARN 로깅으로 방어.
  이메일 또는 SMS 중 선택. 흐름은 6자리 인증코드 하나로 통일됩니다 (UUID 토큰 없음).

  ▶ 이메일 방식
    1단계) POST /api/auth/find-password/email/send
           → 가입 이메일로 6자리 인증코드 발송 (5분 유효, 쿨다운 없음)
           → 재발송: /email/resend
    2단계) POST /api/auth/find-password/email/verify
           → 6자리 코드 사전 확인 (코드 소비 안 함 — 토큰 미발급)
    3단계) POST /api/auth/password/reset
           → email + 같은 6자리 code + 새 비밀번호 입력 → 변경 완료

  ▶ SMS 방식
    1단계) POST /api/auth/find-password/sms/send
           → 이름+전화번호로 계정 조회 후 6자리 인증코드 SMS 발송 (5분 유효, 쿨다운 없음)
           → 재발송: /sms/resend
    2단계) POST /api/auth/find-password/sms/verify
           → 6자리 코드 사전 확인 (코드 소비 안 함)
    3단계) POST /api/auth/password/reset
           → phone + 같은 6자리 code + 새 비밀번호 입력 → 변경 완료

  ※ email / phone 은 정확히 하나만 채워 보냅니다. 코드 5회 오류 시 무효화 → 재발송 필요.
  ※ confirm(reset) 은 코드 검증을 사용자 조회보다 먼저 수행해 가입 여부·provider 가
    응답으로 새지 않게 합니다 (A-M1).
  ※ 비밀번호 변경 성공 시 모든 기기에서 자동 로그아웃됩니다.
    - refreshToken 전부 삭제 + 발급돼 있던 accessToken도 즉시 무효화
      (Redis password:invalidate:{userId} 에 변경 시각 기록 → JWT 필터가
       그 시각 이전 발급 토큰을 401 차단. Critical-1)
    - 이로써 "비밀번호를 바꿔도 옛 accessToken이 최대 30분 살아 있던" 결함 해소
  ※ 정책(2026-05-23 갱신): send/resend는 미가입 시 404("해당 이메일로 가입된 계정이 없습니다"
    /SMS는 "사용자를 찾을 수 없습니다"), 카카오 가입 계정은 400으로 명확히 안내한다.
    (기존 "가입 여부 노출 방지를 위해 계정이 없어도 200 반환"은 폐지 — 시니어 이탈 UX 개선)
    어뷰징 방어: 미가입 시 SMS/메일 발송 전 차단(비용 보호), 미가입 404는 [PW-RESET] WARN 로깅.
  ※ Rate Limit(2026-05-23 갱신): send/resend 4개는 IP 이중 윈도우 1분 10회 / 1시간 30회.
    per-email 발송 상한 password:email:sendcount 1시간 10회(SMS sms:sendcount A-M3와 대칭).
  ※ POST /api/auth/password/reset 도 1분 10회 rate limit 적용 (M-8).
  ※ 비밀번호 재설정 완료 시 access_log에 IP/UA 포함 기록 (M-3).

  [ 3-6. 보호자 ↔ 피보호자 연결 ]
  ─────────────────────────────
  보호자가 피보호자의 6자리 아이디를 입력해 신청하고, 피보호자가 수락하거나 거절합니다.
  신청은 보호자만 할 수 있습니다.

  연결 신청 (보호자):
    → POST /api/guardian/connection/request
    → body: { "targetId": "피보호자 6자리 ID" }
    → "수락 대기(PENDING)" 상태로 저장됩니다
    → 피보호자에게 알림이 갑니다 (앱 푸시 + 보고 있는 화면에 즉시)

  수락 / 거절 (피보호자):
    → POST   /api/ward/connection/{연결ID}/accept            → 연결됨(ACTIVE)  → 보호자에게 알림
    → DELETE /api/ward/connection/request/{연결ID}/refusal   → 거절됨          → 보호자에게 알림

  목록 보기:
    → GET /api/guardian/connection/select    → 보호자: 내 피보호자 (연결된 사람 + 대기 중인 사람)
    → GET /api/guardian/connection/requests  → 보호자: 내가 보낸 신청 전부 (취소·거절된 것 포함)
    → GET /api/ward/connection/active        → 피보호자: 내 보호자 (연결된 사람만)
    → GET /api/ward/connection/pending       → 피보호자: 받은 신청 카드 (전화번호는 가려서, 최소 정보만)

  상대방 정보는 연결이 된 뒤에만 보입니다 (2026-06-02 보강):
    언제나 보이는 것 : partnerUserId, partnerName, partnerProfileImage, relation, status,
                       isRequester, connectedAt, createdAt
    연결된 뒤에만    : partnerPhone, partnerAddress, partnerAddressDetail, partnerPostcode,
                       partnerGender(FEMALE/MALE), partnerBirthDate, partnerEmail
                       (수락 전에는 전부 null입니다)
    → 돌봄 서비스라 연결된 두 사람은 서로의 정보를 볼 수 있게 했습니다.
      성별·생년월일·우편번호는 원래 입력을 안 한 계정이면 연결된 뒤에도 null입니다.
    → 비밀번호, 소셜 로그인 내부 정보, 권한, 계정 상태, 마지막 로그인 시각은 절대 안 보여줍니다.
    ※ 수락 전 카드에 정보를 최소한만 담고 전화번호를 가리는 건 일부러 그런 것입니다.
      아직 수락하지 않은 상대에게 내 정보를 보여줄 이유가 없기 때문입니다.

  연결 끊기 / 신청 취소:
    → DELETE /api/guardian/connection/cancel/{연결ID}   → 보호자: 아직 수락 안 된 신청을 취소
    → DELETE /api/guardian/disconnection/{연결ID}       → 보호자: 연결 끊기
    → DELETE /api/ward/disconnection/{연결ID}           → 피보호자: 연결 끊기

  상태가 바뀌는 길:
    수락 대기  →  연결됨      [피보호자가 수락 → 보호자에게 알림]
    수락 대기  →  끝남        [보호자가 취소 → 알림 없음 / 피보호자가 거절 → 보호자에게 알림]
    연결됨     →  끝남        [누가 끊든 상대에게 알림]

    ※ 취소할 때만 알림이 없는 건 실수가 아닙니다.
      거절은 "싫다"는 분명한 의사표시라 상대가 알아야 하지만, 신청을 없던 일로 하는 건
      굳이 알릴 일이 아니라고 판단했습니다. 나중에 "통일성" 때문에 알림을 붙이지 마세요.


  긴급 SOS (피보호자만 누를 수 있습니다):
    → POST /api/ward/sos
      먼저 기록을 남기고(sos_event), 연결된 보호자 전원에게 알립니다.
      알림이 실패하더라도 "눌렀다"는 기록은 반드시 남습니다.

      · 생명이 걸린 알림이라 보호자가 알림을 꺼 놨어도 앱 푸시를 보냅니다.
        푸시가 실제로 전달되지 않으면(등록된 기기가 없거나, 만료됐거나, 보내다 실패)
        문자로 대신 보냅니다. 이 "안 가면 문자로" 장치는 SOS에만 있습니다.
      · 보호자가 여러 명이면 전원에게 보냅니다. 한 명에게 실패해도 나머지는 그대로 갑니다.
      · 짧은 시간에 여러 번 눌러도 알림은 한 번만 갑니다(놀라게 하지 않으려고).
        이 억제 장치에 문제가 생기면 억제를 포기하고 알림을 보냅니다 - 안 가는 것보다 낫기 때문입니다.
      · 환경설정의 "SOS 동작 설정"(GET·PUT /api/ward/sos-setting)은 119 화면을 어떻게
        보여줄지만 정합니다. 어떤 값으로 해도 보호자 알림은 항상 갑니다 (3-12 참고)
      · 보낼 내용은 전부 선택입니다.
        - { location } 어디서 눌렀는지 자유롭게 적는 칸(100자). 안 보내면 "위치 모름"으로 남습니다.
          ⚠️ 서버는 위치를 추측하지 않습니다. 주소를 찾아보거나 좌표로 바꾸지 않고,
            프론트가 보낸 글자 그대로 저장하고 보여주기만 합니다.
        - { triggerType } SOS_BUTTON(기본) 또는 GUARDIAN_CALL
          보호자 카드를 눌러 전화를 걸 때 이 API도 같이 부르면 그 전화도 기록에 남습니다.
          어느 쪽이든 보호자 알림은 똑같이 갑니다.
      · 응답: { sosEventId, triggeredAt }
      · 119 화면과 보호자에게 거는 전화는 프론트가 처리합니다(서버는 관여하지 않습니다).
        ⚠️ 119는 키패드 화면만 보여주고 실제로 걸지 않습니다(2026-08-26 결정, 학생 프로젝트라서).
        보호자 전화번호는 GET /api/ward/connection/active 의 partnerPhone을 쓰세요.

  SOS 기록 보기 (보호자만):
    → GET /api/guardian/sos/history

  [ 3-7. 푸시 알림(FCM) 토큰 관리 ]
  ─────────────────────────────
  앱은 기기별 FCM 토큰을 서버에 등록/삭제해야 푸시 알림을 받을 수 있습니다.

  [역할 분담]
  - 프론트엔드 : Firebase SDK 초기화 → 알림 권한 요청 → FCM 토큰 발급 →
                 백엔드 API 로 토큰 등록/삭제
  - 백엔드      : 토큰을 DB 에 저장(fcm_token) → 이벤트 발생 시 저장된 토큰으로
                 Firebase Admin SDK 통해 푸시 발송 (이미 구현됨)
  - Firebase    : 같은 프로젝트(silverbridgebe) 를 프론트/백엔드 모두 공유

  [프론트엔드가 받아야 하는 Firebase 값]
  웹 (React/Vue/Next 등):
    Firebase Console → 프로젝트 설정 → 일반 → "내 앱(웹)" → SDK 설정 및 구성
      apiKey, authDomain, projectId, storageBucket, messagingSenderId, appId
    Firebase Console → 프로젝트 설정 → Cloud Messaging → 웹 푸시 인증서
      VAPID 공개키 (getToken 호출 시 필요)
    배포 시 도메인 루트에 firebase-messaging-sw.js 함께 배포 (백그라운드 메시지 처리)

  Android:
    Firebase Console → "내 앱(Android)" → google-services.json 다운로드
    위치: app/google-services.json
    Gradle 에 com.google.gms.google-services 플러그인 적용
    (VAPID 키 불필요)

  iOS:
    Firebase Console → "내 앱(iOS)" → GoogleService-Info.plist 다운로드
    Xcode 프로젝트에 추가
    APNs 인증키(.p8) 를 Firebase Console → Cloud Messaging 에 등록(빌드 환경 작업)

  ※ apiKey / VAPID 공개키는 Firebase 가 클라이언트 노출을 전제로 설계한 값이라
    공개 저장소에 들어가도 보안상 문제가 없습니다. 보안은 Firebase Security
    Rules + 백엔드 인증으로 보장됩니다.

  [프론트엔드 호출 흐름]
  사용자 UX 에서는 "알림 허용" 권한 팝업 한 번만 보임. 토큰 등록/갱신은
  앱이 백그라운드로 처리.

    ① 앱 시작 또는 로그인 직후
       Firebase SDK 초기화 → 권한 요청 → getToken() 으로 토큰 발급 →
       POST /api/notifications/fcm-token

    ② 토큰 갱신 콜백 (onTokenRefresh)
       새 토큰 받아 다시 POST /api/notifications/fcm-token

    ③ 로그아웃
       DELETE /api/notifications/fcm-token?token=...

  [API 명세]
  토큰 등록 (앱 시작 시, 토큰 갱신 시):
    → POST /api/notifications/fcm-token
    → headers: Authorization: Bearer {accessToken}
    → body: { "token": "...", "platform": "android|ios|web" }
    → 200: { "message": "FCM 토큰이 등록되었습니다.", "success": true }
    → 동일 토큰 재등록 시 무시(중복 저장 안 함), 200 그대로 반환

  토큰 삭제 (로그아웃 시):
    → DELETE /api/notifications/fcm-token?token=...
    → headers: Authorization: Bearer {accessToken}
    → 200: { "message": "FCM 토큰이 삭제되었습니다.", "success": true }
    → 존재하지 않는 토큰이어도 200 (idempotent)

  [개발 단계 백엔드 테스트 도구]
  프론트 없이 백엔드 단으로 푸시 파이프라인을 검증하고 싶을 때:
    tools/fcm-test/index.html (정적 페이지)
    firebaseConfig / VAPID 키 채운 뒤 npx http-server 로 localhost 서빙 →
    브라우저에서 토큰 발급 → Swagger 로 등록 → 트리거 API 호출 → 푸시 도착 확인.


  [ 3-7-A. 알림 보내는 길과 채널별 수신 설정 ]  (2026-05-31 추가 / 알림톡 2026-07-27 가동)
  ─────────────────────────────
  알림 종류는 많지만 전부 같은 길을 지나갑니다.
  "무슨 일이 생김 → 알림 보내는 곳 한 군데 → 종류에 맞는 방법으로 발송"입니다.

  보낼 수 있는 방법은 4가지입니다.
    앱 푸시(FCM) / 문자(SMS) / 카카오 알림톡 / 이메일
    이 중 이메일은 자리만 만들어 두고 아직 만들지 않았습니다 - 켜 두어도 조용히 건너뜁니다.

  ▶ 구조가 이렇게 된 이유
    알림 종류가 늘 때마다 여기저기서 각자 보내면, 나중에 "이 알림은 왜 안 갔지"를 찾을 수 없습니다.
    그래서 보내는 곳을 한 군데로 모으고, 종류마다 "어떻게 보낼지"를 미리 정해 뒀습니다.
    - 새 방법(예: 이메일)을 추가할 때는 그 방법 하나만 만들어 등록하면 됩니다.
      보내는 곳이 알아서 찾아 씁니다.
    - 한 방법이 실패해도 나머지는 그대로 갑니다. 아직 안 만든 방법은 조용히 건너뜁니다.
    - 종류마다 "이 종류는 이 방법까지만 쓴다"고 정해 둘 수 있습니다(2026-09-01 추가).
      그러면 사용자가 켜 둔 방법 중에서도 허용된 것만 씁니다.
      ⚠️ 다만 "무조건 보내는 앱 푸시"는 이걸로 줄어들지 않습니다.
        줄일 수 있게 만들면 SOS·화재 알림이 안 가는 구멍이 생깁니다.
        지금 좁게 정해 둔 건 이상감지 "확인해 주세요"(앱 푸시만) 하나뿐입니다.
    - 화면 실시간 갱신(웹소켓)은 이 길을 지나지 않고 항상 보냅니다.
      화면을 보고 있는 사람에게는 바로 반영돼야 하기 때문입니다.

  ▶ 종류마다 어떻게 보내는가 (3가지 방식)
    ① 사용자 설정대로
       사용자가 켜 둔 방법으로만 보냅니다.
       → 연결 신청·수락·거절·해제, 문의 답변,
         복약 알림·체크 안 한 약 요약·복약 중지 안내,
         이상감지 "확인해 주세요"(이 종류는 앱 푸시만 쓰도록 좁혀 뒀습니다)

    ② 무조건 앱 푸시 + 안 가면 문자
       설정을 무시하고 앱 푸시를 보내고, 실제로 전달되지 않으면 문자로 대신 보냅니다.
       → SOS. 생명이 걸린 알림이라 설정으로 끌 수 없습니다.

    ③ 앱 푸시는 무조건 + 나머지는 설정대로
       앱 푸시는 반드시 보내고, 문자·알림톡은 켜 둔 사람에게만 보냅니다. 문자로 대신 보내지는 않습니다.
       → 이상감지(화재·연기).
         문자는 사용자가 고르는 방법인데, "안 가면 문자로"를 넣으면 그 선택을 뒤집는 셈이라
         일부러 넣지 않았습니다.

  ▶ 끌 수 있는 알림 / 끌 수 없는 알림
    끌 수 없는 것
      - 문자 인증번호(가입·비밀번호 재설정). 이건 아예 이 길을 지나지 않고 바로 보냅니다.
        그래서 설정으로 끄는 것 자체가 불가능합니다.
      - SOS의 앱 푸시, 이상감지의 앱 푸시 (위 ②③)
    끌 수 있는 것
      - 연결 관련 알림, 문의 답변, 복약 알림·요약·중지 안내, 이상감지 "확인해 주세요"
      - SOS와 이상감지의 문자·알림톡
    ※ 복약 체크는 화면 갱신만 하므로 이 분류에 들어가지 않습니다. 설정과 상관없이 항상 반영됩니다.

  ▶ 처음 값
    설정한 적이 없으면 앱 푸시는 켜짐, 문자·알림톡·이메일은 꺼짐입니다.
    기존 사용자도 그대로 앱 푸시를 받게 되어, 따로 데이터를 채워 넣는 작업이 필요 없었습니다.

  ▶ 설정 API  (Swagger 태그: "공통 - 알림 설정")
    보기:
      → GET /api/user/me/notification-settings
      → 헤더: Authorization: Bearer {accessToken}
      → 응답: { "settings": [ { "channelType": "FCM", "enabled": true }, ... 전체 방법 ] }
      → 정한 적 없는 방법은 처음 값으로 보여줍니다(앱 푸시만 켜짐)

    바꾸기:
      → PUT /api/user/me/notification-settings
      → 헤더: Authorization: Bearer {accessToken}
      → 보낼 것: { "settings": [ { "channelType": "SMS", "enabled": true }, ... ] }
        보낸 것만 바뀝니다.
      → 응답: 바꾼 뒤의 전체 설정
      → 카카오 알림톡을 켜 두면 이상감지 알림이 카카오톡으로도 옵니다.
        이메일은 값만 저장되고 실제로 보내지지는 않습니다.

  ▶ 카카오 알림톡에 대해
    카카오톡 채팅으로 도착합니다. 전화번호로 받는 사람을 찾기 때문에
    카카오 로그인이나 친구추가가 필요 없습니다.

    - ⚠️ 카카오에서 미리 승인받은 문구만 보낼 수 있습니다.
      마음대로 쓴 문장은 못 보내고, 정해진 자리에 이름·장소 같은 값만 채워 넣을 수 있습니다.
      승인받은 문구가 없는 알림은 알림톡만 조용히 건너뜁니다(다른 방법으로는 갑니다).
    - 이상감지 문구는 2026-07-27에 승인받았습니다(보호자용).
      채워 넣는 값: 피보호자 이름, 장소, 감지 종류, 감지 시각
    - 🚫 피보호자 본인에게는 알림톡을 보내지 않습니다.
      승인받은 문구가 "보호자로 등록하시고 직접 신청하신…"으로 시작해서, 본인에게 보내면
      사실과 어긋나고 카카오에서 제재를 받을 수 있습니다.
      본인에게 가는 화재 알림은 다른 종류로 처리되고 그 종류엔 승인 문구가 없어서
      알림톡만 빠집니다(앱 푸시·화면 알림·문자는 그대로 갑니다).
    - 🚫 "알림톡이 실패하면 문자로 대신 보내기"는 꺼 두었습니다.
      문자를 원하지 않은 사용자에게 요금이 나가고 문자가 가기 때문입니다.
    - 설정값은 .env.dev 에 넣습니다: ALIMTALK_ENABLED / ALIMTALK_PF_ID / ALIMTALK_TEMPLATE_ANOMALY

  ▶ 프론트가 할 일
    기존에 있던 것을 바꾸지 않고 더하기만 했기 때문에, 지금 코드는 그대로 두어도 똑같이 동작합니다.
    알림 설정 화면을 만들 때만 위의 두 API를 연결하면 됩니다.

  소유자 = 피보호자(ward_id). 보호자는 ACTIVE 연결을 통해 전이 접근합니다(피보호자당 여러 대 = 방별).

    → GET    /api/ward/camera        → 내 카메라 목록
    → PATCH  /api/ward/camera/{id}   → 라벨(설치 위치) 수정
    → DELETE /api/ward/camera/{id}   → 카메라 삭제

  보호자(GUARDIAN 전용):
    → GET /api/guardian/camera       → 연결된 피보호자들의 카메라 목록(ACTIVE 연결 기준 allowlist)

  ※ 타인 카메라 접근 시 403 CAMERA_NOT_AUTHORIZED("본인이 등록한 카메라만 사용할 수 있습니다.")
    — 방 이름·세션ID 등 내용은 노출하지 않고, 시도는 [IDOR-ATTEMPT] WARN으로 남깁니다.
    없는 카메라는 404. (2026-07-14 정책: 404 위장 → 403 명시 안내)
  ※ 카메라 등록 시 CameraRegisteredEvent가 발행돼 AI 세션 목록을 즉시 재요청합니다
    ("스트리밍 먼저, 등록 나중" 순서에서도 구독이 살아나도록).


  [ 3-11. AI 이상감지 (수신 → 판정 → 이력 → 알림) ]  (anomaly, 2026-07-13/07-14)
  ─────────────────────────────
  AI 서버에는 웹훅이 없어서, 백엔드가 AI의 WebSocket에 **클라이언트로 접속**해 분석 결과를
  구독합니다(AI 서버 코드 변경 없음). 프론트가 호출하는 API가 아니라 서버 내부 파이프라인입니다.

  흐름:
    AI WS(latest_analysis) 수신 → 판정 → 이력 쿨다운 → anomaly_event 적재
    → AnomalyDetectedEvent → (커밋 후) 리스너가 ACTIVE 보호자 전원 + 피보호자 본인에게 발송

  - 구독 대상: 등록된 camera.session_id만 subscribe(미등록 세션은 애초에 구독하지 않음)
  - 판정: ANOMALY_TRIGGER_MODE=DANGER(기본) — AI가 채운 danger 플래그만 신뢰(위험 판정 책임=AI).
    CONFIDENCE는 폴백 모드(confidence >= 0.6). ※ 배포된 AI가 danger를 항상 false로 내리는 동안은
    이력 0건이 정상이며 [ANOMALY-DANGER-MISMATCH] WARN으로 드러납니다.
  - 발송 채널: WebSocket(anomaly-detected, 항상) + FCM(고정) + SMS·알림톡(사용자 설정대로).
    알림톡은 보호자만 받습니다(3-7-A의 알림톡 항목 참고).
  - 문구: 보호자 "OOO님 댁 거실에서 화재가 감지되었습니다." / 본인 "거실에서 화재가 감지되었습니다.
    안전한 곳으로 대피해 주세요."(현장 당사자에게는 대피 행동을 함께 지시)
  - 알림 data: type·wardId·wardName·location·sessionId·detectedType·detectedTypeLabel·
    detectedAt(KST yyyy-MM-dd HH:mm)·anomalyEventId·incidentId(2026-09-01 추가)
    ※ incidentId는 판정 단위(상황) ID입니다. 보호자가 알림에서 바로 오탐 응답을 누르려면
      이력 행 ID(anomalyEventId)가 아니라 이 값이 필요합니다. 기존 키는 이름·의미 그대로입니다.
  - 빈도(2026-07-28 조정): 이력 1분 / 보호자 알림 5분 / 본인 알림 3분.
    이력은 촘촘히 남겨 화재 지속 구간의 타임라인을 확보하고, 사람에게 가는 알림은 성기게 보냅니다
    (보호자는 알림톡·SMS가 같은 간격으로 나가 과금·카카오 신고 리스크가 함께 걸립니다).
  - 발송 실패·WS 연결 실패·AI_API_KEY 미설정은 앱 기동을 막지 않습니다(구독만 비활성).


  [ 3-11-A. 이상감지 판정 - "진짜였나요?"를 보호자에게 물어보기 ]  (2026-09-01 추가)
  ─────────────────────────────
  AI가 "위험하다"고 알려줘도, 그게 정말 불이었는지 아니면 요리 연기를 잘못 본 것인지
  서버는 알 방법이 없습니다.
  AI가 주는 숫자는 "얼마나 불꽃처럼 보이는가"이지 "정말 불이 났는가"가 아니기 때문입니다.

  그래서 집 사정을 아는 보호자에게 나중에 물어봅니다.
  관리자는 보호자들 답이 서로 다를 때만 나서서 정리합니다.

  ▶ 여러 번 감지돼도 한 번만 물어봅니다 ("상황"으로 묶기)
    같은 카메라에서 불이 3분 이어지면 기록은 1분에 하나씩 3개가 쌓입니다.
    그렇다고 보호자에게 3번 물어볼 수는 없습니다. 그래서 이어지는 감지를 하나로 묶고,
    그 묶음을 "상황"이라고 부릅니다. 보호자는 상황 하나에 한 번만 답하면 됩니다.

    - 같은 집·같은 카메라·같은 종류이고, 마지막 감지에서 10분 안이면 같은 상황으로 잇습니다.
      ⚠️ "10분짜리 토막"이 아니라 "마지막 감지 기준"입니다.
        불이 1시간 이어져도 계속 이어지기만 하면 상황은 1건입니다.
    - 거실 화재와 주방 연기는 따로 셉니다. 대응하는 방법이 다르기 때문입니다.
    - 밤 12시(한국 시간)를 넘기면 새 상황으로 나눕니다.
      안 그러면 이 사건이 어느 날짜에 속하는지 애매해집니다.
    - 화면과 통계에 나오는 숫자는 전부 "상황 몇 건"입니다. 기록 몇 줄이 아닙니다.

  ▶ 보호자가 쓰는 API
    → GET  /api/guardian/anomaly/history?wardId=&page=&size=
                                → 이상감지 목록 (최신순, 여러 쪽으로 나눠서)
                                  wardId를 안 보내면 연결된 피보호자 전체를 합쳐서 보여줍니다
    → POST /api/guardian/anomaly/{incidentId}/feedback   { "verdict": "REAL" | "FALSE_ALARM" }
                                → 답하기. REAL = 진짜 위험, FALSE_ALARM = 잘못 본 것
                                  같은 건에 다시 보내면 답을 바꾸는 것입니다 (한 사람당 한 표)
    → GET·PUT /api/guardian/anomaly/reminder-setting     { "reviewReminderEnabled": true }
                                → "확인해 주세요" 알림을 받을지 말지 (기본은 받음)

    목록에 들어 있는 것:
      incidentId          이 상황의 번호 (답할 때 이 번호를 씁니다)
      wardId · wardName   누구 집인지
      cameraLabel         어느 카메라인지 ("거실"). 카메라를 지웠으면 null
      detectedType        FIRE(화재) / SMOKE(연기)
      detectedTypeLabel   "화재" / "연기" - 알림 문구와 같은 단어를 서버가 줍니다
      startedAt           처음 감지된 시각
      lastDetectedAt      마지막으로 감지된 시각
      eventCount          이 상황에서 몇 번 잡혔는지 (보호자가 판단할 근거가 됩니다)
      maxConfidence       가장 확실해 보였던 정도 (0~1)
      reviewStatus        지금 판정 상태 (아래 참고)
      myVerdict           내가 뭐라고 답했는지. 아직 안 했으면 null
      resolvedByAdmin     관리자가 이미 정리한 건이면 true → 답변 버튼을 막아야 합니다

  ▶ 판정 상태 4가지 (reviewStatus)
    PENDING       아직 아무도 답하지 않음
    REAL          답한 보호자 모두가 "진짜 위험이었다"
    FALSE_ALARM   답한 보호자 모두가 "잘못 본 것이다"
    CONFLICTED    보호자끼리 답이 서로 다름 → 관리자가 확인할 차례

    ⚠️ 많은 쪽으로 정하지 않습니다.
      3명 중 2명이 "잘못 봤다"고 해도 "엇갈림"으로 남깁니다.
      한 명은 진짜 불로, 한 명은 요리 연기로 봤다는 그 사실 자체가 관리자가 확인해야 할
      정보인데, 표를 세어 한쪽으로 정해 버리면 그 정보가 사라지기 때문입니다.
    ⚠️ 관리자가 정리한 건은 그걸로 끝입니다.
      나중에 다른 보호자가 답해도 관리자 결정이 바뀌지 않습니다(그런 시도는 409로 막습니다).
      ※ 다만 관리자가 정리하는 화면은 아직 없습니다. 그래서 resolvedByAdmin은 지금 항상 false입니다.
    ⚠️ "잘못 봤다"고 답해도 이미 보낸 알림을 취소하지 않습니다.
      "아까 그건 아니었어요"를 또 보내면 알림만 두 배가 되고,
      정작 다음에 진짜 불이 났을 때 사람들이 안 믿게 됩니다.

  ▶ 누가 볼 수 있나
    지금 연결되어 있는 피보호자의 기록만 볼 수 있습니다. SOS 기록·복약과 같은 규칙입니다.
    연결을 끊으면 예전 기록까지 그 즉시 안 보입니다.

    - 연결되지 않은 사람의 기록을 보려고 하면 → 403 "연결된 피보호자의 기록만 볼 수 있습니다"
      (그런 시도는 로그에 남깁니다)
    - 없는 번호를 부르면 → 404
    - 관리자가 이미 정리한 건에 답하려 하면 → 409

  ▶ 아무도 안 누르면 다시 물어봅니다
    답을 안 하면 판정 자료가 하나도 안 쌓이기 때문에, 서버가 한 번 더 물어봅니다.
    다만 조심스럽게 물어봅니다.

    - 상황이 끝나고(마지막 감지에서 10분) 1시간이 지나도 아무 답이 없으면 → 그 건에 대해 한 번
    - 그 뒤로는 하루에 한 번만, 저녁 8시에 "아직 답 안 하신 게 N건 있어요"로 묶어서
    - 상황이 생긴 지 3일이 지나면 더 이상 묻지 않습니다

    - 앱 푸시로만 보냅니다.
      문자는 반복해서 보내면 요금이 계속 나가고, 카카오 알림톡은 이런 반복 알림을 보내려면
      카카오에서 따로 승인을 받아야 하는데 아직 없습니다.
    - 밤 10시부터 아침 8시까지는 묻지 않고 아침으로 미룹니다.
      ⚠️ 화재 감지 알림 자체는 밤에도 그대로 갑니다. 미루는 건 "확인해 주세요"뿐입니다.
    - 보호자가 이 "확인해 주세요" 알림만 따로 끌 수 있어야 합니다.
      못 끄면 귀찮아서 앱 알림을 통째로 꺼 버리고, 그러면 그 집의 SOS·화재 알림까지 같이 죽습니다.
    - 보호자 중 한 명이라도 답하면 나머지에게는 더 묻지 않습니다.
      다만 답하는 창구는 계속 열려 있어서, 나중에 다른 보호자가 다르게 답하면
      그때 "엇갈림"이 됩니다.
    - 문구는 단정하지 않습니다.
      "화재가 발생했습니다"(X)
      "9월 1일 21:03 · 김영희님 거실에서 화재 감지가 있었습니다. 실제 상황이었는지 확인해 주세요."(O)
      진짜 위험이었는지는 아직 아무도 모르고, 그걸 묻는 것이 이 알림의 목적이기 때문입니다.
    - 문제가 생기면 ANOMALY_REVIEW_REMINDER_ENABLED=false 로 이 "다시 묻기"만 끌 수 있습니다.
      기록 보기와 답하기는 그대로 동작합니다.

  ▶ 프론트가 알아야 할 것
    - 화재 알림에 incidentId(상황 번호)가 추가됐습니다. 기존 항목은 그대로라 지금 코드는 안 깨집니다.
      ⚠️ 답할 때 보내는 번호는 anomalyEventId(기록 번호)가 아니라 incidentId입니다. 헷갈리기 쉽습니다.
    - 보호자 앱에 "진짜 위험이었나요 / 잘못 본 건가요" 버튼이 필요합니다.
      ⚠️ 이 화면이 없으면 "확인해 주세요" 알림을 받아도 누를 곳이 없고,
        판정 자료가 전부 "답 없음"으로만 쌓입니다.
        예전에 SOS에도 "처리했어요" 기능을 만들었다가 화면이 끝내 안 붙어서 기록이 전부 비었고,
        결국 2026-08-26에 그 기능을 없앴습니다. 같은 일을 반복하지 마세요.
    - resolvedByAdmin이 true면 답변 버튼을 눌리지 않게 해 주세요(누르면 409가 납니다).


  [ 3-11-B. 관리자 대시보드 - 안전 현황 / 운영 현황 ]  (2026-09-02 추가)
  ─────────────────────────────
  관리자 화면의 두 탭에 들어갈 숫자를 세어 주는 기능입니다.
  새 테이블을 만들지 않고 이미 있는 데이터를 세기만 합니다.
  (Swagger 태그: "관리자 - 대시보드")

    → GET /api/admin/dashboard/safety      → 안전 현황 탭
    → GET /api/admin/dashboard/operation   → 운영 현황 탭

  탭마다 주소를 나눈 이유는, 한쪽 탭만 보고 있을 때 다른 쪽 숫자까지 세느라 서버가
  괜히 일하지 않게 하기 위해서입니다.
  관리자만 볼 수 있고, 다른 사람이 부르면 거부(403)합니다.

  ▶ 왜 이제야 만들 수 있었나
    2026-08-07에 관리자 화면을 다시 설계할 때 "AI가 얼마나 잘못 봤는지(오탐률)" 카드를
    만들려다 포기했었습니다. 잘못 봤다는 걸 기록하는 곳이 아예 없어서 셀 것이 없었기 때문입니다.
    3-11-A에서 보호자가 "진짜였다 / 잘못 봤다"를 답할 수 있게 되면서 이제 셀 수 있게 됐습니다.

  ▶ 안전 현황 (/safety) - 무엇이 위험한 상태인가
    aiConnected           : AI 서버와 연결되어 있는지
    subscribedSessions    : 지금 지켜보고 있는 카메라 수 (AI와 끊겼으면 0)
    totalCameras          : 등록된 카메라 전체 대수
    streamingCameras      : 지금 화면이 들어오는 카메라 수   ※ AI와 끊겼으면 null
    safetyEvents          : 지켜보는 사람이 없거나 장비가 빠진 곳들
                            - disconnectedCameras     화면이 안 들어오는 카메라 (※ AI 끊기면 null)
                            - wardsWithoutGuardian    연결된 보호자가 한 명도 없는 피보호자
                            - wardsWithoutCamera      카메라를 한 대도 안 단 피보호자
                            - stalePendingConnections 7일 넘게 답이 없는 연결 요청
    todayAnomaly          : 오늘 이상감지 - 전체 건수, 종류별, 그리고 판정 결과 4가지

  ▶ 운영 현황 (/operation) - 서비스가 어떻게 굴러가는가
    totalUsers            : 전체 회원 수 (관리자는 빼고 셉니다)
    newUsersToday         : 오늘 가입한 사람
    memberComposition     : 피보호자 몇 명, 보호자 몇 명
    cameras               : 카메라 몇 대, 카메라를 가진 피보호자 몇 명
    pendingConnections    : 아직 수락 안 된 연결 요청
    unansweredInquiries   : count(답변 못 한 문의 건수) /
                            longestWaitingHours(가장 오래 기다린 문의가 몇 시간째인지)
                            ※ 기다리는 문의가 없으면 longestWaitingHours 는 null
    signupTrend           : 최근 7일 가입 추이. 가입이 없는 날도 0으로 채워서 보냅니다
    pendingItems          : 처리해야 할 것들 (연결 요청 / 오늘 문의 / 작성 중인 공지)

  ▶ 모르는 값을 0으로 채우지 않습니다 (가장 중요)
    카메라 정보에는 "지금 켜져 있는지"를 적어두는 칸이 없습니다.
    그래서 "몇 대가 켜져 있나"는 AI 서버와 대화하면서 알아냅니다.

    ⚠️ 그런데 AI 서버와 연결이 끊기면 우리는 카메라 상태를 알 수 없게 됩니다.
      이때 "0대"라고 답하면, 사실은 우리 쪽이 고장난 건데 화면에는
      "집집마다 카메라가 전부 꺼졌다"로 보입니다. 관리자가 큰일 난 줄 알고 놀랍니다.
      그래서 이럴 때는 0이 아니라 null(모름)로 보냅니다.
      화면에는 "확인 불가"처럼 표시해 달라고 프론트에 전달했습니다.

    같은 이유로, 기다리는 문의가 한 건도 없을 때 대기 시간은 0시간이 아니라 null입니다.
    0시간이라고 하면 "방금 막 들어온 문의가 있다"와 구분이 안 됩니다.

    이 3개 말고는, 데이터가 없어도 항상 0이나 빈 목록이 들어 있습니다.

  ▶ "잘못 본 비율"은 반드시 "얼마나 답했는지"와 같이 보여줘야 합니다
    판정 결과 4가지(답 없음 / 진짜 위험 / 잘못 봄 / 엇갈림)를 전부 보냅니다.
    답한 건수 = 전체 - 답 없음 이므로, 화면에서 이렇게 쓸 수 있습니다.

      "오늘 5건 중 3건 답변(60%), 그중 1건이 잘못 본 것"

    ⚠️ "잘못 봄 1건"만 덜렁 띄우면 안 됩니다.
      물어봐도 모두가 답하지는 않기 때문에, 답 안 한 것까지 합쳐서 비율을 내면 실제보다
      낮게 나오고, 답한 것만 세면 높게 나옵니다. 어느 쪽으로 센 건지 화면에 같이 적어야
      관리자가 그 숫자를 믿을 수 있습니다.
      예전에 SOS에서도 "처리했어요" 기록이 전부 비어 있는 걸 두고 "보호자가 아무도 대응
      안 했다"로 읽힐 뻔했습니다. 같은 함정입니다.

  ▶ 그 밖의 약속
    - 종류별 숫자에는 실제로 감지된 것만 담습니다.
      "낙상 0건"은 안전했다는 뜻이 아니라 AI가 아직 낙상을 못 본다는 뜻인데,
      0이라고 적어두면 정확히 반대로 읽힙니다.
    - 보호자끼리 답이 엇갈린 건은 "위험 신호" 목록에 넣지 않았습니다.
      그건 지금 조치할 일이 아니라 관리자가 따로 확인할 일이라 성격이 다릅니다.
      오늘 몇 건인지는 판정 결과 숫자에서 볼 수 있습니다.
    - 날짜는 전부 한국 시간 기준입니다.
    - 숫자를 미리 저장해 두지 않고 볼 때마다 새로 셉니다.
      미리 저장해 두면 "방금 문의에 답했는데 왜 안 줄지?" 같은 일이 생겨서
      관리자가 화면을 믿지 못하게 됩니다. 대신 화면 갱신은 30초에 한 번 이상으로 권했습니다.
    - 대시보드를 본 기록은 남기지 않습니다. 숫자만 보는 데다 계속 새로고침되는 화면이라,
      기록하면 정작 중요한 "누가 공지를 고쳤다" 같은 기록이 파묻힙니다.
      단, 개인 기록을 들여다보는 화면(다음에 만들 이상감지 로그)은 반드시 남깁니다.

  ▶ 아직 없는 것
    관리자가 이상감지 기록을 목록으로 보고 엇갈린 판정을 정리하는 화면은 아직 없습니다.
    그래서 3-11-A의 resolvedByAdmin은 항상 false입니다. 다음 작업입니다.


  [ 3-12. 피보호자 SOS 동작 설정 ]  (sos_setting, 2026-07-23 추가)
  ─────────────────────────────
  환경설정 > "SOS 동작 설정"을 계정 단위로 보관합니다(종전에는 프론트 localStorage 전용이라
  기기·브라우저를 바꾸면 초기화됐습니다).

    → GET /api/ward/sos-setting   → 현재 설정(행이 없으면 기본값 CALL_119_AND_NOTIFY)
    → PUT /api/ward/sos-setting   → 설정 저장(upsert). WARD 전용

  값(SosAction): CALL_119 / CALL_119_AND_NOTIFY / NOTIFY_GUARDIAN_FIRST

  ※ 이 설정은 "119 안내 화면을 언제 어떻게 보여줄지"(프론트 흐름)만 정합니다.
    ⚠️ 119로 실제 전화를 걸지 않습니다 (2026-08-26 결정) - 프론트는 119가 입력된 키패드 화면만
    보여주고 발신은 하지 않습니다(학생 프로젝트라 실제 신고가 나가면 안 되기 때문).
    값 이름 CALL_119는 "전화를 건다"가 아니라 "119 화면을 띄운다"는 뜻입니다.
    ⚠️ 어떤 값에서도 보호자 알림은 항상 발송됩니다 - SOS는 필수 알림(WARD_SOS)이라 사용자 설정으로
    끌 수 없습니다. CALL_119도 "알림 없이"라는 뜻이 아닙니다.

  4. WebSocket(실시간 알림) 사용 가이드

  연결 엔드포인트:
    wss://api.devdmu.gosky.kr:6511/ws  (STOMP, 네이티브 WebSocket)
    인증: 쿼리 파라미터로 ?token={accessToken} 전달 (JWT 검증 필수)

    import { Client } from '@stomp/stompjs';
    const stompClient = new Client({

      onConnect: () => {
        stompClient.subscribe('/topic/' + myUserId + '/connection-request', msg => {...});
      },
    });
    stompClient.activate();

  ▶ 구독 가능 토픽 (본인의 userId만 허용 — 타인 토픽 구독 시 거부됨)
    /topic/{userId}/connection-request     피보호자가 받는 보호자의 연결 요청

    /topic/{userId}/connection-refused     보호자가 받는 피보호자의 거절 알림 (2026-05-28 추가)
    /topic/{userId}/connection-cancelled   연결 해제 알림
    /topic/{userId}/sos-triggered          보호자가 받는 피보호자의 긴급 SOS 알림 (2026-06-09 추가)
    (sos-acknowledged 토픽은 처리 결과(ACK) 기능 철회로 제거됨 - 2026-08-26, V39)
    /topic/{userId}/anomaly-detected       이상감지 알림 — 보호자·피보호자 본인 모두 (2026-07-14 추가)
                                           payload = wardId·wardName·location·detectedType·
                                           detectedTypeLabel·detectedAt·anomalyEventId 등
                                           ※ 피보호자 화면을 24시간 켜두는 사용 형태에서는 이 토픽이
                                             가장 확실한 경보 경로입니다(브라우저 알림 권한·무음 설정과 무관).
    /topic/{userId}/medication-taken        복약 체크·해제 실시간 반영 (2026-08-04 추가)
                                           — 해당 피보호자의 ACTIVE 보호자 전원 + 피보호자 본인 수신
                                           payload = medicationId·wardId·medicationName·doseDate·
                                           taken·takenAt (값은 모두 문자열, 해제 시 takenAt은 null)
                                           ※ 푸시·문자는 없습니다(일상 동작이라 소음).
    /topic/{userId}/medication-stopped      등록 보호자 탈퇴로 약이 중지됨 (2026-08-04 추가)
                                           — 남은 ACTIVE 보호자만 수신. payload = wardId·stoppedCount

  ※ 보안: StompSubscriptionAuthorizationInterceptor가 구독 시점에
    {userId}가 인증 세션의 userId와 일치하는지 검증해, 타인의 실시간 알림
    도청을 차단합니다.


--------------------------------------------------------------------------------
  5. 데이터베이스 테이블 및 컬럼 설명
--------------------------------------------------------------------------------

  ※ 모든 날짜/시간 컬럼은 시간대 포함(TIMESTAMPTZ) 형식으로 저장됩니다.
     예) 2025-04-19T09:00:00+09:00
  ※ 모든 사용자 ID(users.id, user_id 참조)는 6자리 문자열입니다.
  ※ 테이블 이름은 단수형입니다 (2026-07-14, V31에서 통일 — connection·camera·anomaly_event…).
     users만 예외로 복수형을 유지합니다 — user는 PostgreSQL 예약어라 모든 참조를 "user"로
     인용해야 하고, 인용을 빠뜨린 쿼리는 테이블이 아니라 세션 사용자를 뜻해 조용히 오동작합니다.


  [ users — 회원 ]
  ─────────────────────────────
  id             : 회원 고유 ID (6자리 문자열)
  email          : 이메일 주소 (중복 불가, 로그인 사용)
  password       : 암호화된 비밀번호 (카카오 가입자는 NULL)
  name           : 이름
  phone          : 전화번호 (중복 불가, 선택)
  role           : 역할 — WARD(피보호자) / GUARDIAN(보호자) / ADMIN(관리자)
  status         : 계정 상태 — ACTIVE(정상) / INACTIVE(비활성)
                   ※ 탈퇴는 hard delete로 행 자체가 삭제됨 — INACTIVE는 탈퇴 처리 중
                     과도 상태이거나 관리자 정지 등 비활성 계정을 의미 (3-5절 참고)
  provider       : 가입 방식 — LOCAL(이메일) / KAKAO(카카오)
  provider_id    : 카카오 고유 ID (일반 가입자는 NULL)
  profile_image  : 프로필 이미지 파일명 (NULL 시 기본 이미지)
  gender         : 성별 — FEMALE / MALE (V18 추가, 기존 사용자는 NULL)
  birth_date     : 생년월일 (DATE, V18 추가, 기존 사용자는 NULL)
  postcode       : 우편번호 5자리 (V18 추가, 기존 사용자는 NULL)
  last_login_at  : 마지막 로그인 일시
  address        : 주소 (DB 기본값 빈 문자열, 단 신규 가입·프로필 수정 시 필수)
  address_detail : 상세 주소 (DB 기본값 빈 문자열, 단 신규 가입·프로필 수정 시 필수)
  created_at     : 가입 일시
  updated_at     : 마지막 수정 일시 (트리거로 자동 갱신)
  ※ name 은 V18에서 VARCHAR(50)→VARCHAR(20) 축소. 신규 가입·프로필 수정 시 성별/생년월일/우편번호 필수입력.


  [ refresh_token — 로그인 재발급 토큰 ]
  ─────────────────────────────
  id         : 고유 번호
  user_id    : 어떤 회원의 토큰인지 (users.id FK, CASCADE 삭제)
  token      : 토큰 문자열 (중복 불가)
  expires_at : 토큰 만료 일시
  created_at : 발급 일시

  ※ 만료된 토큰은 매일 새벽 3시(TokenCleanupScheduler)에 자동 삭제됩니다.
  ※ 비밀번호 변경 시 해당 회원의 모든 refresh token 삭제 + 발급된
    accessToken도 Redis password:invalidate 로 즉시 무효화 (Critical-1).
  ※ refresh token 재사용(도난) 감지 시 해당 회원 토큰 전부 강제 폐기 (H-3).


  [ access_log — 접근 로그 ]
  ─────────────────────────────
  id         : 고유 번호
  user_id    : 해당 회원 ID (탈퇴 시 NULL 보존)
  action     : 행동 유형
                 LOGIN, LOGOUT, KAKAO_LOGIN, TOKEN_ISSUE, PASSWORD_RESET,
                 WITHDRAW, TOKEN_REUSE_DETECTED
                 ※ WITHDRAW: 회원 탈퇴 시점 기록 (탈퇴 직전에 user_id와 함께 기록)
                 ※ TOKEN_REUSE_DETECTED: refresh token 재사용(도난) 감지 시
                   강제 폐기와 함께 기록 (V16, H-3)
                 ※ PASSWORD_RESET 은 IP/UA 포함 기록 (M-3)
  ip_address : 요청 IP
  user_agent : 요청 브라우저/앱 정보
  created_at : 발생 일시


  [ sos_event — 피보호자 긴급 SOS 발생 이력 ] (2026-06-09 추가)
  ─────────────────────────────
  id         : 고유 번호
  ward_id    : SOS를 발생시킨 피보호자 ID (탈퇴 시 NULL 보존 — 익명 감사 기록)
  created_at : 발생 일시
  location   : 발생 위치 자유 문구 (선택, 100자 — 프론트가 보낸 값 그대로. NULL이면 위치 미상)  (V34, 2026-07-31)
  trigger_type : 발생 경로 - SOS_BUTTON(긴급 SOS 버튼) / GUARDIAN_CALL(보호자에게 직접 전화)  (V39, 2026-08-26)
                 NOT NULL, 기본값 SOS_BUTTON. 표시 전용이며 알림 발송을 가르지 않음.
  ※ 발송된 보호자 목록은 저장하지 않음 - 알림은 이력 커밋 후 발송되며,
    대상 보호자는 발송 시점의 ACTIVE connection에서 도출(정규화 유지).
  ※ 처리 결과(ACK) 컬럼 4종(ack_status·ack_by·ack_at·ack_note, V33)은 기능 철회로 제거됨
    (V39, 2026-08-26). 보호자 화면이 붙은 적이 없어 전건 미처리로 쌓이는 지표였고,
    이력은 "언제·어떤 경로로 발생했는지"까지만 답하기로 정리했다.


  [ medication — 복약 일정 ] (V35, 2026-08-04 추가)
  ─────────────────────────────
  id          : 고유 번호
  ward_id     : 약을 복용하는 피보호자 ID (탈퇴 시 CASCADE 삭제)
  created_by  : 등록한 보호자 ID (탈퇴 시 CASCADE — 그 보호자가 등록한 약도 함께 중지)
  name        : 약 이름 (100자)
  time_slot   : 복용 시간대 — MORNING / LUNCH / DINNER / BEDTIME
  dose_time   : 복용 시각 (미지정 시 time_slot 기본값 08:00/13:00/18:00/22:00)
  dose_amount : 복용량(정, 기본 1)
  memo        : 복용 안내 (선택, 100자 — 예 "식사와 함께")
  deleted_at  : 삭제 일시 (NULL이면 사용 중 — soft delete로 지난 복용 이력을 보존)
  created_at / updated_at
  ※ 등록은 보호자만 — created_by가 피보호자인 행은 존재하지 않습니다.
  ※ 조회는 항상 deleted_at IS NULL로 거릅니다(부분 인덱스도 같은 조건).
  ※ 인덱스: (ward_id)·(created_by) 부분 인덱스(V35) + (dose_time) 부분 인덱스(V38, 2026-08-06).
    dose_time 인덱스는 스케줄러가 1분마다 던지는 "복용 시각이 지난 약" 조회가 풀스캔이 되지 않게

  dose_date     : 복용 예정일 (KST 기준 날짜)

  [ medication_reminder_log — 복약 알림 발송 기록 ] (V36, 2026-08-05 추가)

  id            : 고유 번호

  attempt       : 발송 회차 — 1=최초, 2=재알림
  sent_at       : 발송 시각
  ※ 행의 존재 = 그 회차를 이미 보냈다는 뜻입니다. 스케줄러가 1분마다 돌기 때문에 이 기록이 없으면
    유예 창 동안 같은 알림이 반복됩니다.
  ※ UNIQUE(medication_id, dose_date, attempt) — 재기동·주기 중복에도 같은 회차는 한 번만 나갑니다.
  ※ 발송 "전"에 기록을 먼저 남기고 보냅니다. 발송이 실패하면 그 회차는 재시도하지 않습니다
    (알림이 두 번 가는 쪽이 더 나쁘다는 판단 — 재알림이 두 번째 기회).

  [ guardian_medication_setting — 보호자별 복약 알림 수신 설정 ] (V37, 2026-08-05 추가)
  ─────────────────────────────
  id                   : 고유 번호
  guardian_id          : 보호자 회원 ID (UNIQUE, CASCADE)
  missed_alert_enabled : 미복용 요약 알림 수신 여부

                         ※ NULL을 21:00으로 백필하거나 NOT NULL DEFAULT로 바꾸지 마세요 —
                           서버 기본값을 바꿔도 기존 보호자가 따라오지 않게 됩니다.
  created_at / updated_at
  ※ UNIQUE (guardian_id, ward_id) — 보호자당 1행에서 (보호자, 피보호자)당 1행으로 바뀌었습니다(V41).
  ※ 행이 없으면 기본값 ON. medication_setting(피보호자 단위)과 축이 다릅니다 —
    저쪽은 "피보호자에게 무엇을 보낼지", 이쪽은 "보호자가 무엇을 받을지"입니다.

  [ medication_missed_alert_log — 미복용 요약 발송 기록 ] (V37, 2026-08-05 추가)

  ward_id      : 대상 피보호자 (CASCADE)

  [ anomaly_event — AI 이상감지 이력 ] (2026-07-13 추가, 1단계)
  ─────────────────────────────
  id            : 고유 번호
  ward_id       : 카메라 소유 피보호자 (CASCADE — 탈퇴 시 이력도 삭제)
  session_id    : 감지된 카메라 세션 (camera.session_id 비정규화 — 카메라 삭제 후에도 판독)
  detected_type : FIRE / SMOKE  (fall·weapon 은 AI 라이브 미탑재)
  confidence    : 신뢰도
  danger        : AI 위험 판정 플래그 (판정 근거 기록 — CONFIDENCE 폴백 적재분은 false)
  detected_at   : AI 분석 시각(analyzedAt). NULL 허용 — AI 캐시 미스 페이로드엔 이 값이 없음
                  (NULL = 분석 시각 불명, 수신 시각은 created_at)
  incident_id   : 이 이력이 속한 상황 (V44, 2026-09-01 추가. CASCADE)
                  NULL = 상황 묶음 도입 이전 이력이라는 뜻이며 판정 대상이 아닙니다
                  (사후에 채울 근거가 없어 백필하지 않았습니다)
  created_at    : 백엔드 수신·적재 일시

  ※ 적재 조건: AI WS(latest_analysis) 신호 중 danger=true (기본 DANGER 모드) 인 건만.
    같은 (session_id, detected_type) 은 Redis 쿨다운 1분에 1건만 적재된다 (2026-07-28 5분→1분)
    (AI가 매 프레임 broadcast 하므로 쿨다운이 없으면 위험 1건에 이력 수백 개).
  ※ 보호자·본인 알림 발송은 2단계로 구현 완료(2026-07-14) — 3-11 참고.
    알림은 이력이 적재된 건에만 발행되므로, 이력 쿨다운이 알림 상한도 함께 정한다.


  [ anomaly_incident — 이상감지 "상황" (판정 단위) ] (V44, 2026-09-01 추가)

--------------------------------------------------------------------------------
  6. Redis 키 (임시 데이터)
--------------------------------------------------------------------------------

  모든 Redis 키는 global/util/RedisKeys.java 상수로 관리됩니다.

  ▶ SMS 인증
    sms:verify:{phone}           회원가입 SMS 인증코드 (5분)
    sms:verified:{phone}         회원가입 인증 완료 상태 (10분)
                                 값 = verificationNonce(UUID), 가입 요청과 대조 (H-5)
    sms:attempt:{phone}          오류 횟수 (5분)
    sms:sendcount:{phone}        per-phone 발송 건수 — 1시간 10회 상한 (A-M3)
                                 ※ 재발송 쿨다운(sms:cooldown) 키는 폐지됨

  ▶ 비밀번호 재설정 (6자리 코드 — UUID 토큰/쿨다운 폐지)
    password:email:verify:{email}  이메일 재설정 인증코드 (5분)
    password:email:attempt:{email} 이메일 오류 횟수 (5분)
    password:email:sendcount:{email} per-email 발송 건수 — 1시간 10회 상한 (2026-05-23,
                                   SMS sms:sendcount A-M3와 대칭. 가입 확인된 이메일만 카운트)
    password:sms:verify:{phone}    SMS 재설정 인증코드 (5분)
    password:sms:attempt:{phone}   SMS 오류 횟수 (5분)
    password:invalidate:{userId}   비밀번호 변경 시각 — 이전 발급 accessToken
                                   무효화 기준 (TTL = accessToken 만료시간, Critical-1)

  ▶ 카카오 OAuth
    kakao:pending:{kakaoId}      신규 가입 임시 이메일 (10분)
    ※ OAuth state 는 프론트 검증 모델 → Redis 미사용 (M-1)

  ▶ 로그인 보안
    login:fail:{userId}          실패 횟수 (30분, user.id 기준 — H-2)
    login:lock:{userId}          잠금 상태 (30분, user.id 기준 — H-2)
    logout:{SHA-256(accessToken)} 로그아웃 토큰 블랙리스트 (남은 만료시간)
                                 키는 토큰 원문이 아닌 해시 (M-6)

  ▶ 요청 속도 제한
    rate:{endpoint}:{identifier} IP 또는 userId 기반 1분 고정 윈도우 (최대 10회)
                                 INCR+EXPIRE를 Lua로 원자 처리 (RedisCounter, M-4)
                                 적용 endpoint 확대: token-refresh, kakao-login,
                                 pw-reset-confirm (M-8), signin (A-H2)
    rate:{endpoint}:1m:{ip}      비밀번호 재설정 send/resend 이중 윈도우 — 분 카운터 (2026-05-23)
    rate:{endpoint}:1h:{ip}      동 시간 카운터. pw-reset-email/pw-reset-sms = 1분 10회/1시간 30회
                                 (미가입 응답 노출에 따른 자동화 enumeration 방어, 한쪽 초과 시 429)

  ▶ 이상감지 (2026-07-13 / 알림 쿨다운 2026-07-14)
    anomaly:cooldown:{sessionId}:{detectedType}
                                 이상감지 이력 적재 쿨다운 (기본 1분, SET NX EX)
                                 AI는 매 프레임(초당 여러 번) 분석 결과를 broadcast 하므로
                                 이 키가 없으면 위험 1건이 이력 수백 행이 된다.
                                 Redis 장애 시 fail-open (중복 이력 < 이력 유실)
    anomaly:notify:{userId}:{sessionId}:{detectedType}
                                 수신자별 알림 재발송 쿨다운 — 보호자 5분 / 피보호자 본인 3분.
                                 이력 쿨다운과 별개다: 이력은 촘촘히 남기고 사람에게는 성기게 알린다.
                                 보호자 쪽은 알림톡·SMS가 같은 간격으로 나가 과금·카카오 신고
                                 리스크가 함께 걸리므로 더 길게 잡는다.
                                 Redis 장애 시 fail-open (화재 알림을 인프라 장애로 삼키지 않는다)

  ▶ 기타
    character:expression:{wardId} 최근 표정 캐시 (조회 API용)
    ws:connected:{userId}        WebSocket 접속 상태 (12시간)


--------------------------------------------------------------------------------
  7. 보안 정책 요약
--------------------------------------------------------------------------------

  [ 인증/인가 ]
  - JWT: accessToken 30분, refreshToken 7일 (Rotation 적용)
  - JWT typ(access/refresh) 클레임으로 토큰 용도 구분 — refreshToken을 Bearer로
    제시해 보호 자원에 접근하는 혼용을 필터가 차단 (A-H1)
  - 로그아웃 시 accessToken을 Redis 블랙리스트 등록 (키는 SHA-256 해시, M-6)
  - 비밀번호 변경/재설정 시 refreshToken 전부 삭제 + 발급된 accessToken도
    즉시 무효화 (password:invalidate + JWT 필터 iat 검증, Critical-1)
  - refresh token 재사용(도난) 감지 시 해당 회원 토큰 전부 강제 폐기 (H-3)
  - BCrypt strength 12 (M-11)

  - @PreAuthorize로 Role 기반 엔드포인트 제한
    예: /api/guardian/** → GUARDIAN, /api/ward/** → WARD, /api/admin/** → ADMIN
  - /api/auth/logout 은 permitAll에서 분리해 인증 필수, 미인증 401 JSON (L-3)

  [ 응답 보안 헤더 (A-L2) ]
  - HSTS / X-Frame-Options: DENY / X-Content-Type-Options: nosniff / Referrer-Policy: same-origin
  - Content-Security-Policy: default-src 'self' (+ Swagger UI 호환 위해 script/style
    'unsafe-inline') + frame-ancestors 'none' / object-src 'none' / base-uri 'self'

  [ 로그인 보호 ]
  - 로그인 실패 응답 통합: 미가입 이메일 / 비밀번호 불일치 모두
    INVALID_CREDENTIALS(401) — 계정 enumeration 차단 (H-1)
  - INACTIVE 안내는 비밀번호 검증 통과한 본인에게만 노출 (H-1)
  - user.id 기준 5회 실패 → 30분 잠금 (LOGIN_LOCKED 429).
    미가입 이메일은 잠금 카운터 영향 없음 — 정상 사용자 DoS 차단 (H-2)
    잠금 횟수/시간은 application.yaml auth.login.* 로 외부화 (M-12)
  - INACTIVE 계정은 로그인 차단 + Refresh Token 즉시 삭제
    (login·kakaoLogin·refresh 세 경로 일관, H-4)

  [ 관리자 보호 ]
  - 공지사항 쓰기 작업은 admin_audit_log 자동 기록 (AdminAuditLogService)

  [ 전화번호 변경 시 SMS 인증 필수 ]
  - PUT /api/user/me 에서 phone 변경 시 sms:verified 키 + nonce 확인
  - 미인증/nonce 불일치 시 SMS_NOT_VERIFIED 400 반환

  [ 요청 속도 제한 (Redis 기반, 기본 1분 10회) ]
  - IP 기반: signin, email-check, find-email, signup-sms, pw-reset-email, pw-reset-sms,
    token-refresh, kakao-login, pw-reset-confirm
    (signin은 A-H2에서 추가, token-refresh·kakao-login·pw-reset-confirm은 M-8에서 추가)
  - pw-reset-email/pw-reset-sms(send·resend)는 이중 윈도우 1분 10회 / 1시간 30회 (2026-05-23)
    — 미가입 응답 노출에 따른 자동화 enumeration·어뷰징 방어, 한쪽 초과 시 429
  - userId 기반: sos-trigger, connection-request, fcm-register
  - per-phone: SMS 발송(sms:sendcount) 1시간 10회 상한 (A-M3)
  - per-email: 비번재설정 메일 발송(password:email:sendcount) 1시간 10회 상한 (2026-05-23)
  - INCR+EXPIRE는 Lua 스크립트로 원자 처리 (RedisCounter, M-4/L-2)

  [ 비밀번호 재설정 — 가입 여부 명시 응답 (2026-05-23) ]
  - 정책 변경: send/resend는 미가입 시 404, 카카오 가입 계정은 400으로 명확히 안내
    (기존 always-200 enumeration 차단 폐지 — 시니어/4050 타겟 이탈 UX 개선)
  - enumeration·비용 방어: IP 이중 윈도우 + per-email/per-phone 상한 + 미가입 [PW-RESET] WARN
    로깅 + 미가입자 SMS/메일 발송 전 차단. confirm(reset) 단계는 코드 선검증 유지(A-M1)
  - 거부안: 응답 시간 정규화(존재 여부를 의도적으로 노출하므로 모순), 의심 IP 블랙리스트
    (공용 NAT 시니어 다수 오차단 위험)

  [ 타인 자원 접근(IDOR) 응답 — 404 위장 → 403 명시 안내 (2026-07-14) ]
  - 종전에는 타인의 카메라·문의를 404로 위장해 존재 자체를 숨겼으나, "왜 안 보이지"로 이탈하는
    시니어/4050 UX를 우선해 무슨 일이 일어났는지 그대로 안내하도록 바꿨습니다
    (비밀번호 재설정의 판단과 동일).
  - CAMERA_NOT_AUTHORIZED(403) "본인이 등록한 카메라만 사용할 수 있습니다."
    INQUIRY_NOT_AUTHORIZED(403) "본인이 작성한 문의만 볼 수 있습니다."
    없는 자원은 그대로 404(*_NOT_FOUND).
  - 수용한 노출은 "그 id의 자원이 존재한다"는 사실뿐 — 방 이름·세션ID·문의 본문 등 내용은
    절대 응답에 싣지 않습니다. 시도는 [IDOR-ATTEMPT] WARN(userId + 대상 id)으로 로깅합니다.

  [ WebSocket 구독 권한 ]
  - StompSubscriptionAuthorizationInterceptor가 SUBSCRIBE 시
    /topic/{userId}/... 의 userId를 세션 인증 userId와 비교
  - 타인 토픽 구독 시 거부 (IDOR 차단)

  [ 파일 업로드 ]
  - 5MB 이하, JPG/PNG/WebP/GIF만 허용
  - 이미지 교체 시 기존 파일 자동 삭제 (실패는 로그만)

  [ 페이지네이션 크기 제한 ]
  - ?size= 최대값 100 (초과 시 자동 제한)

--------------------------------------------------------------------------------
  8. 빌드 도구 — Gradle
--------------------------------------------------------------------------------

  ★ Gradle이란?
  프로젝트를 "빌드"하는 도구. 소스 코드를 실행 가능한 JAR 파일로 만들어줍니다.
  마치 요리 레시피(소스)를 실제 음식(실행 파일)으로 만드는 과정입니다.


  [ build.gradle 주요 내용 ]
  ─────────────────────────────

  ▶ plugins
    id 'java'                             → Java 프로젝트
    id 'org.springframework.boot'         → Spring Boot 패키징
    id 'io.spring.dependency-management'  → 버전 관리 자동화

  ▶ java toolchain
    Java 21 사용

  ▶ repositories
    mavenCentral() → 공개 라이브러리 저장소

  ▶ dependencies (주요 라이브러리)

    spring-boot-starter-webmvc            : HTTP API 서버
    spring-boot-starter-data-jpa          : DB 연동 (SQL 자동 생성)
    spring-boot-starter-data-redis        : Redis 연동
    spring-boot-starter-security          : 인증/인가
    spring-boot-starter-oauth2-client     : 카카오 OAuth
    spring-boot-starter-validation        : 입력값 유효성 검사
    spring-boot-starter-mail              : 이메일 발송
    spring-boot-starter-websocket         : WebSocket
    spring-boot-starter-actuator          : /actuator/health 헬스체크 + 관측성
    springdoc-openapi-starter-webmvc-ui   : Swagger UI
    jjwt-api / jjwt-impl / jjwt-jackson   : JWT 토큰
    lombok                                : @Getter, @Setter 등 자동 생성
    postgresql                            : PostgreSQL 드라이버
    flyway-core / flyway-database-postgresql : DB 스키마 버전 관리
    firebase-admin                        : FCM 푸시
    solapi SDK                            : SMS 문자 발송
    aspectjweaver                         : AOP (공통 로그)

  ▶ plugins 추가
    org.owasp.dependencycheck             : 의존성 취약점(CVE) 스캔
                                            CVSS 7.0(High) 이상 발견 시 빌드 실패

  ▶ 주요 Gradle 명령어
    ./gradlew build -x test --no-daemon       → 테스트 제외 빌드 (푸시 전 검증)
    ./gradlew bootJar --no-daemon             → JAR 파일 생성
    ./gradlew test                            → 테스트 실행
    ./gradlew dependencyCheckAnalyze --info   → 의존성 취약점 스캔
                                                결과: build/reports/dependency-check-report.html
    ./gradlew dependencies                    → 의존성 트리

  ※ CI(테스트 자동 실행)는 없습니다 — 로컬에서 ./gradlew build 검증 후 푸시.
  ※ CD는 GitHub Actions(.github/workflows/cd.yml)에 구성되어 있어,
    dev 브랜치 push 또는 수동 workflow_dispatch 시 self-hosted 러너(label: dev)가
    git pull → docker compose up -d --build api → 이미지 정리를 자동 수행합니다.
    배포 직전에 .env.dev 존재 여부를 확인하고, 없으면 친화적 에러로 즉시 중단합니다.

    healthcheck    : 10초마다 pg_isready

--------------------------------------------------------------------------------
  9-1. 관측성 (Observability) — Spring Boot Actuator
--------------------------------------------------------------------------------

  Actuator는 서버 상태를 외부에 노출하는 표준 엔드포인트 세트입니다.
  보안상 노출은 최소화했습니다.

  ▶ 공개 엔드포인트 (인증 불필요)
    GET /actuator/health   → 200 { "status": "UP" } (DB/Redis 내부 상태는 숨김)
    GET /actuator/info     → 빌드 메타 정보

  ▶ 상태 확인 방법
    로컬    : curl http://localhost:6511/actuator/health
    개발    : curl https://api.devdmu.gosky.kr/actuator/health
    Docker  : docker ps  (STATUS 열에 healthy/unhealthy 표시)

  ▶ 정책
    - show-details: never (DB·Redis 상태 세부 노출 차단)
    - exposure.include = health, info (그 외 actuator 엔드포인트 전부 비공개)
    - health.probes.enabled = true (liveness/readiness 분리)

        한 번에 모아 에러로 알려주므로 안심하고 채우면 됩니다.

     ▶ PostgreSQL (DB 컨테이너 + Spring 양쪽에서 사용)
       POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD
       DB_HOST, DB_NAME, DB_USERNAME, DB_PASSWORD
       ※ DB_USERNAME / DB_PASSWORD 는 약한 기본값(dev) 제거로 필수 — 미설정 시 시작 실패 (A-L3)

     ▶ Redis
       REDIS_HOST

     ▶ JWT
       JWT_SECRET           (32자 이상 랜덤, 약한 기본값은 거부됨)
       ※ AI_SERVER_API_KEY 는 AI 도메인 제거로 더 이상 필요/검증되지 않음 (A-L5)

     ▶ 메일 (Spring Mail)
       MAIL_USERNAME, MAIL_PASSWORD
       (선택) MAIL_HOST, MAIL_PORT — 미설정 시 smtp.gmail.com:587

     ▶ 카카오 OAuth
       KAKAO_REST_API_KEY, KAKAO_CLIENT_SECRET, KAKAO_REDIRECT_URI
       ※ KAKAO_CLIENT_SECRET: 카카오 콘솔 [보안 > Client Secret] 발급 값, "사용 함" 활성화 필요 (2026-05-25 추가)

     ▶ Solapi SMS
       SOLAPI_API_KEY, SOLAPI_API_SECRET, SOLAPI_SENDER_PHONE

     ▶ Firebase (FCM)
       FIREBASE_SERVICE_ACCOUNT_BASE64
         서비스 계정 JSON을 base64로 인코딩한 문자열을 단일 라인으로 넣습니다.
         (원본 JSON을 그대로 .env에 넣으면 docker compose env_file 파서가 \n을
          실제 newline으로 변환해 깨지므로 base64로 우회 — application.yaml에서 디코딩)
         예) base64 -w0 service-account.json   → 출력된 문자열을 그대로 대입
         ※ 더 이상 src/main/resources/firebase-service-account.json 또는 docker volume mount 방식을 사용하지 않습니다.

     ▶ (선택) APP_CORS_ORIGINS — 미설정 시 기본값 사용

  2) Docker로 전체 실행
     docker compose -f docker-compose.dev.yml up -d

  3) 빌드 검증 (푸시 전 필수)
     ./gradlew build -x test --no-daemon

  4) API 문서 확인

     개발   : https://api.devdmu.gosky.kr/swagger-ui/index.html

  12. Git 브랜치 전략
--------------------------------------------------------------------------------

  prod    : 배포 기준 브랜치
  dev     : 개발 기준 브랜치 (feature 브랜치의 merge 대상)
  feature : 기능 개발 브랜치 (dev에서 분기, merge 후 자동 삭제)

  브랜치 네이밍: type/short-description
    feature, fix, hotfix, refactor, design, docs, test, chore, infra, release

  커밋 메시지 포맷:
    type: 무슨 작업을 했는지 한국어로
    - 상세 내용 (선택)

  작업 순서:
    1) git pull origin dev
    2) git checkout -b type/short-description
    3) 작업 및 커밋
    4) push 전 ./gradlew build -x test --no-daemon 검증
    5) git push origin type/short-description
    6) PR 생성 → dev로 머지 → 브랜치 자동 삭제 → 서버 자동 배포

  ⚠️ dev/prod에 코드를 직접 커밋·푸시하지 않습니다 — feature 브랜치 → PR → dev 흐름만 허용.
  📄 예외: 문서(.md·docs/**)만 바뀌는 변경은 PR을 생략하고 dev에 직접 커밋·푸시합니다
     (2026-06-20 결정). CD가 paths-ignore로 배포를 어차피 건너뛰므로 PR 게이트가 불필요합니다.
     코드가 1줄이라도 섞이면 이 예외는 적용되지 않습니다.

  배포 환경이 둘입니다:
    - vkcs-linux : dev push 시 CD(GitHub Actions self-hosted)로 자동 배포
    - skyserver  : 공개 도메인(api.devdmu.gosky.kr)이 붙은 환경. 수동 배포
                   (git reset --hard origin/dev → docker compose build/up → image prune)
    ※ dev에 머지해도 skyserver는 바뀌지 않습니다. 각 서버의 .env.dev도 서로 별개입니다.

  13. 연관 서비스 — 이미 구축된 SilverBridge 도메인 (다른 저장소)
--------------------------------------------------------------------------------

  SilverBridge는 이 백엔드(SilverBridgeBe) 하나로 끝나지 않고, 같은 GitHub 조직
  (Dongyang-Mirae-University-software)의 여러 저장소가 역할을 나눠 맡는 구조입니다.
  아래 서비스들은 이미 구현되어 배포 서버(skyserver, 내부 IP 58.75.21.151)에
  Docker 컨테이너로 떠 있습니다. 이 백엔드나 프론트에서 "새로 만드는" 것이 아니라
  "API로 연결"하는 대상입니다.

  ※ 아래 포트는 서버 내부(localhost) 기준입니다. 공개 도메인이 붙은 것도 있고,
    없는 것은 SSH 터널로만 접근합니다.

  ▶ (A) SilverBridgeReservation — 병원 예약 / 병원 예약 현황  [이미 구현·가동 중]
    - 역할   : 병원 예약, 예약 현황(운영상태·혼잡도·대기), 예약 가능 시간대 제공
    - 스택   : NestJS + Prisma + JWT  (자체 관리자 웹 admin-ui, MCP 브릿지 포함)
    - 포트   : 6015  (컨테이너 silverbridgereservation-reservation-api-1)
    - 문서   : Swagger  http://localhost:6015/docs
    - 주요 API (prefix /api/v1)
        예약     : POST /reservations,  GET /reservations/my,
                   GET /reservations/{id},  PATCH /reservations/{id}/cancel,
                   DELETE /reservations/{id}
        예약현황 : GET /hospitals,  GET /hospitals/{id},
                   GET /hospitals/{id}/status          (운영상태·혼잡도·대기인원),
                   GET /hospitals/{id}/available-slots  (예약 가능 시간대),
                   GET /hospitals/{id}/departments
    - ⚠️ 데이터는 실제 병원 EMR이 아니라 "더미(모의)"입니다. 데모/과제용 연동 목적.
    - ✅ 결론: 병원 예약·예약 현황은 우리가 새로 구현할 필요 없이 위 API만 연결.

  ▶ (B) SilverBridgeAiServer — AI 이상감지 / 의료 챗 서버  [이미 구현·가동 중]
    - 역할   : 카메라·모델 관리, 이미지/스트림 이상감지 분석, iPad 송출(MJPEG),
               의료 챗(MedGemma) 상담, 예약 API 키 저장, 미니 게임
    - 스택   : FastAPI (Python) + PostgreSQL,  API Key 인증
    - 포트   : 6017 (AI 서버, 컨테이너 silverbridge-ai-server) / 6019 (전용 PG)
    - 주요 API (prefix /api/v1)
        카메라       : /camera (등록·목록·상세·수정·삭제·연결테스트)
        모델         : /models  (등록·목록·상세·활성화 등)
        스트림/이상감지: /stream-sessions, /live-streams/{id}/mjpeg,
                        /live-streams/{id}/latest-analysis
        의료 챗      : POST /chat,  GET /chat/logs
        예약 연동    : POST /reservation-credentials (예약 API 키 저장)
    - 참고: 배포본은 로컬 SilverBridgeAi(개발용)보다 앞선 버전.

  ▶ (C) ChatSilverBridge — 의료 AI(MedGemma) 챗 백엔드
    - 역할   : 증상/건강 질문에 대한 의료 보조 안내형 답변 (모델 medgemma-1.5-4b-it)
    - 스택   : FastAPI (Python),  API: GET /health, POST /chat
    - 참고   : HuggingFace gated 모델(HF_TOKEN 필요). AiServer의 챗 기능과 연관.
    - 테스트 FE: ChatSilverBridgeTest (Next.js, ChatSilverBridge /chat 호출 검증용)

  ▶ (D) SilverBridgeFe — 메인 프론트엔드  [가동 중]
    - 스택   : Next.js,  포트 6510 (컨테이너 silver-bridge-fe-dev-web)
    - 참고   : 로컬 경로는 ../SilverBridgeFe. 이 백엔드(6511)와 짝을 이루는 앱.

  ▶ (E) SilverBridgeStreamTestFe — 스트림/이상감지 테스트 프론트  [가동 중]
    - 역할   : SilverBridgeAiServer(6017)의 카메라·스트림·감지기 출력 점검용 UI
    - 스택   : React/Next,  포트 6018 (컨테이너 silverbridge-stream-test-fe)

  ▶ (F) 보조·실험 저장소 (참고용, 주력 아님)
    - SilverBridgeAi        : AI 관련 개발 브랜치(developing) 저장소
    - AiSilverBridgeSky     : 카메라 송출/DISPLAY_MODE 관련 초기 서비스
    - SilverBridgeSSOBe     : 별도 SSO 백엔드(Spring, Auth·Kakao·Admin) — 참고
    - SilverBridgeSky       : 상위 셋팅 저장소(umbrella)

  ※ 같은 서버에 있는 WhiteHouse* / sky-card / skyhub / ocrall / immich 등은
    SilverBridge와 무관한 다른 프로젝트이므로 위 목록에서 제외했습니다.

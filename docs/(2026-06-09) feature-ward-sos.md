# 피보호자 긴급 SOS 기능 (feature/ward-sos)

- **작업 일자**: 2026-06-09
- **브랜치**: `feature/ward-sos` (← `dev`)
- **유형**: feature (신규 도메인 `sos`)

---

## 1. 기능 정의

피보호자(WARD)가 대시보드 > 긴급 전화 > **"긴급 SOS"** 버튼을 누르면 백엔드가:

1. **SOS 발생 이력을 DB에 저장**한다 (`sos_events`). 알림 발송 성공 여부와 무관하게 **항상 기록**된다.
2. 연결된 **ACTIVE 보호자 전원**에게 **긴급 알림**을 발송한다 (WebSocket + FCM).

### 핵심 정책

- **필수 알림**: SOS 알림은 보호자의 알림 설정(ON/OFF)과 **무관하게 무조건 발송**된다.
- **전원 발송**: 연결된 ACTIVE 보호자가 여러 명이면 **전원**에게 발송하며, 한 명 발송 실패가 다른 보호자를 막지 않는다(실패 격리).
- **WARD 전용**: 피보호자(WARD 역할)만 SOS를 발생시킬 수 있다.

---

## 2. 범위

### 범위 안 (백엔드)
- SOS 발생 이력 저장 + ACTIVE 보호자 전원 긴급 알림(FCM + WebSocket).

### 범위 밖 (프론트 처리 — 백엔드 무관)
- **119 통화 화면**: 순수 프론트 연출. 백엔드는 119를 전혀 모른다.
- **보호자 직접 전화**: 프론트가 `tel:` 링크로 처리. 전화번호는 기존 보호자 조회(`GET /api/ward/connection/active`)의 `partnerPhone`으로 이미 제공됨 — 신규 API 불필요.

## 3. 설계

### 3-1. 엔드포인트
```
POST /api/ward/sos        (피보호자 전용, @PreAuthorize("hasRole('WARD')"))
요청 바디: 없음
인증: Authorization: Bearer {accessToken}
응답: ApiResponse<SosResponse> { success, data: { sosEventId, triggeredAt } }
```

### 3-2. 이력 테이블 (신규, Flyway V26)
```sql
CREATE TABLE sos_events (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ward_id    VARCHAR(6) NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_sos_events_ward FOREIGN KEY (ward_id) REFERENCES users (id) ON DELETE SET NULL
);
CREATE INDEX idx_sos_events_ward_created ON sos_events (ward_id, created_at DESC);
```
- **최소 설계**: 발송된 보호자 목록은 저장하지 않는다 — 알림은 이력 커밋 *후*(AFTER_COMMIT) 발송되므로 저장 시점엔 미확정이고, 보호자는 발송 시점의 ACTIVE connections에서 도출 가능(정규화 유지).
- `ward_id`는 회원 탈퇴(hard delete) 시 `ON DELETE SET NULL`로 **익명 보존** — `access_logs`와 동일 정책.

### 3-3. 처리 흐름 (기존 connection 알림 패턴 미러링)
```
WardSosController.triggerSos(wardId)
  └─ SosService.trigger(wardId)              @Transactional
       1. userRepository.findById  → 피보호자 이름 확보 (없으면 USER_NOT_FOUND)
       2. sosEventRepository.save(SosEvent)  ← 이력 무조건 저장
       3. publishEvent(SosTriggeredEvent(wardId, sosEventId, wardName))
  └─ (커밋) ───────────────────────────────────────────────
  └─ SosNotificationListener.handleSosTriggered
        @Async("notificationExecutor") @TransactionalEventListener(AFTER_COMMIT)
       1. connectionService.getActiveGuardianIds(wardId)   ← ACTIVE 보호자 전원
       2. 보호자 0명 → 이력만 남기고 종료
       3. for each guardian (try/catch 실패 격리):
            - WebSocket  : /topic/{guardianId}/sos-triggered
            - Dispatcher : NotificationType.WARD_SOS (필수 → 설정 무시 FCM)
```
- **AFTER_COMMIT**: 알림 발송 실패가 이력 저장을 롤백시키지 않는다(이력은 무조건 보존). DB 롤백 시엔 알림도 나가지 않는다.
- **@Async**: 발송 지연이 HTTP 응답 시간에 포함되지 않는다.

### 3-4. 긴급 알림 내용
| 채널 | 내용 |
|------|------|
| WebSocket | 토픽 `/topic/{guardianId}/sos-triggered`, payload `{ wardId, wardName, sosEventId }` |
| FCM | 제목 `긴급 SOS` / 본문 `{피보호자}님이 긴급 도움을 요청했습니다.` / data `{ type: "WARD_SOS", wardId, sosEventId }` |

### 3-5. 필수 알림 분류 (설정 무시)
- `NotificationType`에 **`WARD_SOS(true)`** 추가 — `isMandatory()==true`.
- `NotificationDispatcher`는 mandatory 타입이면 사용자 설정을 무시하고 `MANDATORY_CHANNELS`(현재 `{FCM}`)로 강제 발송. → SOS는 보호자가 알림을 꺼도 **반드시** FCM을 받는다. (enum javadoc이 예고했던 "긴급 알림용 확장 지점"의 첫 사용처.)
- WebSocket은 채널 추상화 밖이라 항상 발송.

## 5. 프론트 인계

### SOS API
```
POST /api/ward/sos
Headers: Authorization: Bearer {accessToken}
Body: (없음)

200 OK
{
  "success": true,
  "data": { "sosEventId": 42, "triggeredAt": "2026-06-09T12:34:56+09:00" }
}
403  → WARD 역할이 아님
401  → 미인증
```

### 보호자 측 WebSocket (SOS 수신)
```
구독 토픽: /topic/{guardianId}/sos-triggered
payload  : { "wardId": "...", "wardName": "...", "sosEventId": "42" }
```
- 본인 userId 토픽만 구독 가능(`StompSubscriptionAuthorizationInterceptor`가 검증). 이벤트명 화이트리스트 없이 `{userId}==세션` 범용 검증으로 자동 보호됨.
- FCM data: `type=WARD_SOS` 로 포그라운드 분기.

### 프론트가 처리할 범위 밖
- **119 통화 화면**: 프론트 연출(백엔드 호출 없음).
- **보호자 직접 전화**: `GET /api/ward/connection/active` 응답의 `partnerPhone` + `tel:` 링크.

### 기존 테스트 갱신 (의도된 변경)
- `NotificationDispatcherTest`의 분류 가드 `현재_모든타입_선택`(모든 타입이 비-필수임을 단언)은 **mandatory 타입이 추가되면 깨지도록 설계된 가드**였다(주석: "mandatory 타입이 추가되면 의도적 검토를 유도"). `WARD_SOS(true)` 도입으로 의도대로 트리거됨 → 가드를 다음으로 교체:
  - `필수알림_설정무시_FCM강제발송`: WARD_SOS 디스패치 시 설정 조회 없이 FCM 강제 발송 검증.
  - `분류_가드_필수타입_고정`: 디스패처 경유 필수 타입은 `WARD_SOS` 하나뿐, 연결 알림은 모두 선택임을 고정.

## 7. 배포/운영 메모

- **마이그레이션 V26**은 `dev` 머지 시 CD가 자동 적용(빈 테이블 신규 생성, 비파괴적). 기존 `V1`~`V25` 미수정.
- **rate limit 미적용(의도)**: SOS는 긴급 버튼이라 과도한 제한이 실제 위급을 차단할 위험이 있어 별도 rate limit을 두지 않았다. (필요 시 추후 별도 결정.)

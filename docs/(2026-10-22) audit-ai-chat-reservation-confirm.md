## 0-2. 남은 한계 해소 (2026-10-22, AI #30 `34aeb03` · 예약 서비스 #2 `a6e0f06`, gosky 반영 완료)

| 한계 | 상태 | 조치 |
|---|---|---|
| 선점이 단일 서버·프로세스 전제(메모리) | ✅ | 선점을 DB 테이블 `reservation_token_claims`((user_id, token) 기본키)로 이동. 채팅 세션과 분리된 짧은 세션으로 INSERT 후 즉시 커밋, 기본키 충돌이면 이미 선점. 선점 직후 10분 지난 행 정리(실패해도 선점 무영향). DB 오류는 삼키지 않고 요청 실패(예약 안 함). `create_all`이 테이블을 만든다(마이그레이션 없음). 서버가 여러 대여도 유효 |
| 예약 서비스 중복 검사가 `findFirst` 후 INSERT | ✅ | 활성(BOOKED·CONFIRMED) 예약에만 걸리는 **부분 유니크 인덱스 2개**(`Reservation_active_user_slot_key`: 사용자+날짜+시간 / `Reservation_active_hospital_slot_key`: 병원+날짜+시간). 취소·완료·거절 슬롯은 재사용 가능. 인덱스 위반(P2002)은 기존 코드(`DUPLICATE_RESERVATION`/`SLOT_TAKEN`)로 변환해 AI·FE 응답이 달라지지 않는다. 관리자 상태 변경이 취소 예약을 되살릴 때도 같은 코드로 변환 |
| 시험 가상 계정 | ✅ | 예약 서비스에 삭제 API가 없어 승인받은 id 32·33·34(사용자 3·취소 예약 16·API 키 4)와, 실서버 시험이 새로 만든 id 35·36·37(사용자 3·취소 예약 6·API 키 3)을 가드 스크립트(이름 "가상환자"·10/22 생성·활성 예약 0건이 아니면 중단)로 삭제. 사용자 14명·예약 166건으로 시험 이전과 같다 |

- **발견**: 예약 서비스 DB는 Postgres가 아니라 **SQLite**(도커 볼륨 `reservation_sqlite`)였고, 서비스에 테스트가 없었다. 부분 유니크 인덱스는 SQLite가 지원해 방향은 유효했다. 인덱스를 빼고 같은 동시 요청 테스트를 돌리면 **실제로 중복 예약이 생겼다** - 예약 서비스 자체에 경합이 있었다는 증거다. 테스트 러너(`pnpm test`, Node 내장 + tsx)를 새로 추가했다.
- **배포**: 예약 서비스 → AI 순. 예약 서비스는 `dev.db`를 `VACUUM INTO`로 백업(`/app/data/dev.db.bak-202610220142`)하고 겹침 0건을 다시 확인한 뒤 재빌드, 컨테이너 시작 시 `prisma migrate deploy`가 인덱스 2개를 만들었다(예약 182건 보존). AI는 카메라 프레임·분석 트래픽이 없는 것을 확인한 뒤 재빌드(헬스 `:6017/health` 200, 에러 로그 0, 새 테이블 생성).
- **검증**: AI pytest 420건·예약 서비스 6건 통과, 변이(AI 4종·예약 마이그레이션 제거) 모두 테스트에서 실패. 실서버(가상 계정):
  - 같은 토큰 동시 3클릭 x3라운드 -> 매 라운드 예약 1건(나머지는 "처리 중" 또는 만료 안내)
  - **서로 다른 사용자 3명이 같은 병원·같은 슬롯을 동시에 확정** x3라운드 -> 매 라운드 활성 예약 1건, 나머지 2명은 "이미 마감된 시간대" 안내. 이 경로는 AI 선점이 막지 못하는 경우(토큰이 서로 다름)라 예약 서비스 쪽 방어가 실제로 작동한 것이다(응답이 `findFirst`에서 났는지 인덱스에서 났는지는 구분하지 못했고, 인덱스 경로는 단위 테스트가 고정한다)
  - 시험 예약은 전부 취소, 활성 0건, 챗 기록·예약 키 삭제
- **남은 것(수용)**: 인덱스는 SQLite 전제다. 예약 서비스를 다른 DB로 옮기면 부분 인덱스 문법을 확인해야 한다. 슬롯 유니크는 "병원 슬롯 한 건" 구조(R-6)를 전제로 하므로 한 시간에 여러 명을 받게 바꾸면 이 인덱스를 먼저 바꿔야 한다. `prisma migrate dev`가 부분 인덱스를 드리프트로 보고 지우려 할 수 있어 `schema.prisma`에 주석을 남겼다. **`dev.db` 백업(`/app/data/dev.db.bak-202610220142`, 약 120KB)은 7일 보관하기로 했다 - 2026-10-29 이후 삭제 가능**(gosky에 `at`이 없고 cron은 다른 프로젝트와 공유라 자동 삭제는 만들지 않았다, 삭제는 `docker exec silverbridgereservation-reservation-api-1 rm /app/data/dev.db.bak-202610220142`).

## 3. 이슈

### 🟡 M-1 같은 확인 버튼을 동시에 눌러 중복 예약이 생길 수 있다 (구조적, 실서버 미재현)

- **구조**: 확인 토큰은 "직전 `chat_log` 한 행"을 읽어 검증하고, 소비(= 새 로그 기록)는 응답을 만든 **뒤**에 일어난다. 두 요청이 직전 로그를 같이 읽으면 둘 다 검증을 통과해 `create_reservation`을 각각 부른다. 예약 서비스의 중복 거절(`findFirst` 후 생성, `userId+날짜+시간` 인덱스는 유니크가 아님)도 같은 방식이라 동시 요청을 막는다고 보장할 수 없다.
- **로컬 재현**: 예약 서비스 응답을 0.2초 지연시킨 가짜로 같은 토큰 2회 동시 호출 → `create` 2회 호출(임시 테스트 `test_A1_double_click_race_creates_twice`).
- **실서버**: 가상 계정으로 같은 토큰을 3개 스레드가 동시에 보내기를 5라운드(15회) → 매번 `make_appointment` 1건 + 나머지 2건은 만료 응답, **활성 예약 1건**. 서버에 명시적 잠금은 없고(`threading`·`Lock` 없음, 동기 `def chat`은 스레드풀 실행) 왜 직렬처럼 보였는지는 확정하지 못했다.
- **영향**: 어르신이 버튼을 더블 탭한 경우가 현실적인 경로다. 같은 병원·날짜·시간 예약이 두 건 생기고 사용자는 취소 흐름으로 지울 수 있다(타인에게 영향 없음). 그래서 🟠이 아니라 🟡.
- **수정 제안** (승인 후 별도 PR):
  1. 서버 안에서 `(userId, 토큰)` 단위 소비를 원자적으로 한다 - 단일 인스턴스 전제의 프로세스 내 락 + "이미 소비한 토큰" 집합(TTL), 또는 `chat_log` 행에 대한 조건부 UPDATE(소비 표시)로 먼저 선점하고 호출한다(복약 알림 "선점 후 발송"과 같은 방식).
  2. 생성 직전에 같은 날짜·시간에 이미 BOOKED 예약이 있는지 `list_my_appointments`로 한 번 확인한다(원자적이지 않지만 창을 줄인다).
  3. 동시 호출 테스트를 고정한다(지연 있는 가짜 + 스레드 2~3개, 락 제거 시 실패).
- **참고**: 예약 서비스의 `userId+날짜+시간` 유니크 제약은 예약 서비스 저장소 범위다(별도 판단).

- 두 세션 교차(`test_A_two_sessions_same_user_do_not_cross`), 응급 문장 3단계(`cancel_pick`·`cancel_confirm`·`confirm_card`)

### 🟢 L-2 "취소"·"변경" 문장 오인

키워드(`예약`+`취소`/`변경·바꿔…`)만 보므로 아래가 취소/변경 요청으로 읽힌다. **모두 확인 단계를 거치므로 실제 취소·변경은 일어나지 않고**, 목록에 "그만두기"가 있다.

| 문장 | 취소 | 변경 | 비고 |
|---|---|---|---|
| 예약 잘 됐어요 취소 안 할게요 | ✔ | | 부정문 |
| 예약을 취소하지 않을래요 | ✔ | | 부정문 |
| 예약 취소 말고 변경할래 | ✔ | ✔ | 취소가 우선 |
| 병원 예약 변경 방법 알려줘 | | ✔ | 질문 |
| 예약 시간 바꿔줘 | | ✔ | 예약 진행 중이면 신규 예약 수정 의도일 수 있음 |
| 취소된 예약 내역 보여줘 | ✘ | ✘ | 조회 키워드 제외로 정상 |

개선 제안: 부정 표현("안 할게", "하지 않", "말고")은 취소 후보에서 제외. 실제 LLM 라우터를 거친 대량 측정은 하지 않았다.

### 🟢 L-3 취소·변경 목록에 지난 날짜가 나오고 개수 상한이 없다

`_cancellable_rows`는 상태(BOOKED/CONFIRMED)만 거른다. 날짜가 지난 BOOKED 예약도 목록에 나오고, 예약이 많으면 칩이 길어진다. 선택 뒤에는 예약 서비스가 취소 가능 여부를 판단한다. 제안: 오늘 이후만 보여주고 날짜순 최대 10건.

### 🟢 L-4 INFO 로그에 환자 이름이 남는다

`[예약트레이스]`가 `reservation_submit`·`reservation_draft`에서 `patient_name`을 INFO로 남기고 `decisionTrace`로 `chat_log`에도 저장한다. 기존 패턴이고 전화번호는 끝 4자리만이다. 새로 늘어난 노출은 아니며(`reservation_submit`은 기존에 있던 필드), 로그 위생 기준(이름 미출력)을 맞추려면 이름은 길이만 남기는 쪽을 제안한다.

### 4-2. 인가·대리

- **남의 예약**: 선택·취소는 모두 키 소유자 범위로 예약 서비스가 판정한다(`getOne`·`cancel`이 `{id, userId}`로 조회, 없으면 404). 남의 id는 서비스 404 메시지가 그대로 전달되고 취소 호출이 일어나지 않는다.
- **pick 값 조작**: `+5`·공백 포함·전각 `５`는 5로 해석되어 정상 흐름(확인 단계)으로 갈 뿐 무해하고, `0`·`-1`·초대형·문자열·소수·`5;6`·빈 값은 호출 없이 안내만 나간다.
- **대리 예약**: 카드에 "누구의 예약인지"가 표시되고, 확인 시점의 `wardId`가 카드 생성 때와 다르면 거부된다(변이 M1 제거 시 테스트 실패). `wardId`·이름·전화는 BE 중계가 ACTIVE 연결 검증 후 DB 값으로 채운다(2026-10-20 점검). AI 서버는 BE 전제를 신뢰한다(기존 수용).
- **PII**: 응답에 `meta`·`pendingAction`이 실리지 않는다(응답 키 목록 확인). `GET /chat/logs`의 `contextJson`에는 들어 있지만 BE `ChatLogProjection`이 허용 목록으로 걸러 FE에 나가지 않는다. 확인 카드의 연락처는 `010-****-0001` 형태로 가린다.

### 4-3. 기능 정합성 (실서버 포함)

- 정상 흐름(요청 → 병원 → 날짜 → 시간 → 카드 → 예약 → 취소) 통과. 날짜 미입력은 항상 묻는다(이력의 "오늘" 문구가 이월되지 않음, 변이로 확인).
- 고치기 중 직접 입력: 실서버에서 "오후 2시로 해주세요" → 카드 시간 14:00 반영(옛 시간이 이력에서 되살아나지 않음).
- 변경: 새 예약 실패 시 기존 유지 / 성공 후 기존 취소 / 기존 취소 실패 시 안내 + 재시도 확인 / 선택하는 사이 기존 예약이 취소되면 "이미 취소" 안내(로컬).
- 새 예약 요청 문장은 고치기 흐름을 빠져나온다(예약 호출 없음).
- 응급: 취소 목록·취소 확인·확인 카드 세 단계 모두 응급 문장이 상담으로 가고 예약 호출이 없다(`test_B_emergency_text_in_every_stage`).
- 두 세션을 번갈아 쓰면 직전 로그가 달라져 대기 중이던 카드가 만료된다 - 안전하게 실패한다.

### 4-4. 구조·계약

- 새 도구 이름 `cancel_reservation`을 FE `ChatToolCard`는 알지 못해 **카드를 그리지 않고 무시**한다(`return null`). 응답 `ui`(select)는 field와 무관하게 칩으로 그려진다.
- 응답 형식(`type`·`ui`·`tool`·`toolData`)과 `chat_logs` 형식은 그대로다. 새 `type`은 `tool_result`/`tool_error`/`ui`/`message`의 기존 값이다.
- 예약 생성 성공 응답에서 FE 카드(`make_appointment`)의 "예약 목록 보기" 버튼과 `reservation_followup` 칩이 같이 보인다 - 이번 변경 전부터 있던 중복이다.

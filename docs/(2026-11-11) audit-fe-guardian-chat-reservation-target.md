## A. 보안·인가

| 항목 | 결과 | 근거 |
|---|---|---|
| wardId 출처 | PASS | 대상 선택지 값(AI가 BE `guardianWards`로 만든 목록) 또는 그 답을 받은 요청의 wardId만. 고르지 않은 ID를 만드는 경로 없음 |
| 서버 검증 짝 | PASS | 선택 턴에 `uiSelection.value`와 같은 값을 `context.wardId`로 싣는다(실측 `wardIdEqSel=true`) |

| 대화 바뀜 중 응답 | PASS | 답 대기 중 [새 대화] 막힘, 대화가 바뀌면 늦은 답 버림 |
| PII·로그 | PASS | 새 console 로그 없음. 탭 저장소의 wardId·선택지 이름은 #249 이전(대화 키·선택지)과 같은 수준 |

## B. 기능 정합성 - 이슈

### 🟡 M-1 연결이 끊긴 피보호자 대리 예약 중이면 [새 대화] 전까지 모든 입력이 실패한다
- 상황: 대리 예약 도중(직전 답 = wardId 요청의 예약 답) 그 피보호자와 연결이 끝남 → 다음 글·버튼이 그 wardId로 나가 BE 403 `CHAT_WARD_NOT_CONNECTED`.
- 실패 안내는 `failed`라 `stepSource`·`textWardId`가 건너뛴다 → 다음 입력도 같은 wardId → 다시 403. 패널 선택지도 같다. 안내 문구("연결 상태를 확인해 주세요")에는 [새 대화]로 벗어나라는 말이 없다.
- #249 이전에는 끊긴 피보호자가 선택 칸에서 빠지고 대화가 바뀌어 저절로 풀렸다 - 이번 변경으로 생긴 막힘(드묾, 데이터 노출 없음).
- 수정 제안: 응답 `code === 'CHAT_WARD_NOT_CONNECTED'`이고 그 요청에 wardId가 있었으면, 실패 안내를 "…예약을 이어갈 수 없어요. [새 대화]로 다시 시작해 주세요."로 바꾸고 이어 싣기를 끊는다(실패 안내에 끊김 표시를 두고 `textWardId`·패널이 그 뒤로는 싣지 않게). 테스트: 403 뒤 다음 글 입력의 context에 wardId 없음.

### 🟡 M-2 한 대화창에서 두 피보호자를 예약하면 기록이 첫 피보호자로만 묶인다
- `targetOf`가 첫 피보호자 ID만 쓴다. 같은 대화에서 A 예약을 마친 뒤 다시 예약을 시작해 B를 고르면(AI가 다시 묻는다) 표시는 "A 님 예약", B 칩 필터에는 이 대화가 안 나온다 - 실제 기록이 필터에서 숨는다.
- 수정 제안: 세션에 `wardIds: string[]`(등장 순서·중복 제거)를 두고 필터는 포함 여부로, 표시는 "A 님 예약 외 1명". 테스트: 두 피보호자 섞인 세션이 두 칩 모두에서 보임.

### 🟢 L-1 예약 흐름 답 뒤의 빠른 질문 칩도 wardId를 싣는다
- 계약 ③의 "글 입력" 규칙과 같다(칩 = 글). 예약 진행 중에는 칩 줄이 패널로 바뀌어 보이지 않고, `ui` 없는 예약 답(목록 결과 등) 뒤에만 해당 - 의도된 동작으로 기록만.

### 🟢 L-2 지난 답의 카드 버튼 출처 판정이 테스트로 고정되지 않았다
- 말풍선마다 그 답을 출처로 넘긴다(코드상 맞음). 본인 답 카드와 대리 답 카드가 섞인 대화에서 각각 자기 요청 wardId를 싣는지 브라우저 테스트가 없다(`ChatToolCard`를 목으로 둔다).

### 🟢 L-3 대상 질문 뒤 10분 넘게 지나 복원되면 선택지가 사라진다
- 저장 10분 뒤 `ui`를 지우고 복원한다. 다시 예약을 말하면 AI가 다시 묻는다(AI도 30분 뒤 질문을 "지남"으로 처리) - 막힘 없음, 기록만.

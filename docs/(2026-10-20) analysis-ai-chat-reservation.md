## 2. 현재 구조

```
FE → BE POST /api/{guardian|ward}/chat (userId는 토큰으로 덮어씀, context는 그대로 전달)
   → AI POST /api/v1/chat (ChatService.process_message)
       ① "무슨 과?" 규칙 답변
       ② Claude 라우터(CLAUDE_MODEL_NAME = claude-opus-5-5) → reservation | symptom | general
          실패하면 키워드 분류
       ③ _force_emergency: 응급 키워드가 있으면 무조건 symptom + 119 안내   ← 미커밋 변경
       ├ symptom/general → MedGemma 1.5 4B (로컬 GPU, RTX 4070 SUPER 12GB를 감지 모델과 공유)
       │                   실패하면 ChatSilverBridge(:6012) 업스트림 → 그래도 실패하면 키워드 고정 문구
       └ reservation   → 예약 계정 확보(ensure_credential) → ReservationOrchestrator
                          (정규식 초안 + Claude 추출 → 병원 검색 → 진료과 → 날짜 → 시간 → 바로 예약 생성)
                          → 예약 서비스(:6015, SQLite, 가짜 병원 46곳)
   → chat_logs 저장 (AI Postgres)
```

#### 처리 상태 (2026-10-22, AI 서버 PR #25·#26, gosky 반영 `298b3e2`)

| # | 상태 | 처리 내용 |
|---|---|---|
| R-1 | ✅ | 예약 생성 전 확인 카드(환자·병원·진료과·날짜·시간·가린 연락처) + [예약하기 / 고치기]. 생성은 "예약하기" 뒤에만 호출한다. 고치기는 병원·진료과·날짜·시간 중 하나만 다시 묻는다. 버튼 입력 대신 "네"를 직접 쳐도 카드가 다시 뜰 뿐 예약되지 않는다 |
| R-2 | ✅ | 추출 프롬프트가 날짜 미입력을 빈 값으로 두고 서버가 날짜를 묻는다. 새 예약 요청은 지난 요청·이력 안내 문구("오늘은 …")의 날짜를 이어받지 않는다 |

- **확인 우회 방지**: 버튼 값에는 토큰만 싣고 초안은 서버가 저장한다. 토큰·세션·wardId가 직전 턴과 같을 때만 실행하고, 그 사이 다른 대화(응급 문장 포함)가 끼면 만료된다. 스키마 변경 없음.

- **검증**: pytest 337건 통과(변이 3종 - 확인 없이 생성·토큰 검사 제거·변경 시 취소 선행 - 이 모두 테스트에서 실패함을 확인). gosky 실서버에서 가상 계정으로 확인 카드 → 예약 → 취소까지 한 바퀴 확인했고 가상 계정의 챗 기록·예약 키는 지웠다.
- **알려진 한계**: 변경 흐름에서 새 예약은 됐는데 기존 예약 취소가 실패하면 예약이 두 개 남는다(안내 후 취소 재시도를 제안한다). "예약 시간 바꿔줘"처럼 예약 중에 한 말도 변경 요청으로 읽힐 수 있어 목록에 "그만두기"를 둔다. 시험으로 만든 가상 계정은 예약 서비스에 남는다(삭제 API 없음).

  SilverBridge AI 서버 프로젝트 설명서
================================================================================

  작성 기준일 : 2026-05-28
  대상 저장소 : SilverBridgeAiServer (백엔드 SilverBridgeBe와는 별도 저장소)
  문서 목적   : AI 서버를 처음 접하는 팀원/연동 담당자가 구조와 API를
                빠르게 이해하고 바로 붙일 수 있도록 정리.

  ※ 이 문서는 PRD(요구사항)가 아니라 "현재 구현된 코드"를 기준으로 작성했습니다.
     요구사항 전체는 저장소 루트의 PRD 파일을 참고하세요. 둘이 다를 경우
     이 문서가 실제 동작 기준입니다(MVP 단계라 PRD보다 단순한 부분이 있음).


--------------------------------------------------------------------------------
  1. 이 프로젝트는 무엇인가요?
--------------------------------------------------------------------------------

SilverBridge는 노인(피보호자)과 그 가족(보호자)을 연결하는 돌봄 서비스입니다.
그중 "AI 서버"는 SilverBridge 생태계에서 AI 기능만 독립적으로 담당하는
별도 서버 프로그램입니다.

  [전체 시스템에서의 위치]
    보호자 앱 / 피보호자 앱  ─(REST/Socket)→  API 서버(SilverBridgeBe)
    API 서버                 ─(REST)────────→  AI 서버(이 저장소)
    카메라(RTSP/MJPEG/DroidCam) ──(스트림)───→  AI 서버
    AI 서버                  ─(저장)────────→  DB (모델/카메라/분석결과/챗로그)

  즉 AI 서버는 사용자 앱과 직접 통신하지 않습니다.
  "API 서버가 AI 서버의 고객"이고, AI 서버는 분석/응답 생성만 책임지는
  내부 전문 서비스입니다.

  [AI 서버가 하는 일]
    - 미리 학습된 AI 모델의 메타데이터 등록/관리/활성화/비활성화
    - 카메라(스트림) 등록/관리/연결 테스트
    - 단일 이미지 분석 / 실시간 스트림 분석(시작·중지·상태·결과 조회)
    - 의료 챗(증상 기반 위험도 분류 + 권장 행동) 및 챗 로그 저장
    - 위 기능을 REST API + Swagger 문서로 API 서버에 제공

  [AI 서버가 하지 않는 일 — 책임 분리]
    - 보호자/피보호자 앱 직접 연동
    - Socket 실시간 브로드캐스트, 알림톡/SMS/전화/푸시 발송
    - 사용자 인증·인가 전체 책임 (AI 서버는 API Key 한 겹만 검사)
    - 분석 결과를 보호자에게 전달하는 로직 (그건 API 서버 몫)

  ★ 현재 단계 안내 (중요)
    이 서버는 MVP(최소 동작 버전)입니다. 구조(파이프라인, API, DB, 인증)는
    완성되어 있으나, 실제 딥러닝 추론과 LLM 응답은 아직 "모의(스텁)" 상태입니다.
      - 영상 분석: ultralytics/torch로 진짜 추론하지 않고, 프레임 수신 여부에
        따라 가짜 confidence(0.8/0.0)와 모델 타입 기반 결과를 돌려줍니다.
      - 의료 챗: medgemma 등 LLM을 호출하지 않고, 키워드 규칙으로 위험도를
        분류해 정해진 안내 문구를 돌려줍니다.
    → 연동/시연은 가능하되, "탐지 정확도"는 아직 의미가 없습니다. 추론 엔진
       교체 지점은 5절(분석)·6절(챗)의 ※ 표시를 참고하세요.


--------------------------------------------------------------------------------
  2. 사용하는 기술 (비유로 이해하기)
--------------------------------------------------------------------------------

  Python 3.11        : 서버를 만드는 프로그래밍 언어.

  FastAPI            : 파이썬 웹 API 프레임워크. "프레임워크"는 건물의 철골
                       구조처럼 기본 틀을 제공합니다. URL 요청을 받아 처리하고
                       JSON으로 응답합니다. 코드만 적으면 Swagger 문서가
                       자동 생성됩니다.

  Uvicorn            : FastAPI 앱을 실제로 띄워주는 실행기(ASGI 서버).
                       포트 9000에서 요청을 받습니다.

  SQLAlchemy         : 파이썬 코드(클래스)와 DB 테이블을 연결해 주는 도구(ORM).
                       SQL을 직접 쓰지 않고 객체로 데이터를 다룹니다.

  SQLite             : 파일 하나로 동작하는 가벼운 데이터베이스(기본값:
                       data/ai_server.db). 엑셀 표처럼 행/열로 데이터를 관리.
                       운영에서는 DATABASE_URL만 바꾸면 PostgreSQL로 교체 가능.

  Pydantic           : 들어온 요청 JSON의 형식/값을 검증하는 도구.
                       예) threshold는 0.0~1.0, type은 정해진 값만 허용.

  OpenCV (cv2)       : 카메라 스트림을 열고 프레임(사진 한 장)을 읽는 영상 처리
                       라이브러리. opencv-python-headless(화면 없는 서버용)를 사용.

  ultralytics / torch / transformers
                     : 딥러닝 추론용 라이브러리(YOLO, PyTorch, HuggingFace).
                       의존성에는 포함돼 있으나 현재 코드에서는 아직 호출하지
                       않습니다(추론은 스텁). 실제 모델 연결 시 사용할 예정.

  API Key            : API 서버만 호출할 수 있도록 하는 "공용 비밀번호".
                       모든 보호된 요청 헤더에 X-API-Key를 넣어 신원을 증명합니다.
                       (JWT 같은 사용자별 토큰이 아니라 서버 간 단일 키)

  Docker             : 서버 프로그램을 "컨테이너"라는 독립 환경에 담아 실행.
                       어느 서버에서든 동일하게 동작하도록 포장해줍니다.

  Swagger / OpenAPI  : FastAPI가 자동 생성하는 API 명세서.
                       /docs (Swagger UI), /redoc (ReDoc), /openapi.json


--------------------------------------------------------------------------------
  3. 인증 방식 (X-API-Key)
--------------------------------------------------------------------------------

  AI 서버는 사용자 로그인 개념이 없습니다. "API 서버가 호출하는가"만 확인합니다.

  - 보호된 모든 API는 요청 헤더에 다음을 넣어야 합니다.
        X-API-Key: {API_KEY}
    (.env의 API_KEY 값과 정확히 일치해야 함. 기본 예시값은 change-me)

  - 키가 없거나 틀리면 401을 반환합니다.
        { "success": false, "message": "유효하지 않은 API Key 입니다.",
          "errorCode": "AUTH_INVALID_KEY", "data": null }

  - 인증 불필요(공개) 엔드포인트
        GET /health   ← 헬스체크만 키 없이 호출 가능
    그 외 /api/v1/** (모델·카메라·분석·챗) 전부 X-API-Key 필수.

  ※ CORS는 현재 모든 origin 허용(allow_origins=["*"]). AI 서버는 브라우저가
    아니라 API 서버가 호출하는 내부 서비스라는 전제. 외부 노출 시 좁혀야 함.


--------------------------------------------------------------------------------
  4. 주요 기능과 API 흐름
--------------------------------------------------------------------------------

  ★ API란?
  API 서버가 AI 서버의 특정 주소(URL)로 요청을 보내는 것입니다.
    - GET    : 데이터 조회 (읽기)
    - POST   : 데이터 생성 또는 특정 동작 실행
    - PATCH  : 데이터 일부 수정
    - DELETE : 데이터 삭제(또는 비활성화)

  ★ 명명 규칙 (중요)
    - 요청/응답 JSON 필드는 camelCase  (예: modelNo, streamUrl, isActive)
    - DB 컬럼은 snake_case            (예: model_no, stream_url, is_active)
    서비스 계층에서 둘을 자동 변환합니다. 연동 시에는 camelCase를 씁니다.

  ★ 기본 경로 : /api/v1
  ★ 기본 포트 : 9000


  [ 4-1. Health (서버 상태 확인) ]
  ─────────────────────────────
    → GET /health        (인증 불필요)
    → 응답 data: { "status": "ok", "timestamp": "2026-05-28T..." }
    Docker/로드밸런서 헬스체크, 배포 직후 기동 확인용.


  [ 4-2. 모델 관리 (Model CRUD) ]
  ─────────────────────────────
  "미리 학습된 모델"의 메타데이터(이름/타입/파일경로/임계값 등)를 관리합니다.
  실제 모델 파일(.pt 등)은 DB에 넣지 않고 file_path(경로)만 저장합니다.

    POST   /api/v1/models                          → 모델 등록
    GET    /api/v1/models                          → 모델 목록 (최신순)
    GET    /api/v1/models/{id}                     → id(PK) 기준 상세
    GET    /api/v1/models/by-identifier/{identifier} → identifier 기준 조회
    GET    /api/v1/models/by-model-no/{model_no}   → modelNo 기준 조회
    PATCH  /api/v1/models/{id}                     → 모델 수정(부분)
    DELETE /api/v1/models/{id}                     → 비활성화(소프트 삭제, isActive=false)
    PATCH  /api/v1/models/{id}/activate            → 다시 활성화(isActive=true)

  ▶ 등록 요청(camelCase) 필드
      modelNo*(고유), identifier*(고유), name, type*, filePath, framework*,
      version("v1"), description(""), threshold(0.75, 0~1), isActive(true)
      * = 필수

  ▶ type 허용값      : fall_detection / fire_detection / weapon_detection /
                       medical_chat / custom
  ▶ framework 허용값 : ultralytics / pytorch / onnx / transformers / custom

  ※ 등록 시 identifier 또는 modelNo가 이미 있으면 409 MODEL_ALREADY_EXISTS.
  ※ DELETE는 실제 행 삭제가 아니라 isActive=false 처리(데이터 보존).
  ※ "활성 모델은 타입당 하나만" 같은 제약은 아직 없습니다(정책 미구현).
    여러 모델이 동시에 활성일 수 있습니다.


  [ 4-3. 카메라 관리 (Camera CRUD) ]
  ─────────────────────────────
  분석 대상 카메라(스트림)를 등록/관리합니다.

    POST   /api/v1/cameras                            → 카메라 등록
    GET    /api/v1/cameras                            → 카메라 목록 (최신순)
    GET    /api/v1/cameras/{id}                       → id 기준 상세
    GET    /api/v1/cameras/by-identifier/{identifier} → identifier 기준 조회
    PATCH  /api/v1/cameras/{id}                       → 카메라 수정(부분)
    DELETE /api/v1/cameras/{id}                       → 비활성화(소프트 삭제)
    POST   /api/v1/cameras/{id}/test-connection       → 연결 테스트

  ▶ 등록 요청(camelCase) 필드
      cameraNo*(고유), identifier*(고유), name, streamUrl*, streamType*,
      targetUserId(""), guardianUserId(""), locationName(""), isActive(true)

  ▶ streamType 허용값 : rtsp / http_mjpeg / droidcam
  ▶ targetUserId / guardianUserId : API 서버 쪽 피보호자/보호자 식별자를
                                     문자열로 보관(연동 편의용, AI 서버는 검증 안 함)

  ※ streamUrl 형식 검증: scheme가 rtsp/http/https 이고 호스트가 있어야 통과.
    형식이 틀리면 400 CAMERA_STREAM_INVALID.
  ※ test-connection은 현재 "URL 형식이 유효한가"만 확인합니다(빠른 검증).
    실제로 스트림을 열어 프레임을 받아보지는 않습니다. 형식이 맞으면
    { cameraIdentifier, connected: true } 반환. (PRD의 "실제 프레임 수신
    확인"은 향후 고도화 항목)
  ※ 등록 중복 검사는 identifier 기준만 수행합니다.


  [ 4-4. 영상 분석 (Analysis) ]
  ─────────────────────────────
  단일 이미지 1장 분석, 또는 카메라 스트림을 백그라운드로 계속 분석합니다.

    POST /api/v1/analysis/image                  → 단일 이미지 분석(즉시 1회)
    POST /api/v1/analysis/start                  → 스트림 분석 시작(백그라운드)
    POST /api/v1/analysis/stop                   → 스트림 분석 중지
    GET  /api/v1/analysis/status/{cameraIdentifier} → 해당 카메라 분석 중 여부
    GET  /api/v1/analysis/latest/{cameraIdentifier} → 해당 카메라 최신 결과 1건
    GET  /api/v1/analysis/results                → 결과 목록(필터 가능)
    GET  /api/v1/analysis/results/{id}           → 결과 상세 1건

  ▶ 단일 이미지 분석 (POST /analysis/image)
      body: { cameraIdentifier*, modelIdentifier*, imagePath? }
      흐름:
        1) cameraIdentifier로 카메라, modelIdentifier로 모델 조회
           (없으면 404 CAMERA_NOT_FOUND / MODEL_NOT_FOUND)
        2) imagePath가 있고 실제 파일이 존재하면 그 이미지를 사용
           아니면 OpenCV로 카메라 streamUrl을 열어 프레임 1장 캡처 →
           스냅샷(.jpg) 저장
        3) 분석 결과를 analysis_results에 저장하고 결과 반환

  ▶ 스트림 분석 시작/중지 (POST /analysis/start, /stop)
      body: { cameraIdentifier*, modelIdentifier* }
      - start: 백그라운드 스레드(daemon)를 띄워 카메라 스트림을 계속 읽습니다.
        STREAM_SAMPLE_EVERY_N_FRAMES(기본 15) 프레임마다 1번 분석하고,
        매 루프 사이 STREAM_FALLBACK_INTERVAL_SEC(기본 2초) 쉽니다.
        분석할 때마다 결과를 DB에 저장(프레임 있으면 스냅샷도 저장).
      - 이미 같은 카메라가 돌고 있으면 새로 시작하지 않고 running:true 반환.
      - stop: 해당 카메라 워커에 중지 신호를 보냄. 워커가 없으면
        404 ANALYSIS_NOT_RUNNING.
      ※ 워커 상태는 서버 메모리(프로세스 내 dict)에 보관됩니다. 서버를
        재시작하면 진행 중 세션 정보는 사라집니다(분석 결과 행은 DB에 남음).

  ▶ 결과 목록 필터 (GET /analysis/results)
      쿼리: cameraIdentifier / startAt / endAt (ISO8601, 예 2026-05-28T09:00:00)
      analyzed_at 기간 + 카메라로 필터, 최신순 정렬.

  ▶ 위험 판정 규칙 (DetectionService — 현재 스텁)
      - confidence    : 프레임을 받았으면 0.8, 못 받았으면 0.0 (고정 모의값)
      - detectedType  : 모델 type에 따라 매핑
                          fall_detection   → fall
                          fire_detection   → fire
                          weapon_detection → weapon
                          그 외            → normal
                          프레임 못 받음   → unknown
      - danger        : confidence >= 모델.threshold 이고
                        detectedType이 normal/unknown이 아니면 true
      ※ 여기가 "진짜 추론"으로 교체할 지점입니다. 현재는 실제 영상 내용과
        무관하게 위 규칙으로만 결과를 만듭니다.


  [ 4-5. 의료 챗 (Chat) ]
  ─────────────────────────────
  사용자가 보낸 증상 메시지를 기반으로 위험도와 권장 행동을 돌려줍니다.
  기존 ChatSilverBridge의 "안전한 의료 안내" 방향을 통합한 MVP입니다.

    POST /api/v1/chat              → 의료 챗 요청(응답 생성 + 로그 저장)
    GET  /api/v1/chat/logs         → 챗 로그 목록 (최신순)
    GET  /api/v1/chat/logs/{id}    → 챗 로그 상세

  ▶ 요청 (POST /chat)
      body: {
        userId*: int,
        message*: "어지럽고 숨이 차요",
        context?: { age?, gender?, guardianId? }
      }
  ▶ 응답 data
      { reply, riskLevel, recommendedAction, reservationRequired,
        intent, chatLogId, chatNo }

  ▶ 분류 로직 (ChatService — 현재 키워드 규칙 기반, LLM 미호출)
      - intent (의도)
          emergency_guidance   : "호흡곤란","가슴 통증","의식 없음","쓰러짐" 등
          hospital_reservation : "예약","근처 병원","응급실" 등
          medical_advice       : "어지럽","복통","발열","두통" 등 중위험 키워드
          general_chat         : 위 어디에도 안 걸림
      - riskLevel / recommendedAction / reservationRequired
          high   → hospital_visit    / reservationRequired=true
                   (응급 키워드 또는 가슴·호흡·의식·출혈·마비 등 고위험)
          medium → guardian_contact  / reservationRequired=false
                   (예약/조언 의도 또는 중위험 키워드)
          low    → home_monitoring   / reservationRequired=false
      - reply : 위험도별 정해진 안내 문구. 모든 답변에 "정확한 진단·치료는
                의료진 상담이 필요합니다"라는 안전 고지 문구가 포함됩니다.
      ※ PRD의 critical / emergency_call 단계는 아직 코드에 없습니다(low/medium/high).
      ※ 여기가 실제 의료 LLM(medgemma 등)으로 교체할 지점입니다.


--------------------------------------------------------------------------------
  5. 표준 응답 형식
--------------------------------------------------------------------------------

  모든 응답은 동일한 포맷을 유지합니다. API 서버는 success / errorCode만으로
  분기 처리할 수 있습니다.

  [성공]
    {
      "success": true,
      "message": "요청 처리 완료",
      "data": { ... }            ← 없으면 {} 로 채워짐
    }

  [실패]
    {
      "success": false,
      "message": "사람이 읽는 에러 메시지",
      "errorCode": "MACHINE_CODE",
      "data": null
    }

  ▶ 주요 errorCode
      AUTH_INVALID_KEY        API Key 누락/불일치 (401)
      MODEL_NOT_FOUND         모델 없음 (404)
      MODEL_ALREADY_EXISTS    모델 중복 등록 (409)
      CAMERA_NOT_FOUND        카메라 없음 (404)
      CAMERA_ALREADY_EXISTS   카메라 중복 등록 (409)
      CAMERA_STREAM_INVALID   streamUrl 형식 오류 / 연결 실패 (400)
      ANALYSIS_NOT_RUNNING    중지할 분석 세션 없음 (404)
      ANALYSIS_NOT_FOUND      분석 결과 없음 (404)
      CHAT_LOG_NOT_FOUND      챗 로그 없음 (404)
      HTTP_ERROR              그 외 HTTP 예외 공통 변환

  ※ FastAPI/Pydantic 검증 실패(필수 필드 누락, 타입 오류 등)는 FastAPI
    기본 422 응답(detail 배열)으로 나갑니다. 위 표준 포맷과 형태가 다릅니다.


--------------------------------------------------------------------------------
  6. 데이터베이스 테이블 및 컬럼 설명
--------------------------------------------------------------------------------

  ※ 기본 DB는 SQLite(data/ai_server.db). 서버 시작 시 테이블이 없으면
     자동 생성됩니다(SQLAlchemy create_all). 별도 마이그레이션 도구는 없습니다.
  ※ 모든 시간 컬럼은 UTC 기준 datetime으로 저장됩니다.
  ※ DB 컬럼은 snake_case, API 필드는 camelCase (4절 명명 규칙 참고).


  [ ai_models — 등록된 AI 모델 메타데이터 ]
  ─────────────────────────────
  id           : 내부 PK (정수, 자동 증가)
  model_no     : 외부 연동용 모델 번호 (중복 불가)
  identifier   : 고유 식별자 (중복 불가, API 서버가 모델 지정 시 사용)
  name         : 모델명
  type         : 모델 유형 (fall_detection / fire_detection / weapon_detection /
                 medical_chat / custom)
  file_path    : 실제 모델 파일 경로 (바이너리는 DB에 저장하지 않음)
  framework    : 프레임워크 (ultralytics / pytorch / onnx / transformers / custom)
  version      : 버전 (기본 "v1")
  description  : 설명
  threshold    : 위험 감지 임계값 0.0~1.0 (기본 0.75)
  is_active    : 활성 여부 (DELETE는 이 값을 false로 — 소프트 삭제)
  created_at   : 등록 일시
  updated_at   : 수정 일시 (수정 시 자동 갱신)


  [ cameras — 분석 대상 카메라 ]
  ─────────────────────────────
  id               : 내부 PK
  camera_no        : 카메라 번호 (중복 불가)
  identifier       : 고유 식별자 (중복 불가)
  name             : 카메라명
  stream_url       : 스트림 주소 (rtsp:// 또는 http(s)://)
  stream_type      : rtsp / http_mjpeg / droidcam
  target_user_id   : 피보호자 식별자(문자열, API 서버 쪽 값 보관용)
  guardian_user_id : 보호자 식별자(문자열, 보관용)
  location_name    : 설치 위치명 (예: "거실")
  is_active        : 활성 여부 (소프트 삭제)
  created_at       : 등록 일시
  updated_at       : 수정 일시 (자동 갱신)


  [ analysis_results — 분석 결과 ]
  ─────────────────────────────
  id                : 내부 PK
  analysis_no       : 분석 고유 번호 (예: ANL-xxxxxxxxxxxx, 중복 불가)
  camera_id         : 카메라 PK (FK → cameras.id)
  camera_identifier : 카메라 식별자 (조회 편의용 사본)
  model_id          : 모델 PK (FK → ai_models.id)
  model_identifier  : 모델 식별자 (사본)
  detected_type     : 감지 결과 (fall / fire / weapon / normal / unknown)
  confidence        : 신뢰도 0.0~1.0
  danger            : 위험 여부 (true/false)
  snapshot_path     : 분석 시점 스냅샷 이미지 경로 (없으면 빈 문자열)
  raw_result_json   : 원본 추론 결과 JSON 문자열 (확장용 보관)
  analyzed_at       : 분석 수행 시각 (목록 필터 기준)
  created_at        : 행 생성 시각


  [ chat_logs — 의료 챗 기록 ]
  ─────────────────────────────
  id                  : 내부 PK
  chat_no             : 챗 고유 번호 (예: CHAT-xxxxxxxxxxxx, 중복 불가)
  user_id             : 사용자 ID (정수)
  message             : 사용자가 보낸 증상 메시지
  context_json        : 요청 context(age/gender/guardianId) JSON 문자열
  reply               : 생성된 응답 문구
  risk_level          : low / medium / high
  recommended_action  : home_monitoring / guardian_contact / hospital_visit
  reservation_required: 예약 권유 여부 (true/false)
  created_at          : 기록 일시


--------------------------------------------------------------------------------
  7. 보안 정책 요약
--------------------------------------------------------------------------------

  [ 인증 ]
  - 서버 간 단일 API Key 방식. 헤더 X-API-Key가 .env의 API_KEY와 일치해야 함.
  - /health 만 공개, 나머지 /api/v1/** 전부 키 필수. 불일치 시 401.
  - 사용자별 인증(JWT 등)은 AI 서버 책임이 아님 — API 서버가 담당.

  [ 입력 검증 ]
  - Pydantic으로 요청 형식/범위 검증 (예: threshold 0~1, type/streamType는
    정해진 값만 허용).
  - streamUrl은 scheme(rtsp/http/https) + 호스트 존재 여부를 검증.

  [ 데이터 노출 ]
  - 모델/업로드/스냅샷 경로는 .env로 관리하며 응답에 파일 자체를 내보내지 않음.
  - 민감 설정(API_KEY, HF_TOKEN 등)은 .env로만 주입(코드/Git 비노출, .gitignore에 .env).

  [ 예외 처리 ]
  - HTTPException은 공통 핸들러가 표준 응답 포맷으로 변환.
  - 서비스 계층에서 발생한 도메인 오류는 errorCode와 한국어 메시지를 함께 반환.

  [ 현재 한계 (의도된 MVP 범위) ]
  - CORS allow_origins=["*"] (모든 출처 허용) — 외부 직접 노출 시 좁혀야 함.
  - API Key는 단일 평문 키(회전·만료 없음). 내부망 + API 서버 전용 호출 전제.
  - 요청 속도 제한(rate limit), HTTPS 강제, 보안 헤더 등은 아직 없음.


--------------------------------------------------------------------------------
  8. 환경변수 (.env)
--------------------------------------------------------------------------------

  .env.example을 복사해 .env로 만들어 사용합니다. 주요 값:

  [ 앱 기본 ]
    APP_NAME      앱 이름 (Swagger 제목)        기본 "SilverBridge AI Server"
    APP_ENV       실행 환경                      기본 development
    APP_VERSION   버전                           기본 0.1.0
    APP_PORT      포트                           기본 9000
    LOG_LEVEL     로그 레벨(INFO/DEBUG 등)       기본 INFO

  [ DB / 인증 ]
    DATABASE_URL  DB 접속 URL   기본 sqlite:///./data/ai_server.db
                  (PostgreSQL 예: postgresql+psycopg://user:pw@host:5432/db)
    API_KEY       서버 간 인증 키 (반드시 운영용으로 교체! 기본 change-me)

  [ 파일 경로 ]
    MODEL_BASE_PATH     모델 파일 루트          기본 /app/models
    UPLOAD_BASE_PATH    업로드 루트             기본 /app/uploads
    SNAPSHOT_BASE_PATH  스냅샷 저장 루트        기본 /app/uploads/snapshots

  [ 챗 모델 ]
    DEFAULT_CHAT_MODEL  기본 챗 모델 식별자     기본 google/medgemma-1.5-4b-it
    CHAT_MODEL_PATH     로컬 모델 경로(선택)
    HF_TOKEN            HuggingFace 토큰(선택)
    ※ 현재 챗은 키워드 규칙이라 위 값들은 아직 실제로 사용되지 않음(향후용).

  [ 분석 튜닝 ]
    DEFAULT_DETECTION_THRESHOLD   기본 위험 임계값          기본 0.75
    STREAM_SAMPLE_EVERY_N_FRAMES  스트림 N프레임마다 분석   기본 15
    STREAM_FALLBACK_INTERVAL_SEC  스트림 루프 간 대기(초)   기본 2
    SAVE_NORMAL_RESULTS           정상 결과도 저장할지       기본 true

  [ 문서 경로 ]
    DOCS_PATH / OPENAPI_PATH / REDOC_PATH   기본 /docs, /openapi.json, /redoc


--------------------------------------------------------------------------------
  9. 실행 방법
--------------------------------------------------------------------------------

  [ A. 로컬 실행 ]
    1) 가상환경 + 의존성 설치
         python -m venv .venv
         source .venv/bin/activate
         pip install -r requirements.txt
    2) 환경변수 준비
         cp .env.example .env       # API_KEY 등 필요한 값 수정
    3) 서버 실행
         uvicorn app.main:app --host 0.0.0.0 --port 9000 --reload
    4) 확인
         http://localhost:9000/health
         http://localhost:9000/docs   (Swagger UI)

  [ B. Docker 실행 ]
    1) cp .env.example .env
    2) docker compose up --build
       - 컨테이너명 silverbridge-ai-server, 포트 9000 노출
       - 볼륨 마운트: ./models, ./uploads, ./logs, ./data
         → 컨테이너 재시작 후에도 모델/업로드/로그/DB 보존
       - restart: unless-stopped (비정상 종료 시 자동 재시작)

  ※ requirements.txt에 torch/ultralytics/transformers가 포함돼 첫 설치/빌드는
    용량이 크고 시간이 걸립니다(수백 MB~수 GB). 추론 미사용 단계라면 향후
    경량화 여지가 있습니다.

  10. 폴더 구조
--------------------------------------------------------------------------------

  app/
  ├── main.py                  FastAPI 앱 생성, lifespan(테이블·디렉토리 생성),
  │                            CORS, 공통 예외 핸들러, 라우터 등록(인증 의존성 부착)
  ├── core/

  │   ├── security.py          require_api_key (X-API-Key 검사 의존성)
  │   └── response.py          success_response / error_response (표준 포맷)
  ├── database/
  │   ├── base.py              SQLAlchemy DeclarativeBase
  │   └── session.py           engine / SessionLocal / get_db (요청별 세션)
  ├── models/                  DB 테이블(엔티티)
  │   ├── ai_model.py          ai_models
  │   ├── camera.py            cameras
  │   ├── analysis_result.py   analysis_results
  │   └── chat_log.py          chat_logs
  ├── schemas/                 요청/응답 Pydantic 모델(camelCase)
  │   ├── ai_model_schema.py / camera_schema.py / analysis_schema.py
  │   ├── chat_schema.py
  │   └── common.py            StandardResponse
  ├── routers/                 API 엔드포인트(요청/응답만 담당)
  │   ├── health_router.py     /health
  │   ├── model_router.py      /api/v1/models
  │   ├── camera_router.py     /api/v1/cameras
  │   ├── analysis_router.py   /api/v1/analysis
  │   └── chat_router.py       /api/v1/chat
  ├── services/                실제 비즈니스 로직(핵심 두뇌)
  │   ├── model_service.py     모델 CRUD
  │   ├── camera_service.py    카메라 CRUD + streamUrl 검증
  │   ├── detection_service.py 프레임 → 분석 결과(현재 스텁)
  │   ├── stream_service.py    백그라운드 스트림 워커 매니저(스레드)
  │   └── chat_service.py      증상 분류 + 응답 생성 + 로그 저장
  └── utils/
      ├── file_utils.py        디렉토리 생성, 스냅샷 경로 생성
      └── logger.py            로깅 설정

  (런타임 생성 폴더) models/ uploads/ uploads/snapshots/ logs/ data/

  계층 원칙:
    router  → 요청을 받고 service에 위임, 결과를 표준 응답으로 포장
    service → 실제 로직과 DB 작업
    model   → DB 테이블 구조
    schema  → API 입출력 형식/검증

## 이슈

### 🟠 H-1. 로그인·갱신·로그아웃이 커넥션 2개를 겹쳐 쥔다 - 동시 10건이면 DB 풀이 30초 멈춘다

- 위치: `AuthService.java:132`(login, `@Transactional`) → `:196` `accessLogService.log(...)` / 같은 형태로 logout `:214·224`, refresh `:233·272·334` / `AccessLogService.java:29-33`(`PROPAGATION_REQUIRES_NEW`). 커넥션 풀 설정이 `application.yaml`·compose·서버 환경변수 어디에도 없어 HikariCP 기본 10개다(gosky dev 컨테이너에 HIKARI 환경변수 0건 확인).
- 구조: 바깥 트랜잭션이 커넥션 1개를 쥔 채(로그인은 그 안에서 BCrypt 강도 12 비교까지 한다) 접속 로그가 **두 번째 커넥션**을 요구한다. 요청 10건이 동시에 바깥 트랜잭션에 들어가면 10개가 모두 소진된 상태에서 전원이 두 번째를 기다려 아무도 반납하지 못한다.
- 재현 경로: 정상 계정 하나로 `POST /api/auth/signin` 10건을 동시에 보낸다(IP당 분 10회 제한 안, IP를 나누면 그 이상). 10건이 모두 BCrypt 구간에 있는 수백 ms 사이에 풀이 비고, 접속 로그 쪽이 커넥션 대기 30초(HikariCP 기본) 뒤 실패해 `[ACCESS-LOG-FAILED]`로 버려진 다음에야 로그인이 끝난다. 그 30초 동안 **DB를 쓰는 모든 요청**(`POST /api/ward/sos` 포함)이 커넥션을 기다리고, 줄이 길면 30초 뒤 오류로 끝난다. 반복할 수 있다. 공격이 아니어도 시연처럼 여러 명이 같은 순간 로그인하면 같은 일이 난다.
- 한계: 실서버에서 재현하지 않았다(운영 영향이 있는 시험이라). 구조와 설정값으로 판단했고, 수정 PR에서 실 DB 통합 테스트로 재현·고정한다.
- 과거 점검: 2026-09-22·09-30 점검은 탈퇴·알림 경로의 "순간 2개"만 보고 PASS로 뒀다(그 경로는 드물고 순차). 로그인 경로는 이번이 처음이다.
- 수정안: ① 로그인·갱신·로그아웃의 접속 로그를 카카오 가입처럼 **AFTER_COMMIT 이벤트**로 옮겨 바깥 커넥션을 반납한 뒤 기록한다(실패·롤백 경로에서 남겨야 하는 로그는 트랜잭션 밖에서 직접 호출). ② HikariCP 값을 명시한다(`maximum-pool-size`·`connection-timeout` 5초 안팎 - 30초 대기는 요청 스레드를 붙든다). ③ 재사용 감지의 세션 폐기(`:334`, REQUIRES_NEW)는 같은 문제가 있는지 함께 본다.

### 🟡 M-1. 컨테이너 종료 유예가 없어 우아한 종료가 10초에서 잘린다

- 위치: `docker-compose.dev.yml`·`docker-compose.gosky.yml`·`docker-compose.prod.yml`의 `api`에 `stop_grace_period` 없음(gosky `dmu-dev-api`의 StopTimeout 미설정 확인). `application.yaml:80` `server.shutdown: graceful`, `AsyncConfig`의 종료 대기 20초.
- 재현 경로: 배포(`up -d --build api`)로 컨테이너가 교체될 때 도커가 SIGTERM 뒤 **기본 10초**에 SIGKILL을 보낸다. 그 시점에 알림 executor 큐에 남아 있거나 발송 중(FCM·Solapi 최대 10초)이던 SOS·화재 알림, 진행 중이던 요청이 끊긴다. 정책 문서(B-3 "종료 대기 20초로 SOS 알림 유실 방지")의 보장이 절반만 성립한다.
- 수정안: 세 compose의 `api`에 `stop_grace_period: 40s`(종료 단계 30초 + 여유). 설정 변경이라 두 서버에서 `up -d`로 재생성해야 반영된다.

### 🟡 M-2. 카카오 로그인이 트랜잭션 안에서 카카오 API를 2번 부른다

- 위치: `KakaoAuthService.java:85-88`(`@Transactional` `kakaoLogin` → `getToken` → `getUserInfo`, 각 10초 제한).
- 재현 경로: 카카오 응답이 느려지면 카카오 로그인 1건이 DB 커넥션을 최대 약 20초 쥔다. 10건이 겹치면 풀(10)이 비어 H-1과 같은 정지가 난다(외부 장애가 우리 DB 가용성으로 번진다). 이 경로도 끝에서 접속 로그(REQUIRES_NEW)를 부른다.
- 수정안: 카카오 호출 2건을 트랜잭션 밖으로 빼고 DB 작업만 트랜잭션으로 묶는다(챗·OCR·STT가 이미 그렇게 한다). H-1과 같은 PR.

##### 잠금 순서
- 확립된 순서: **users → (connection) → anomaly_incident → camera**. 
  - `AnomalyClipService.record`: users(KEY SHARE) → incident(FOR UPDATE) → camera(KEY SHARE). 주석대로 탈퇴 purge와 같은 순서.
  - `submitFeedback`(GuardianAnomalyService:251)은 incident 잠금부터 시작해 users를 잠그지 않음. 이후 리뷰 행 INSERT의 FK 검사로 보호자 users에 KEY SHARE가 암묵적으로 걸리나, KEY SHARE끼리는 충돌하지 않고 충돌 상대(탈퇴 purge의 users DELETE)는 **다른 users 행**(보호자 vs 피보호자)을 잡으므로 교착 쌍을 만들지 못함. 순서는 비일관이나 충돌하는 잠금 쌍이 없음 = 후보 아님(근거 기록).
  - ConnectionService:117(users FOR SHARE) vs AdminUserService:146(users FOR NO KEY UPDATE): 충돌하는 쌍이나 한쪽이 상대 users 행을 추가로 요구하지 않음(요청 경로는 id 정렬 후 2행, 수정 경로는 1행). 이후 connection 행·camera 행 DELETE는 FK의 KEY SHARE만 users에 요구(FOR SHARE와 비충돌). 교착 후보 없음.
- 순서 뒤집힘이 확인된 두 경로 = **없음**.

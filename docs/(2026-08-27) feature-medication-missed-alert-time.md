# 미복용 요약 알림 시각 - 보호자 직접 선택 (2026-08-27)

> 복약 알림 3차(미복용 보호자 요약)의 발송 시각을 전역 고정값에서 **보호자별 설정**으로 바꾼다.
> 마이그레이션 **V40**. 기존 동작(21:00)은 미설정 보호자의 기본값으로 그대로 남는다.

## 1. 배경

3차 기능(2026-08-05)은 발송 시각이 `application.yaml`의 전역 값 하나였다.

```yaml
medication.reminder.missed-alert.alert-time: 21:00
```

모든 보호자가 같은 시각에 받았고, 바꾸려면 서버 환경변수를 고쳐야 했다. 생활 패턴이 제각각인데
"우리 집은 저녁 7시에 확인한다"를 반영할 수단이 없었다.

## 2. 확정된 동작

보호자가 시각을 지정하면 **그 시각이 발송 시각이자 집계 상한**이 된다.

예 - 피보호자의 약이 08:00 / 12:00 / 18:00 / 22:00에 등록돼 있을 때

| 보호자 지정 시각 | 집계 대상 | 발송 문구 |
|---|---|---|
| 21:00 (기본) | 08:00 · 12:00 · 18:00 (3건) | "김영희님의 **21:00까지 예정된** 복약 3건 중 2건이 아직 체크되지 않았습니다." |
| 19:00 | 08:00 · 12:00 · 18:00 (3건) | "…19:00까지 예정된 복약 3건 중…" |
| 12:00 | 08:00 · 12:00 (2건) | "…12:00까지 예정된 복약 2건 중…" |

- **지정 시각 이후에 먹는 약은 그날 요약에서 빠진다.** 아직 먹을 때가 아닌 약을 미복용으로 통보하면
  매일 거짓 알림이 되기 때문이다(불변 규칙 ⑧). 시각을 이르게 잡을수록 포함되는 약이 줄어드는 것은
  **의도된 동작**이며, Swagger 설명과 알림 본문 양쪽에 그 사실을 밝힌다.
- **입력은 분 단위 자유**(00:00~23:59). 스케줄러가 1분 주기라 분 단위까지 그대로 동작한다.
  초·나노는 저장 시 버린다(판정에 쓰이지 않으면서 조회 결과만 지저분해진다).
- **발송 창(120분)은 기준점만 보호자 시각으로 옮겼다.** 정상 상황에서는 지정 시각 정각에 나가고,
  서버가 내려가 있었을 때만 늦게라도 보낼지를 이 창이 결정한다(그 뒤로는 그날 건을 넘긴다).

## 3. 왜 "발송 시각 = 집계 상한"인가

세 안을 검토했다.

| 안 | 동작 | 판정 |
|---|---|---|
| **A. 연동 (채택)** | 지정 시각 = 집계 상한. 문구에 시각을 밝힌다 | 이른 시각을 고르면 이후 약이 그날 요약에서 빠지지만, **문구가 사실을 그대로 말한다** |
| B. 분리 | 발송 시각만 선택, 집계는 항상 21:00 기준 | ❌ 12:00에 "22:00 약 미체크"를 통보 = 매일 거짓 경보. 불변 규칙 ⑧이 막는 바로 그 케이스 |
| C. 하루 2회 | 이른 시각 + 21:00 두 번 | ❌ 하루 1건 규칙(⑨) 위반. 알림 피로로 보호자가 앱 알림을 통째로 끄면 SOS·이상감지까지 죽는다 |

## 4. 스키마 (V40)

```sql
ALTER TABLE guardian_medication_setting
    ADD COLUMN missed_alert_time TIME NULL;
```

`NULL` = 미설정 → 전역 기본값을 따른다. **NOT NULL DEFAULT '21:00'으로 박지 않은 이유** -
그러면 기존 보호자 전원이 21:00에 고정돼, 나중에 서버 기본값을 바꿔도 아무도 따라오지 않는다.
NULL로 두면 "정하지 않았다"와 "21:00을 골랐다"가 구분되고 백필도 필요 없다.

## 5. 집계 구조 변경 (핵심)

기존 Planner는 **"약 → 피보호자 집계 → 보호자"** 순서라 counts가 보호자와 무관하게 먼저 확정됐다.
보호자마다 상한이 다르면 같은 피보호자라도 분모가 달라지므로 이 순서를 유지할 수 없다.

```
[변경 전]  전역 alertTime으로 약 조회 → ward별 (전체, 미체크) 확정 → 보호자 붙이기
[변경 후]  현재 시각까지 약 조회(상위집합) → ward별 미체크 유무로 1차 필터
           → 보호자별 상한으로 다시 세기 → 선점
```

- **상위집합이 성립하는 근거**: 발송 창 안에 있는 보호자의 지정 시각은 언제나 현재 시각 이하다
  (`isWithinSendWindow`가 `now >= alertTime`을 요구). 따라서 `doseTime <= now`로 한 번 읽으면
  모든 보호자의 집계 대상을 포함한다.
- **1차 필터는 남겼다**: 상위집합에서 미체크가 하나도 없는 피보호자는 어떤 상한을 잡아도 대상이 아니므로,
  보호자 조회·설정 조회 전에 걸러 낸다(기존 최적화와 같은 자리).
- **이름 조회는 실제 발송 대상만**: 선점이 확정된 뒤에 `findAllById`를 호출한다.
  빈 결과에 `Map.of()`가 아니라 `Collections.emptyMap()`을 쓰는 이유는 SOS 이력의 NPE 전례와 같다.

### 매 분 전체 스캔 방지 게이트

보호자마다 시각이 달라 "아직 발송 시각 전"을 값 하나로 판단할 수 없다. 그대로 두면 스케줄러가
하루 종일 매 분 복약 테이블을 훑는다. 그래서 설정 테이블의 최이른·최늦은 시각과 전역 기본값으로
전체 구간을 먼저 잡고, 그 밖이면 **복약 테이블을 조회하지 않고 끝낸다**.

```java
earliest = min(기본 시각, MIN(missed_alert_time))   // 활성 보호자 기준
latest   = max(기본 시각, MAX(missed_alert_time))
now < earliest  또는  now > latest + 마감  →  즉시 종료
```

`MIN`/`MAX`는 NULL을 무시하므로 미설정 행은 자연히 빠지고, 그들이 쓰는 기본값은 항상 구간에 포함된다.

## 6. API 변경

`GET·PUT /api/guardian/medication-alert-setting` (보호자 전용, 축이 보호자 본인이라 wardId 없음)

```jsonc
// PUT 요청 - 두 필드 모두 선택. null은 "변경하지 않음"(설정 API 공통 규약)
{ "missedAlertEnabled": true, "missedAlertTime": "19:30:00" }

// 응답 - missedAlertTime은 항상 실효값(미설정이면 기본 21:00)
{ "missedAlertEnabled": true, "missedAlertTime": "19:30:00" }
```

- **하위호환 유지**: 기존 프론트의 `{"missedAlertEnabled": false}` 요청은 그대로 동작한다
  (`missedAlertTime` 생략 = 기존값 유지).
- **기본값으로 되돌리기**: `null`은 규약상 "변경 안 함"이라 초기화 신호로 쓸 수 없다.
  되돌리려면 **21:00을 직접 지정**한다. 별도 reset 필드는 두지 않았다.
- 응답에 "미설정"을 노출하지 않는다 - 보호자가 알아야 할 것은 "지금 몇 시에 받는지"뿐이다.

## 8. 보존한 동작

- 미설정 보호자 = 21:00 그대로, **백필 없음**
- `(guardian, ward, dose_date)` 하루 1건 UNIQUE 유지, **선점 후 발송** 순서 유지(불변 규칙 ④)
- `missedAlertEnabled=false`는 그대로 미발송, 기본 ON 유지(불변 규칙 ⑨)
- 킬 스위치 `medication.reminder.missed-alert.enabled`는 그대로 보호자 요약만 중단
- 발송 창의 **자정 컷** 유지 - 날짜가 바뀌면 요약 대상 자체가 달라진다(불변 규칙 ⑥과 같은 취지)
- 문구는 **"체크되지 않았습니다"** 유지(불변 규칙 ⑦ - 단정 금지)
- **피보호자 복용 알림(2차) 경로는 무변경**
- 알림톡 템플릿 매핑 없음 → 채널은 FCM·문자뿐(불변 규칙 ⑤)

## 9. 검증

`./gradlew build` **403건 / 실패 0** (기존 399 + 신규 4).

신규·수정 테스트

| 테스트 | 고정하는 동작 |
|---|---|
| `집계상한_보호자별` | 같은 피보호자·같은 약이라도 이른 시각을 고른 보호자는 분모가 작다 |
| `조회는_현재시각까지` | 상위집합 조회 cutoff가 "지금"이다(지정 시각이 아니라) |
| `보호자시각_전_제외` | 아직 지정 시각이 안 된 보호자는 이번 주기에서 빠지고 선점도 안 한다 |
| `이른시각_보호자_게이트통과` | 기본 시각 전이라도 이른 시각을 지정한 보호자가 있으면 조회한다 |
| `설정없음_기본값` | 설정 행이 없으면 ON + 전역 기본 시각 |
| `문구_집계상한_노출` | 본문에 "19:30까지 예정된", `data.alertTime`에 시각 |

기존 테스트 중 `집계상한_판정시각`(cutoff == 전역 alertTime)은 상위집합 조회로 바뀌면서
`조회는_현재시각까지`로 대체했고, `판정시각_전`은 게이트 기준이 바뀌어 `발송시각_전`으로 이름을 맞췄다.

### 수동 확인 가이드

1. `PUT /api/guardian/medication-alert-setting` `{"missedAlertTime":"19:30:00"}` → 응답 `19:30:00`
2. 피보호자 약을 19:00·20:00 두 건 등록하고 체크하지 않은 상태로 19:30 대기
3. 보호자에게 "**19:30까지 예정된 복약 1건 중 1건**" 도착 - 20:00 약은 빠진다
4. 같은 피보호자의 다른 보호자가 21:00이면, 그 보호자에게는 **2건 중 2건**이 21:00에 도착

## 10. 프론트 영향

- **파괴적 변경 없음** - 기존 요청·응답 필드는 그대로이고 `missedAlertTime`이 추가될 뿐이다.
- 설정 화면에 시각 선택 UI를 붙일 때, **"선택한 시각 이후 복용 예정인 약은 그날 요약에 포함되지
  않습니다"** 안내를 함께 노출할 것. 이 문장이 없으면 이른 시각을 고른 보호자가 저녁 약까지
  확인된 것으로 오해한다.

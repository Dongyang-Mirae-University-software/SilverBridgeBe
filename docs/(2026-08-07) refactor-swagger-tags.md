# Swagger 태그 체계 정리

> 작업일: 2026-08-07 · 기준 브랜치: `dev` @ `d872654`
> 범위: **문서화(@Tag·설명·표시 순서)만.** URL 경로·권한·요청/응답은 일절 변경하지 않았다.

## 왜 했나

Swagger UI를 열었을 때 **"우리 API에 뭐가 있는지"가 한눈에 안 들어왔다.** 원인은 셋이다.

1. **명명 규칙이 3가지 혼재** — `역할 - 도메인`(`보호자 - 복약 알림`) / `역할`만(`보호자`, `피보호자`) /
   `도메인`만(`인증`, `사용자`, `알림`, `알림 설정`)이 섞여 있었다.
2. **`피보호자` 태그 하나에 서로 다른 3개 도메인이 뭉쳐 있었다** — 연결(5) + SOS 발생(1) + SOS 설정(2).
   펼쳐도 무엇이 무엇인지 구분되지 않았다.
3. **`SwaggerConfig.tags()`에 9개만 등록**돼 있어, 나머지 6개(카메라 2 · SOS 1 · 복약 2 · 알림 설정)는
   **설명 없이 목록 맨 뒤**에 붙었다. 즉 **최근에 만든 기능일수록 문서가 부실**했다.

특히 `사용자` 태그는 주 사용자가 피보호자·보호자인 서비스에서 **제3의 역할처럼 읽혀** 혼동을 만들었다
(실제 내용은 "내 계정" — 프로필·비밀번호·탈퇴).

## 결정한 규칙

**태그 이름 = `<역할> - <도메인>`, 역할은 `공통` / `피보호자` / `보호자` / `관리자` 4가지뿐.**

"누가 쓰는 API인지 → 무슨 기능인지" 두 단계로 읽히게 하는 것이 목적이다.

- **역할만 적은 태그**(`보호자`)를 만들지 말 것 — 그 역할의 API 전부인 것처럼 읽힌다.
- **도메인만 적은 태그**(`인증`)를 만들지 말 것 — 누가 호출하는지가 사라진다.
- **설명은 `SwaggerConfig.tags()`에 일원화**한다. 컨트롤러 `@Tag(description=...)`에 흩어두면
  태그 하나에 컨트롤러가 여럿일 때 설명이 충돌하고, 전체 목록을 한눈에 점검할 수 없다.
- ⚠️ **새 컨트롤러를 추가하면 `SwaggerConfig.tags()`에도 반드시 등록**한다. 이번 정리의 원인이
  바로 이 등록 누락이었다.

### 통합 2건 (사용자 승인)

- **`알림` + `알림 설정` → `공통 - 알림 설정`**: FCM 토큰 등록(기기 단위)과 채널 ON/OFF(계정 단위)를
  한 곳에서 보게 한다. 합쳐도 4개라 부담이 없다.
- **`피보호자`의 SOS 2종 → `피보호자 - SOS`**: 발생(`POST /api/ward/sos`)과 동작 설정
  (`/api/ward/sos-setting`)은 같은 화면 흐름이다.

## 변경 파일

- **컨트롤러 16개** — `@Tag(name=...)` 변경. 이 중 5개(`Auth`·`User`·`Announcement`·
  `NotificationSetting`·`WardSosSetting`)는 인라인 `description`을 제거하고 SwaggerConfig로 이관.
  `AuthController`에 있던 **공통 응답 포맷·토큰 사용법 안내는 `공통 - 인증` 설명에 그대로 보존**했다.
- **`SwaggerConfig`** — `tags()`에 15개 전부 등록(그룹별 구분 주석 + 규칙 주석 포함),
  `operationOrderCustomizer.desiredOrder`에 빠져 있던 **SOS·카메라·복약 경로 12개 추가**.

## 검증

- `./gradlew build` **통과** (407 tests / 0 failures — 태그는 테스트 대상이 아니라 건수 변화 없음)
- **교차 검증 스크립트**로 다음을 확인:

```

컨트롤러 사용 태그      : 15
컨트롤러 수 / 엔드포인트: 22 / 78

설명 없는 태그(누락)    : 없음
사용처 없는 태그        : 없음
중복 등록               : 없음
RESULT: PASS
```

> 앱을 띄워 `/v3/api-docs`를 직접 확인하려 했으나 작업 환경에 Docker(Postgres·Redis)가 없어,
> **컨트롤러 태그 ↔ SwaggerConfig 등록 목록의 정적 교차 검증**으로 대체했다. 이 검사가 실제 위험
> (태그를 쓰는데 설명이 없거나, 등록만 하고 안 쓰는 경우)을 그대로 잡는다. 배포 후 Swagger UI에서
> 태그 15개가 위 순서로 보이는지 눈으로 한 번 더 확인할 것.

## 영향 범위

**프론트엔드 영향 없음** — URL·요청·응답·상태코드·권한이 전부 그대로다. Swagger UI의 그룹 이름과
순서, 설명만 바뀐다. 기존에 만들어 둔 API 호출 코드는 수정할 필요가 없다.

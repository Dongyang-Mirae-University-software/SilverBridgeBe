# 복약 시간대 묶음 3단계 설계안 - 피보호자 묶음 체크·복약 알림 묶음 (2026-10-23)

> 상태: **설계(PHASE 1) - 승인 대기, 코드 미작성.** 1·2단계(FE 화면)는 FE PR #95로 반영 완료.

## 배경
보호자가 약 6개를 하루 3번(아침·점심·저녁)으로 등록하면 BE에는 약×시각 18행이 생긴다(일괄 등록 V62 구조). 그 결과
- 보호자 카드가 "18번 중"으로 셌다 → **FE #95에서 시간대 묶음으로 해결**(BE 변경 없음).
- 피보호자는 아침에만 "먹었어요"를 **6번** 눌러야 한다(체크 API가 약 1개 단위).
- 복약 알림이 약마다 따로 나가 08:00에 **푸시 6건**, 재알림까지 최대 12건, 문자를 켠 분은 문자도 그만큼 받는다.

## PHASE 0 - 확인한 사실 (dev 39dda3f 기준)
| 항목 | 현재 |
|---|---|
| 체크 API | `POST/DELETE /api/ward/medication/{medicationId}/intake` (WARD, 본인 약만, `UNIQUE(medication_id, dose_date)` 멱등) |
| 체크 실시간 반영 | `MedicationIntakeChangedEvent` → AFTER_COMMIT `@Async` → WS `medication-taken`(약 1건씩). FE는 보호자·피보호자 모두 **알림 없이 캐시만 갱신**(GuardianLayout·WardLayout) |
| 알림 선점 | `MedicationReminderPlanner.claim()`이 약마다 `medication_reminder_log`를 먼저 커밋(`UNIQUE(medication_id, dose_date, attempt)`) |
| 알림 발송 | `MedicationReminderService.send()`가 **선점한 약마다 `dispatch` 1회** - 묶는 단계가 없다 |
| 채널 | FCM·문자(설정대로), 알림톡 매핑 없음(다발성 메시지) |

## 제안 A - 피보호자 묶음 체크
**API**: `POST /api/ward/medication/intake/batch` 본문 `{ "medicationIds": [..], "taken": true|false }`
- WARD 전용(클래스 레벨 `@PreAuthorize` 그대로) - **보호자용 체크 API는 만들지 않는다**(복약 불변 규칙 ① 유지).
- 1~50개, 중복 id 400. **한 트랜잭션 - 전부 성공 또는 전부 실패**(일괄 등록과 같은 판단: 일부만 체크되면 본인이 모른다).
- 한 개라도 본인 약이 아니면 전체 403 `MEDICATION_NOT_OWNED` + `[IDOR-ATTEMPT]`, 없는·삭제된 약은 전체 404. 판정은 단건 체크와 **같은 서비스 메서드**를 재사용(복제 금지).
- 이미 체크된 약은 그대로 성공(멱등). 날짜는 `MedicationClock`(KST).
- 실시간 반영은 약마다 기존 `MedicationIntakeChangedEvent`를 그대로 발행 - FE가 조용히 캐시만 갱신하므로 6건이어도 소음이 없다. 새 이벤트 계약을 만들지 않는다.
- 단건 API는 그대로 둔다(약 하나만 풀 때).

**피보호자 화면(FE)**: 시간대 묶음 카드 + 큰 버튼 하나.
```
다음에 드실 약 · 아침 08:00
약 6개 (코싹열정, 신일이부프로펜정 외 4개)
[ ✓ 아침 약 다 먹었어요 ]
  ▸ 약 하나씩 보기(잘못 눌렀을 때 하나만 풀기)
```
- 묶음 버튼 = 그 시간대의 **아직 체크 안 한 약**만 보낸다.

## 제안 B - 복약 알림 묶음
**선점은 지금처럼 약 단위, 발송만 묶는다.**
- `claimFirstReminders`·`claimRetryReminders`가 돌려준 대상을 `(wardId, doseDate, doseTime, attempt)`로 묶어 묶음마다 `dispatch` 1회.
- **선점 후 발송 순서·UNIQUE·유예 30분·자정 미넘김·재알림 사용자 선택·킬 스위치는 바꾸지 않는다.** 묶음은 발송 직전 메모리 안에서만 한다.
- 같은 시각 약이 서로 다른 분에 선점되면(예: 한 약을 늦게 등록) 별도 알림이 된다 - 수용(드문 경우, 중복이 아니라 나뉨).

문구(어르신이 읽는 문장 - 무엇을·언제·얼마나):
| 경우 | 제목 | 본문 |
|---|---|---|
| 첫 알림, 1개 | 복약 시간이에요 | (기존 그대로) 코싹열정 드실 시간입니다. 아침 08:00 · 1정 |
| 첫 알림, 여러 개 | 복약 시간이에요 | 아침 약 6개 드실 시간입니다(08:00). 코싹열정 1정, 신일이부프로펜정 1정 외 4개 |
| 재알림, 여러 개 | 약 드셨나요? | 아침 약 중 2개가 아직 복용 체크되지 않았어요. 코싹열정, 코푸시럽 |

- 문구는 "체크되지 않았어요"(단정 금지) 유지. 이름 나열은 2개 + "외 N개"(문자 90바이트 넘으면 LMS 전환 - 이상감지 G-1과 같이 수용).
- 푸시 data: `type=MEDICATION_REMINDER` 유지, `medicationId`는 첫 약(옛 FE 호환) + `medicationIds`(쉼표 목록) 추가. 알림 이력은 묶음당 1행이 된다(관리자 화면 건수 감소 - 의도).

## 바뀌지 않는 것
- 보호자 미복용 요약(이미 하루 1건 요약), 등록·수정·삭제 API, 알림톡(매핑 없음), 이메일, 마이그레이션 없음.

## 결정이 필요한 것
1. 묶음 체크 API 형태 - **추천: id 목록 + `taken`**(화면이 가진 값 그대로, 시각 기준 조회보다 서버 해석이 단순). 대안: `{doseTime}`로 서버가 찾기.
2. 묶음 체크 해제(전체 풀기)를 화면에 둘지 - **추천: 두지 않음**(잘못 누르면 약 하나씩 풀기). API는 `taken=false`로 지원.
3. 알림 문구 위 표 그대로 갈지.

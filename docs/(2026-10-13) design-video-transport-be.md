### 1-1. 낙상 클립 프레임 환산 (앞 8초 + 뒤 1초 = 9초, 버퍼 10초)

| fps | 낙상 9초 | 버퍼 10초 최대 | 상한 150 | 상한 100(AI 기본) |
|---|---|---|---|---|
| 10 | 90장 | 100장 | 여유 | 딱 맞음 |
| 12 | 108장 | 120장 | 여유 | 초과(앞부분 잘림) |
| 15 | 135장 | 150장 | **경계(정확히 상한)** | 초과 |

- gosky 현재 상한 150이라 15fps에서도 장수는 통과한다. 단 **여유가 0**이다.
- 바이트 상한(세션 64MB)은 별개다. 프레임 0.35MB면 150장 약 52MB, 0.5MB면 약 75MB로 상한을 넘어 오래된 프레임부터 지워진다. **약 0.43MB를 넘으면 15fps에서 낙상 앞 구간이 줄어들 수 있다**(측정으로 확인할 항목).
- AI 분석 부하(1장 19.2ms, 스레드 1개 기준 사용률): 15fps = 1대 약 29% / 2대 약 58% / 3대 약 86%. 10fps(19/38/58%)보다 3대 동시는 여유가 얇다.

## 2. 1부 - 권장 송출 fps 15 시험

- 변경: gosky `.env.dev`에 `CAMERA_RECOMMENDED_FPS=15` 추가, `up -d api`(코드·마이그레이션 없음). 백업 `.env.dev.bak-20261013-2151`(gosky 작업 디렉터리).
- 적용 확인(2026-10-13 21:52): 컨테이너 환경변수 15, api healthy, 기동 로그 ERROR 0건, AI WS 재연결 확인.
- vkcs-linux는 **적용하지 않음**(AI 서버 없음, 기본 10 유지). 결과를 본 뒤 결정한다.
- 되돌리기: gosky `.env.dev`에서 해당 줄을 지우고 `docker compose -f docker-compose.dev.yml up -d api`(restart 아님) → 기본 10.
- 기존 동작 보존: 카메라 등록·sessionId 발급·시청 티켓·MJPEG 중계·클립 저장은 바뀌지 않는다.

### 측정 결과 (송출 시작 후, 읽기 전용, 영상 내용 열람 없음)

gosky, AI `status`·`latest-frame` 읽기 전용 폴링(0.1초 간격 + 응답 지연이라 도착 프레임 수는 **하한**). 같은 기기·위치에서 15 → 10 순서로 측정.

| 항목 | 이전(10fps, 2026-10-07) | 15fps 시험 (10/13 22:xx KST) | 10fps 재측정 (10/14) |
|---|---|---|---|
| AI 보고 fps(running 구간 중앙값) | 10.3 | **14.7** | **9.99** |
| 확인된 프레임 간격 중앙값 | - | 0.130초 | 0.112초 |
| 최대 프레임 간격 | 약 1초 | **19.9초**(송출 +25초, 상태는 running 유지) | 0.68초 |
| 1초 이상 간격 | - | 3회 | 0회 |
| 프레임 크기(`latest-frame`) | - | 측정 못 함 | 약 96~122KB(0.1MB 안팎) |
| 송출 지속 | - | 약 57초(끊김 포함) | 약 13초 뒤 stopped |
| 낙상 클립 | - | 새로 생성된 것 없음 | 새로 생성된 것 없음 |

- 15fps 시험은 **송출 중 19.9초 끊김**이 한 번 있었다. 10fps 재측정은 13초 만에 송출이 멈춰(stopped) 끊김 유무를 비교할 만큼 길지 않다. 첫 15fps 시도도 7초 만에 stopped였고, 15·10 어느 쪽에서도 송출이 짧게 끝났으므로 **끊김·중단을 15fps 탓으로 단정할 수 없다**(원인 미확인: 송출 기기·탭 상태·네트워크 등은 추정 단계).
- 15fps에서 AI 보고 fps는 목표에 가깝게 들어왔다(14.7). 도착 능력 자체는 문제가 없어 보인다.
- 프레임이 약 0.1MB라 15fps 150장 ≈ 15~18MB로 세션 64MB 바이트 상한과 거리가 멀다. **1-1절의 바이트 상한 우려(0.43MB 초과 시)는 이 크기에서는 해당하지 않는다.** 남는 제약은 장수(135 대 150)뿐이다.
- 이 측정으로 15 유지/10 복귀를 가르기에는 송출 지속 시간이 짧다. 현재 gosky는 **10(기본값)으로 되돌린 상태**다(백업 `.env.dev.bak-20261014-0945`).

## 3. 2부 - 시청 중계·연결 자격 발급 설계 (결정 대기, 문서만)

### 3-1. 전환안별 BE 변경 범위

| 영역 | A. WebRTC | B. WS + WebCodecs | C. 현재 유지 |
|---|---|---|---|
| 시청 인가(`getViewableCamera`) | 그대로 재사용 | 그대로 | 변경 없음 |
| 시청 자격 | 티켓 대신 **시그널링 자격**(1회용, 세션·사용자 바인딩) 발급 필요. SDP 교환을 BE가 중계하거나 AI가 직접 받음 | WS 연결용 1회용 티켓 재사용 가능(경로만 `wss`) | 현행 티켓 |
| 영상 경로 | 브라우저↔AI 직결이면 BE는 비디오를 안 거침(중계 상한 20/1인 2 불요). TURN/ICE 설정 필요 | BE 중계 유지(프레임 단위 WS 프록시) 또는 직결 | `AiStreamClient`/`AiMjpegStream` 그대로 |
| 재확인 60초·30분 상한 | BE가 자격을 끊을 수단이 약함(P2P면 AI에 종료 요청 API 필요) | WS 서버 측 루프로 현행과 동일하게 구현 가능 | 현행 |
| 송출(업로드) 경로 | WebRTC 송출 시 업로드 인증 새로 설계(송출용 일회용 자격) | JPEG 업로드 유지 가능 | 변경 없음 |
| `CameraResponse` | 전송 방식 필드(예: `transport`) 추가 검토 | 동일 | `recommendedFps` 값만 조정 |
| 클립 | AI 버퍼가 JPEG 전제면 인코딩 경로 확인 필요(AI 몫) | 동일 | 변경 없음 |
| 마이그레이션 | 없음(예상) | 없음(예상) | 없음 |
| 위험 | 직결이면 AI 키·ICE 주소 노출면 증가, 무인증 경로 위험 | 프레임 단위 중계 CPU·스레드 | 낮음(검증된 경로) |

### 3-2. 지켜야 할 불변 규칙 체크리스트 (어느 안이든)

- [ ] AI 키(`AI_API_KEY`)는 브라우저·URL·응답·로그에 노출하지 않는다(서버 헤더만)
- [ ] 무인증 경로를 만들지 않는다. 불가피한 예외(영상 `<img>` 등)는 1회용 자격으로만
- [ ] 열람은 ACTIVE 연결만(`isActiveConnection`/`getViewableCamera` 한 곳, `getMyWards` 금지), 위반 403 `CAMERA_NOT_CONNECTED` + `[IDOR-ATTEMPT]`
- [ ] 시청 중 60초 재확인(계정·연결·카메라·무효화)과 최대 30분 상한을 유지한다
- [ ] sessionId에 사용자 식별자를 싣지 않는다(`ward_` + 영숫자 16자)
- [ ] 자격은 일회용(사용자·세션·60초·1회), access token을 쿼리로 받지 않는다
- [ ] 동시 시청 상한(전체 20 / 1인 2)과 보호자별 속도 제한을 유지한다
- [ ] 피보호자용 시청 API·관리자용 시청 API를 만들지 않는다(정책 변경 없이는 불가)
- [ ] 실패 시 열린 연결을 끊는 방식이 형식에 맞게 구현된다(MJPEG은 `disconnect()`, WS는 close 코드)
- [ ] 로그에 sessionId·결과 코드만 남기고 프레임·SDP 원문은 남기지 않는다

### 3-3. 새 연결 자격(송출용·시청용) 발급 시 현재 티켓 모델과의 차이와 위험

| 항목 | 현행 시청 티켓 | 새 자격(예: 송출·시그널링용) |
|---|---|---|
| 용도 | `<img>` 한 번의 GET | 장시간 세션(WS/PC) 수립 |
| 수명·소비 | 60초, `GETDEL` 1회 | 수립 시 1회 소비 + 세션 중 **갱신/폐기 수단** 필요 |
| 인가 시점 | 소비 시 계정·연결·무효화 재확인 | 동일 + 수립 후 주기 재확인(현행 60초) |
| 송출용이면 | (현행 송출은 별도 업로드 경로) | 피보호자 본인 카메라만, sessionId 바인딩, 시청 자격과 **분리**해야 함 |
| 위험 | 탈취되어도 60초·1회 | 재사용 가능 자격은 탈취 시 영상 전체 노출. 폐기·바인딩 없으면 정지·연결 해제가 즉시 반영되지 않음 |

## 4. 3부 - 정책 문서 갱신 계획 (전환안 확정 후 적용, 지금은 수정하지 않음)

### `.claude/rules/domain-security-policy.md` "보호자 실시간 카메라 보기"
- 경위의 "FE → 백엔드 → AI 완전 중계" 서술: A안이면 "시청 영상은 직결, 백엔드는 인가·자격 발급" 으로 정정
- 불변 규칙 ②: "`<img>`는 1회용 티켓 / permitAll 경로는 `/api/camera/stream/*/mjpeg` 하나" → 새 경로·자격 이름 반영
- 불변 규칙 ③: "AI MJPEG은 스스로 끝나지 않아 30분 상한" → 전송 방식별 종료 수단으로 교체
- 불변 규칙 ⑥: "MJPEG은 Spring 응답 래퍼로 닫지 말 것" → B/A안이면 해당 형식의 닫기 규칙으로 대체(C안이면 유지)
- 호출 시간 제한 절: `callTimeout` 8초 등 MJPEG 가정 문장 점검
- 동시 시청 상한 절: 직결이면 BE 스레드 점유 논리가 사라지므로 상한 근거 문장 수정
- 수용한 한계: "FE 프록시 무인증 구멍" 항목은 전환 후 상태에 맞게 갱신

### `CLAUDE.md` 카메라 항목 (§1, "보호자 실시간 카메라 보기")
- "FE → 백엔드 → AI 중계(브라우저는 AI에 직접 붙지 않는다)" 문장: A안이면 변경

- "권장 송출 10fps(`camera.recommended-fps`, 2026-10-07 5에서 상향 …)" 문장: 시험 결과에 따라 15 또는 유지로 갱신(값과 근거 날짜)
- "MJPEG는 `HttpURLConnection.disconnect()`로 닫는다" 문장: A/B안이면 삭제 또는 대체

- `application.yaml` 주석(`recommended-fps` 근거 3줄)과 `CameraRecommendedFpsDefaultTest`(기본값 10 고정): **기본값을 15로 바꾸기로 결정하면** 함께 수정 대상(이번 작업에서는 바꾸지 않음)

## 1. 영향 받는 엔드포인트 (4개)

| Method | Endpoint | 비고 |
|--------|----------|------|
| POST | `/api/auth/find-password/email/send` | 이메일 인증코드 발송 |
| POST | `/api/auth/find-password/email/resend` | 이메일 재발송 (send와 동일 동작) |
| POST | `/api/auth/find-password/sms/send` | SMS 인증코드 발송 |
| POST | `/api/auth/find-password/sms/resend` | SMS 재발송 (send와 동일 동작) |

> **변경 범위 밖(그대로):** `find-password/email/verify`, `find-password/sms/verify`(2단계 코드 확인), `password/reset`(3단계 최종 변경). 이 3개는 응답·동작 변화 없음.
> **이미 노출 정책(무관):** `signup/email/check`, `find-email`.

## 2. 응답 Body 형태 (전 엔드포인트 공통)

백엔드 공통 래퍼 `ApiResponse` 사용:

```jsonc
// 성공 (데이터 있음) — send/resend 200
{ "success": true, "data": { "expiresInSeconds": 300, "codeLength": 6 } }

// 실패 — 400 / 404 / 429 / 500
{ "success": false, "message": "사용자에게 보여줄 메시지" }
```

- `data`/`message`가 `null`이면 **응답에서 생략**됨(`NON_NULL`).
- **에러 메시지는 항상 `response.data.message`에 담겨 옵니다.** → FE의 `error.response.data.message` 그대로 표시 가능.
- ⚠️ `code` 필드는 **없습니다**(`success` boolean만 있음). 상태 분기는 **HTTP status code**로 하세요.

## 4. 케이스별 FE 처리 요약

| HTTP | 핵심 동작 | UX 권장 |
|------|-----------|---------|
| **200** | step 진행(인증코드 입력). `data.expiresInSeconds`로 카운트다운 시작 | 그대로 |
| **400 (형식/누락)** | 입력 단계 유지, `message` 인라인 표시 | (선택) 제출 전 정규식 선검증으로 왕복 절감 |
| **400 (카카오)** ⭐신규 | 입력 단계 유지, `message` 표시 | **"카카오 로그인을 이용해주세요" 안내 + 카카오 로그인 이동 CTA 권장** |
| **404 (미가입)** | 입력 단계 유지, `message` 표시 | **회원가입 유도 CTA**(+이메일은 "아이디 찾기" 병행) 권장 |
| **429** | 입력 단계 유지, `message` 표시 | 재발송 버튼 일시 비활성 권장 (대기시간은 §5-2 참고) |
| **500** | 입력 단계 유지, `message` 표시 | 일반 오류 안내 |

> ⭐ **카카오 400은 2026-05-22 문서에 없던 신규 분기입니다.** 미가입(404)과 별개로, "그 이메일/번호는 카카오로 가입된 계정"임을 알려 카카오 로그인으로 유도해야 합니다. (가입 자체는 존재하므로 회원가입 유도는 부적절)
>
> ✅ **공통 전제 충족:** 에러 메시지가 `response.data.message`로 오므로, 기존 인라인 에러 표시(`errorMessage`) 구조로 **메시지 출력은 자동 동작**합니다. 핵심 작업은 여전히 "성공(200)일 때만 다음 step 진행"하도록 분기하는 것(2026-05-22 문서 §4.1 ①).

## 5. 2026-05-22 문서 미해결 질문 — 백엔드 확정 답변

### 5-1. 에러 응답 body 형태 (질문 #1)
- **`{ "success": false, "message": "..." }`** 입니다. `message` 항상 존재 → `error.response.data.message` 그대로 사용 OK.
- `code` 필드는 **없음**. 분기는 HTTP status로.

### 5-2. 429 대기시간 제공 여부 (질문 #2)
- **`Retry-After` 헤더 없음. body에 남은 초 필드도 없음.**
- 카운트다운 UX를 원하면 **클라이언트 측 고정 추정치**(예: 60초)로 처리해야 함. (서버는 1분 윈도우 기준)

### 5-3. Rate Limit 기준 (질문 #3)
- **IP 기준 이중 윈도우: 1분 10회 / 1시간 30회** (한쪽 초과 시 429). `send`·`resend`는 **같은 IP 카운터를 공유**.
- 추가로 **식별자 단위 발송 상한 1시간 10회**: 이메일은 `password:email:sendcount:{email}`, SMS는 `sms:sendcount:{phone}`. (정상 사용자는 도달하지 않음)
- → 재발송 버튼 disable 시간은 굳이 서버와 정밀 동기화할 필요 없음(서버가 시간을 안 내려줌). 짧은 고정 disable로 충분.

### 5-4. 400 트리거 조건 (질문 #4)
- **빈 값/누락(`@NotBlank`)** + **형식 오류(`@Email` / 전화번호 `^\d{10,11}$`)** + **카카오 가입 계정** 모두 400.
- 프론트 정규식: 이메일 표준 형식, 전화번호 `숫자 10~11자리(하이픈 없이)`.

### 5-5. 배포 일자/순서 (질문 #5)
- **dev: 2026-05-23 배포 완료.** prod: **미배포** → 프론트 운영 준비 완료 후, 태그 `prod-2026-05-23-pw-reset`을 체크아웃해 **프론트와 동시 배포**.
- 그 사이 dev에서는 새 응답이 이미 적용 중이니, FE는 dev에서 바로 통합 테스트 가능.

## 7. 회귀/주의 (변경 없는 부분 재확인)
- `email/verify`·`sms/verify`·`password/reset`는 응답 그대로 → 인증코드 확인·최종 재설정 흐름 **수정 불필요**.
- 비밀번호 변경 성공 시 전 기기 로그아웃(기존 동작) 유지.
- 전역 에러 핸들러 수정 시(429 fallback 등) 다른 도메인 API 영향 — 기존 키 문구 변경 금지(2026-05-22 문서 §6 참고).

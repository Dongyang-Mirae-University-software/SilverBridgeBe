## 이슈

### 🔴 C-1. Redis가 비밀번호 없이 인터넷에 열려 있다 (PostgreSQL도 공개)

- **사실**: `docker-compose.dev.yml`이 `db`를 `"6513:5432"`, `redis`를 `"6514:6379"`로 전 인터페이스에 공개한다(api만 `127.0.0.1:`). gosky는 ufw 비활성·INPUT ACCEPT이고, 외부에서 `gosky.kr:6513`·`6514` TCP 연결이 열렸다. Redis는 `requirepass ""`·`protected-mode no`.
- **공격 흔적**: Redis 로그 `Possible SECURITY ATTACK detected` 23회(9월에만 6회), PostgreSQL 로그 `role "postgres" does not exist`(외부 무차별 시도).
- **영향**: Redis에는 `password:email:verify:`·`password:sms:verify:`(비밀번호 재설정 코드), `sms:verified:`(가입 본인확인 통과 표시), `logout:`·`password:invalidate:`(토큰 무효화), `login:lock:`이 들어간다. 공격자가 피해자 이메일로 재설정을 요청하고 Redis에서 코드를 읽으면 **관리자 포함 임의 계정 탈취**가 된다. 키 삭제로 무효화된 토큰을 되살리거나 로그인 잠금을 풀 수도 있다. rate limit·선검증·코드 소비 순서 같은 코드의 방어는 전부 우회된다.
- **침해 여부**: `commandstats`에 `flushall`·`slaveof`·`config set`·`module load` 없음, role master, dir/dbfilename 정상 → 파괴·장악 흔적은 없다. **읽기(GET/SCAN)는 흔적이 남지 않아 확인 불가.**
- **vkcs**: 같은 compose라 6513·6514가 `0.0.0.0`에 묶여 있다. 사설 IP만 확인돼 외부 도달 여부는 미확인.
- **수정안(1줄씩)**: compose의 두 포트를 `"127.0.0.1:6513:5432"`·`"127.0.0.1:6514:6379"`로(또는 ports 제거). 팀원이 외부에서 DB에 직접 붙어 쓰고 있었다면 SSH 터널로 바꿔야 한다. 추가로 Redis `requirepass`.
- **사후 조치 판단**: 코드는 Redis에서 읽혔는지 알 수 없다. `access_log`의 최근 비밀번호 재설정·관리자 로그인 이력을 확인하고, 이상이 있으면 관리자 비밀번호·DB 비밀번호를 교체한다. JWT 시크릿은 Redis에 없어 이 경로로는 노출되지 않는다.

### 🟡 M-1. 역할 변경 시 복약·설정이 정리되지 않는다

- `AdminUserService.applyRole`(`:229-248`)은 연결 정리 + 카메라 삭제 + 토큰 무효화만 한다. `medication`(ward_id·created_by)·`medication_setting`·`guardian_medication_setting`·`guardian_anomaly_setting`·`anomaly_incident_feedback`은 남는다.
- **실제 영향**: 피보호자 → 보호자로 바뀐 사람 앞으로 등록된 약이 살아 있으면 `MedicationReminderPlanner`(삭제·시각·체크·알림 설정만 본다)가 계속 "약 드실 시간" 알림을 보내는데, 본인은 체크(WARD 전용)도 삭제(연결된 보호자 전용)도 할 수 없다. 보호자 → 피보호자는 그 사람이 등록한 약이 남아 상대 피보호자에게 계속 알림이 가지만, 다른 보호자가 없으면 아무도 지울 수 없다.
- 카메라를 함께 지우기로 한 2026-09-10 M-3과 같은 종류의 누락이다. **수정안**: 역할 변경 시 탈퇴와 같은 복약 정리(`removeMedicationsRegisteredBy` + ward 소유 약 soft delete)를 호출.

### 🟡 M-2. FCM·Solapi 호출에 시간 제한이 없다

`FcmConfig`·`SmsSender`·`AlimtalkSender`에 connect/read 타임아웃 설정이 없다(카카오 3s/5s·SMTP 10s·파일 서버 3s/10s는 있음). `@Async`라 요청 스레드는 안 묶이지만, 외부 지연 시 `notificationExecutor`(max 10)가 묶여 뒤따르는 SOS·화재 알림이 큐(500)에서 밀리거나 폐기된다. 정책 "외부 HTTP 클라이언트는 타임아웃 필수"(2026-09-11)의 미적용 2곳.

### 🟡 M-3. 카메라 등록 이벤트를 커밋 전에 처리한다

`AiLiveStreamSubscriber.onCameraRegistered`(`:166`)가 일반 `@EventListener`라 `CameraService.register` 트랜잭션이 끝나기 전에 AI에 세션 목록을 요청한다. AI 응답이 커밋보다 먼저 오면 `findOwnerBySessionId`가 방금 넣은 행을 못 보고 "미등록 세션"으로 건너뛴다. AI는 세션 생성·종료 때만 목록을 다시 보내므로 **에러 없이 그 카메라만 구독되지 않는다.** 확률은 낮다(로컬 커밋 < 네트워크 왕복). **수정안**: `@TransactionalEventListener(AFTER_COMMIT)`.

### 🟡 M-4. api.devdmu.gosky.kr이 평문 HTTP로도 그대로 서비스된다 (인프라)

nginx 80번 블록이 리다이렉트 없이 BE로 프록시한다(`http://.../actuator/health` 200 확인). HSTS는 HTTPS 응답에만 실리므로 처음부터 http로 붙는 클라이언트는 JWT를 평문으로 보낸다. 같은 서버의 `ssl_protocols`에 TLS 1.0·1.1이 켜져 있고, `.env.dev`는 `-rw-r--r--`(공용 서버의 다른 계정이 시크릿을 읽을 수 있음)다. 세 건 모두 관리 권한 밖일 수 있어 수용 여부 결정 필요(E-1 Swagger 공개와 같은 범주).

### 🟡 M-5. 화재 알림이 어떤 채널로도 전달되지 않은 실측 사례 (결정 재확인)

`notification_log`에 `ANOMALY_DETECTED` FAILED 1건·`ANOMALY_DETECTED_SELF` FAILED 1건(사유 `NO_DEVICE`, 다른 채널 꺼짐). 화재는 `FORCED_PUSH_PLUS_SETTINGS`라 SMS 폴백이 없다(2026-07 D-2 결정 - 문자는 사용자 선택). 즉 **앱에 로그인해 기기를 등록한 적 없는 보호자는 화재를 WS로만 받는다.** 정책대로 동작한 것이지만 실제 데이터로 처음 확인됐으므로, "보호자가 기기 없음 상태면 화면에서 경고" 같은 보완을 둘지 판단이 필요하다. 같은 이유로 `CONNECTION_FORCED` 9건 전부 FAILED(`NO_DEVICE`) - 강제 연결 알림이 당사자에게 한 번도 도달하지 않았다(동의 없는 연결의 대체 장치가 알림인데 실효가 없었다).

# FCM 토큰 누적 정리

> 2026-09-02 / 마이그레이션 없음(`created_at`·`updated_at`은 V8부터 존재)

---

## 1. 발단

연결 수락 알림이 두 번 온다는 제보를 조사하다 발견했다. 중복 토스트의 원인은 **프론트의 이중 렌더링**
(WebSocket + FCM을 각각 토스트로 그림)이라 별건이지만, 그 과정에서 **일부 계정에 FCM 토큰이 2~3개
쌓여 있는 것**이 드러났다.

```
gosky : 6명 / 토큰 12개    aB3x9A 3개 · gosky 3개 · GRD001 2개 · Jzejp0 2개 · a9cC5f 1개 · wDLVW1 1개
vkcs-linux : 0개
```

발송 로그는 `FCM 발송 완료: 성공=3, 실패=0` — **FCM은 세 토큰을 모두 유효하다고 판정**한다.
따라서 `cleanupInvalidTokens`(발송 실패 시 정리)에는 영영 걸리지 않는다.

## 2. 진짜 결함은 "누적"이 아니라 "판단 근거가 없다"는 것

토큰은 기기 단위라 한 사람이 여러 개를 갖는 것이 정상이다(폰·PC·태블릿). 문제는 그중 **어느 것이
아직 쓰이는지 알 방법이 없었다**는 점이다.

`registerToken`이 같은 사용자의 재등록을 **no-op**으로 처리했다. 바뀌는 필드가 없으니 Hibernate가
UPDATE를 내지 않고, DB 트리거도 발동하지 않아 `updated_at`이 **최초 등록 시각에 멈춰 있었다.**

실측에서도 12개 중 11개가 `updated_at = created_at`이었다(92·93·97일 전 등).

> 이 상태에서 "60일 미갱신 삭제"를 켜면 **살아 있는지와 무관하게** 지운다. 우리가 기록을 안 남긴
> 탓에 지우는 셈이다. 그래서 시각 갱신이 선행되어야 한다.

## 3. 변경

| | 내용 |
|---|---|
| **①** | **재등록 시 `updated_at` 갱신** — `FcmTokenRepository.touch()` |
| **②** | **사용자당 상한 5개** — 초과 시 마지막 사용이 오래된 것부터 삭제 |
| **③** | **유휴 토큰 정리** — 60일 미갱신, 매일 04:00 KST |

**시각 갱신을 `@Modifying` UPDATE로 한 이유**: 엔티티를 고쳐 변경 감지에 맡기면 바꿀 필드가 없어
UPDATE가 나가지 않는다. 명시적 쿼리라야 확실하다.

**상한 검사는 신규 등록 직후에만** 한다 — 재등록은 개수를 늘리지 않으므로 검사할 이유가 없다.

**04:00에 도는 이유**: 발송이 몰리는 시간(복약 알림·재촉·이상감지)을 피한다.

## 4. 설정

```yaml
notification:
  fcm-token:
    max-per-user:    ${FCM_TOKEN_MAX_PER_USER:5}
    cleanup-enabled: ${FCM_TOKEN_CLEANUP_ENABLED:true}   # 킬 스위치
    stale-days:      ${FCM_TOKEN_STALE_DAYS:60}
```

킬 스위치는 **정리만** 멈춘다 — 등록·발송은 그대로 동작한다.

## 5. 배포 시 일어나는 일

첫 정리에서 **8개가 삭제된다**(60일 이상 미갱신). 계정별로는 `GRD001`(2개 전부)과
`wDLVW1`(1개 전부)이 토큰 0개가 된다.

**전부 개발 테스트 계정이고, 자동 복구된다.** 프론트 `RoleRouteGuard`가 보호 라우트 진입 시
재등록하므로 다음 접속에 되살아난다.

⚠️ **다만 열어둔 탭은 스스로 복구하지 않는다** — `sessionStorage`에 등록 기록이 남아 있으면 서버를
다시 부르지 않는다. 새로고침하면 해결된다.

## 6. 남겨둔 위험 (운영 전환 시 재검토)

토큰이 0개인 동안 알림이 어떻게 되는지는 종류마다 다르다.

| 알림 | 정책 | 토큰 0개일 때 |
|---|---|---|
| SOS | `FORCED_PUSH_WITH_SMS_FALLBACK` | 문자로 폴백 — 살아남음 |
| **이상감지** | `FORCED_PUSH_PLUS_SETTINGS` | **SMS 폴백 없음** — 문자를 안 켰으면 아무 데도 안 감 |
| 그 외 | `SETTINGS_ONLY` | 설정대로. WS는 접속 중이면 별개로 도착 |

**이상감지가 유일하게 조용히 유실될 수 있다.** 실사용자가 붙은 뒤에는 시각 갱신이 쌓여 정리가
정확해지므로 위험이 줄지만, 장기 미접속 피보호자에 대해서는 이 조합을 한 번 다시 봐야 한다.

## 7. 검증

```
./gradlew build   488건 / 실패 0     (기존 480 + 신규 8)
```

테스트가 고정한 것: 재등록 시 행이 늘지 않고 시각만 갱신 / 재등록은 상한 검사를 건너뜀 /
상한 초과 시 오래된 것부터 삭제 / 상한 이내면 삭제 없음(폰·PC 병행은 정상) /
유휴 정리 기준 시각 / 킬 스위치 / 정리 실패가 스케줄러를 죽이지 않음

## 8. 하지 않은 것

- **기존 누적분 수동 정리** — 자동 정리에 맡긴다. 사람이 골라 지우는 건 판단 근거가 없다.
- **마이그레이션** — 필요한 컬럼이 이미 있다.
- **프론트 중복 토스트 수정** — FE 담당(별건). 안내는 Notion `프론트엔드 전달 내용`에 전달했다.

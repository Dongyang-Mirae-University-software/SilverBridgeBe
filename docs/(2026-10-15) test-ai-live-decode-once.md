# AI 서버 실시간 분석 디코드 1회화 - 구현과 처리 시간 측정 결과

> 작성 2026-10-15. 대상은 AI 서버(`SilverBridgeAiServer`)이며 백엔드 코드는 변경이 없다. 응답 형식(`detectedType`·`confidence`·`danger`·`frameQuality` 등)도 그대로다.

## 1. 배경

- 실시간 분석에서 프레임 1장을 **4번 디코드**하고 있었다. 감지기 3개(화재·흉기·낙상)가 JPEG를 각자 컬러로 풀고, 화면 품질 검사가 흑백으로 한 번 더 풀었다.
- 10/14 gosky 측정(합성 화면)에서 순수 추론 합은 13.9ms(화재 4.2 / 흉기 5.7 / 낙상 4.0)였지만 운영 `[LIVE-INFER]`는 20.2ms였다. 차이 약 6ms가 컬러 디코드 3회(장당 약 2.0ms)와 일치했다.
- 함께 검토한 FP16·입력 크기 480은 효과가 없어 채택하지 않았다.

## 4. 처리 시간

### 4-1. 같은 화면 비교 (측정 도구, 10/14 gosky)

- `tools/measure_live_budget.py` - 합성 화면만 쓰고 `nice 19`, 운영 이미지로 띄운 **임시 컨테이너**에서 돌린다(운영 컨테이너 아님). 변경 전·후 경로를 같은 화면에 번갈아 재고 예산(기본 30ms) 판정과 불일치 수를 출력한다.
- 1280x720 합성 화면 300장, 세 번 실행:

| 구간 | 변경 전 평균 | 변경 후 평균 |
|---|---|---|
| decode | (감지기 안) | 1.7ms |
| quality | 1.4ms | 0.45ms |
| fire / knife / fall | 6.1~6.5 / 6.7~7.2 / 6.2~6.6ms | 4.5~4.9 / 5.0~5.4 / 4.4~4.7ms |
| **합계** | **20.4~21.8ms** | **16.0~17.1ms** |

- 프레임당 **약 4.4~4.7ms(약 21%) 절약**. 변경 후 p95 21~26ms로 예산 30ms 안(PASS).

### 4-2. 운영 실측 (배포 후 실제 카메라, 10/15 10:34~11:11 KST)

| 항목 | 값 |
|---|---|
| 60초 창 | 약 25개, 창마다 약 700~790프레임(초당 약 12회 분석) |
| 프레임당 합계 | 평균 20.5~22.2ms |
| 창별 최대 | 31~48ms |
| decode | 1.2~2.1ms |
| quality | 2.5~2.8ms |
| fire / knife / fall | 약 6.0 / 5.9 / 5.2ms |
| 디코드·감지·품질 검사 오류 로그 | 0건 |

- 재시작 후 첫 프레임 1장(688ms)은 모델을 처음 GPU에 올리는 예열 비용이라 제외했다.
- **배포 전과 직접 비교는 못 했다.** 컨테이너를 다시 만들면서 예전 로그가 사라졌고, 20.2ms 기준값은 합성 화면 값이라 장면이 다르다. 같은 항목(디코드 + 감지기 3개)만 보면 지금 약 18~19ms다. 같은 화면 비교는 4-1이 근거다.

## 5. 남은 점

- **운영 품질 검사가 2.6ms다**(측정 도구 0.45ms의 약 6배). 실제 방 화면은 대비가 낮아 밝기 표준편차 30 미만일 때만 도는 선명도 계산(Laplacian)까지 실행되는 것으로 추정한다(미확인). 이번 변경으로 늘어난 시간은 아니고, 줄일 여지가 프레임당 약 2ms 있다 - 별도 작업.
- 측정 도구의 합성 화면에서는 모델 점수가 거의 나오지 않는다. 실제 가정 영상은 쓰지 않는 원칙이라, 박스 단위 비교가 필요하면 점수가 나오는 합성·공개 화면을 따로 만들어야 한다.
